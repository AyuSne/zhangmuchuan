前两篇里，我们已经把人机协作的两块基石铺好了：第 1 篇从第一性原理推导出了**意图下放、Prompt 与 Harness（执行底座）分家、以及模型变强后只留私有底线**的心法；第 2 篇走进 Grok Bot 团队的生产车间，看他们怎么在干净的现代客户端架构里用物理隔离和重型验证工具扛住单月 1.1 万个 PR。

但很多工程师读完这两篇，一回到自己的日常工作现场就会苦笑：

> “道理我都懂，可我接手的根本不是能从头做目录隔离的新框架——而是一个跑了七八年的企业老系统：里面躺着八百多张数据库表、连外键都没有、文档早就过期三年、状态字段里塞满了当年离职同事留下的神秘暗号（比如 `status = 9`），甚至还有几十张每天在定时写入、实际上却早已被业务废弃的‘僵尸表’。把强模型直接放进去，不光猜错业务口径，万一随手来一句全表统计查询，还能直接把线上数据库拖死。”

这正是第 1 篇末尾留下的那个核心深水区：**当通用智力极强的 Agent，真正走进信息错综复杂、充满“模型权重里天然不存在的私有现实”的企业遗留库或复杂个人知识库时，整套数据读取与知识治理体系到底该怎么搭？**

把这个问题剥到第一性原理，其实只围绕着三件互相咬合的工程难题：
1. **怎么拿上下文？**（为什么传统 RAG 在这里会失灵，它和主动探查各自该管哪一摊？）
2. **怎么安全查库？**（如何在不塞爆上下文、绝不锁死生产库的前提下，让 Agent 摸清几百张老表的底细？）
3. **怎么沉淀规则？**（那些读遍代码也猜不出来的“土规矩”，怎么靠系统机制自动长出来、防过期，并在未来自己消亡？）

## 第一层：获取机制的分岔——静态 RAG 预检索 vs. Agent 主动发现

先把底层机制拆清楚。当公司里的数据库表结构、历史视图和内部文档加起来有几百万字，远远超出大模型一次能塞进记忆窗口（Context Window）的上限时，系统必须做一道选择题：**由谁、在什么时候、按什么线索，把最关键的那一小块资料挑出来放进模型的眼里？**

过去几年，行业里最标准的答案叫 **静态 RAG（Retrieval-Augmented Generation，检索增强生成）**。2020 年，Patrick Lewis 等人在论文中正式提出这套框架：在模型开始动脑筋之前（第 0 步），先由外面的检索程序把用户问题转成一串数学向量，再靠**向量余弦相似度（Cosine Similarity）**——把两段话变成高维空间里的两个箭头，算它们之间的夹角有多接近，夹角越小越代表“字面或语义长得像”——从知识库里捞出最相似的前 $k$ 段文本，一把塞进开头的提示词里让模型回答。

打个直观的比喻：**静态 RAG 就像“出门进考场前，仅凭准考证上的几个关键字，盲猜从书架上抽 5 本参考书塞进书包里”**。

只要进了考场，书包就封死了。这招在很多场景里既快又省钱，但一旦走进复杂的企业数据库和大型代码仓库，这种<strong>“开环前馈”</strong>做法会立刻暴露出两个致命伤：

1. **抽象鸿沟（字面根本对不上号）**：用户提的需求往往是业务语言——比如“把 `/team` 企业仪表盘加载压到 2 秒以内”；而真正卡慢的瓶颈，可能藏在一张名叫 `org_member_rel_v3` 的底层关联表和一段历史视图里。这两组词在字面和向量空间里几乎毫无重合，靠相似度捞出来的 5 段文档大概率全在讲前端样式，南辕北辙。
2. **多跳因果断裂（Multi-hop Reasoning）**：解决复杂系统问题很少一跳命中，往往必须像侦探顺藤摸瓜一样连跳三步——**必须先从文档 A 查出关键表名，再去查那张表的索引结构 B，看到状态分布异常后才知道要去翻存储过程 C 里的过滤口径**。第 0 步那一次静态检索根本不知道后面会发现什么线索，链条当场就断了；而模型在书包里没翻到真实资料，又没有工具去二次找书，极易直接拿通用常识瞎猜。

面对高强度的强模型，另一条完全不同的路子叫**Agent 主动上下文发现（Active Context Discovery）**。

如果说静态 RAG 是“盲猜塞 5 本书进考场”，那主动上下文发现就是<strong>“只给你一张极简的图书馆楼层总目录，然后放你带着线索直接走进图书馆按需翻书”</strong>。我们不再由外部脚本在第 0 步替模型盲猜资料，而是把数据库和文档库封装成一组职责单一的**只读探查工具**。模型自己阅读问题后，自己评估“我现在缺哪一块拼图”，自己决定先查目录、再看某张表的字段分布、再顺着调用关系往深处翻，直到凑齐信息为止。

不过，千万不要走极端以为“主动发现永远吊打静态 RAG”。工程设计从来是算账，两种做法在真实业务里各有各的统治区：

| 对比维度 | 静态 RAG 预检索（盲猜装书包） | Agent 主动上下文发现（带目录进图书馆） |
| :--- | :--- | :--- |
| **工作方式** | 第 0 步由外部程序按相似度一次性塞入固定前 $k$ 条片段 | 在推理循环里由模型按当前信息缺口多轮触发只读工具 |
| **多跳推理能力** | **很弱**。必须“先查 A 才知道查 B”的任务几乎必断 | **极强**。天然支持沿表关联、函数调用链、视图血缘逐层下钻 |
| **上下文噪音与信噪比** | 固定抓 $k$ 条很容易陷入两难：抓少了漏关键规则，抓多了混进大量干扰废话稀释注意力 | 强模型按需拉取最小片段，初始极其干净；但前提是模型够聪明且工具输出做过精简过滤 |
| **响应速度与算力账单** | **几乎恒定且极快**。1 次检索 + 1 次大模型推理，首字延迟和预算完全可预测 | **线性叠加**。往往要来回跑 3～8 轮工具往返，耗时长，且每多一轮都要重读前面攒下的记录 |
| **对模型智商的要求** | **低**。找书的事由外部代码兜底，小模型只需要做好“阅读理解” | **高**。模型必须具备元认知能力（知道自己缺什么）和精确构造查询的本事 |

因此，划清边界就非常清楚了：
* **静态 RAG 的统治区**：面向 C 端高并发、要求 1 秒内开始吐字的场景（如客服 FAQ、行政制度问答、互不关联的杂散会议纪要或笔记检索），或者受限于成本只能上小参数模型——这时候用主动多轮探索纯属过度设计；
* **主动上下文发现的统治区**：大型代码库、几百张表的遗留数据库、需要跨模块核对的复杂财务/业务审计——这类场景**错漏一条隐性口径的代价远高于多等十几秒**，必须把探索权交给高成熟度模型。

在现代成熟的强 Agent 架构里，这两者往往收敛成<strong>“静态锚点注入 + 动态按需下钻”</strong>：在对话最开头（第 0 步），用极小的固定篇幅把绝对猜不到的总目录和顶层红线稳稳锚定在系统前缀里消除冷启动盲区；剩下的全库细节，全部交给强模型拿着原子只读工具按需去翻。

## 第二层：不爆窗口、不炸生产库的“四层渐进只读探查工具集”

既然决定放强模型自己去翻企业遗留库，紧接着必须解决两个让人睡不着觉的工程恐怖片：
* **第一个恐怖片是把上下文撑爆**：如果给模型一个工具直接吐出 500 张表的完整建表语句（DDL），几万行字段定义瞬间把工作记忆淹死，大模型直接失智；
* **第二个恐怖片是把线上生产库锁死拖垮**：老系统经常跑着核心交易，如果模型不懂规矩写出一句 `SELECT COUNT(*)` 去数一张十亿行的流水表，或者写出不走索引的全表扫描甚至带写锁的 SQL，整个公司的业务可能当场雪崩。

先顺手把数据库背景里的两个基本概念交代明白：**OLTP** 与 **OLAP**，以及 **外键（Foreign Key）**。

1970 年，IBM 研究员埃德加·科德（Edgar F. Codd）发表了奠定现代关系数据库基石的论文，提出了用二维表组织数据，并引入了<strong>主键（每行唯一身份证）</strong>和<strong>外键（一张表指向另一张表主键的关联锁扣）</strong>来保证数据不会孤立错乱。但在真实企业开发里，很多团队为了写入性能、分库分表或者图省事，**根本不在数据库层设置物理外键**——两张表其实有关联，但从表结构表面看就像两条毫无干系的平行线。后来在 1993 年，还是这位科德老爷子又造出了 **OLAP（联机分析处理）** 这个词，用来区分两种截然不同的库：一种是支撑前台下单、记账、高并发小步快跑的**事务型业务库（OLTP）**；另一种是把各处数据汇总成宽表、专门用来跑多维统计报表和商业分析的**分析型数据仓库（OLAP）**。

面对这种**表极多、外键缺失、无注释、又埋着未写进文档的状态暗号**的遗留系统，绝不能直接给 Agent 塞一个万能 SQL 执行器让它瞎跑，而必须像**特警侦探排查一栋 800 个房间的老旧档案大楼**一样，设计成<strong>“目录定位 → 统计画像 → 语义血缘 → 受控试跑”四层由粗到细的渐进只读工具</strong>——**先看楼层名录缩小范围，再抽查几个抽屉摸清暗号分布，接着翻老主管的交接手记对齐口径，最后进演习沙盘算一遍代价再小批量取证**。

### 第一层：拓扑与目录定位（把 800 张表缩成 3～5 张）

这一层的铁律是：**绝对不返回完整列结构，也绝对不数真实行数。**

1. **`search_catalog(keyword_pattern, min_rows=0)`**
   * **身世背景**：早在 1992 年的 **SQL-92 标准**里，数据库界就定下了一套跨厂商通用的自省元数据目录规范——**`information_schema`（系统目录表）**，专门记录库里有哪些表、哪些列（各家数据库内部还有像 PostgreSQL 的 `pg_catalog` 这样的底层目录）。
   * **它干什么**：按关键词模糊匹配表名、列名或表注释片段，只返回极精简的四样东西：`表名、估算行数、最近改表时间、一句话注释片段`。
   * **防炸细节**：估算行数必须直接读取数据库维护好的统计估值（如 `pg_class.reltuples` 或 SQL Server 的分区统计视图），做到 **$O(1)$ 毫秒级瞬间返回**——**严禁在工具内部偷偷执行 `SELECT COUNT(*)` 去硬数全表！** 这就像问档案室前台要一份花名册估摸每间屋有多少卷宗，而不是亲自跑进去一页一页清点。
2. **`get_table_neighborhood(table_name, depth=1)`**
   * **它干什么**：既然遗留库经常没有物理外键，拿到目标表后怎么知道它平时和哪几张表连着一起查？工具后台需要同时融合三路侦探线索来拼出“隐性关联图”：
     1. 确实存在的物理外键；
     2. 列名后缀暗合（比如 `order_id` 大概率对应 `orders.id`）；
     3. **历史查询日志（如慢查询日志或统计视图 `pg_stat_statements`）里的真实共现频率**——如果历史代码里 80% 查 `orders` 的语句都顺手关联（`JOIN`）了 `org_billing_accounts`，哪怕没建外键，工具也能按共现权重把这几张邻居表直接排在前面亮出来。

### 第二层：结构与数据分布画像（不用读原数据，摸出魔法数字）

锁定 3 到 5 张候选表后，模型不仅需要知道每列是什么类型，更需要看清物理加速通道和真实数据分布——因为数据库里写着 `INT`（整数）的列，根本看不出里面存的 `9` 到底是什么意思。

3. **`inspect_table_schema(table_name)`**
   * **背景科普**：什么是**索引（Index）**、<strong>全表扫描（Seq Scan）</strong>和**分区裁剪（Partition Pruning）**？把一张一亿行的表想象成一本一亿字的大字典。如果不建索引，你要找一个字只能从第一页翻到最后一页，这就叫**全表扫描**；**二级索引**相当于字典前面的“拼音和偏旁部首检索表”（而且多列联合索引是有顺序讲究的，就像先按省再按市查邮编，跳过省直接问市往往就用不上索引）。**分区键**则相当于档案室按“年份”分好的独立大铁柜——查询条件只要带上了 `year = 2026`，系统直接打开 2026 号柜门，把前面十年的柜子全跳过，这就是**分区裁剪**。
   * **它干什么**：拉取单张表的完整列定义、主外键、**所有二级索引的精确列顺序**以及分区键。提前把这些物理线索摆在强模型面前，聪明的大模型在下一步自己写 SQL 时，就会自觉把索引前缀和分区键写进过滤条件，从源头避免跑出拖垮数据库的慢查询。
4. **`profile_column_stats(table_name, columns, sample_rows=10000)`**
   * **背景科普**：数据库里的<strong>基数（Cardinality / Distinct Count）</strong>指这一列到底有多少种不重复的取值——比如“用户身份证号”每行都不一样，叫**高基数列**；而“订单状态（`status`）”或者“订单类型（`order_type`）”统共也就十来个固定数字反复出现，叫**低基数列**。
   * **它干什么**：对指定列执行**有界抽样（Bounded Sampling）**——比如利用 **SQL:2003 标准**引入的 `TABLESAMPLE BERNOULLI` 行级抽样（对磁盘数据按指定概率抛硬币抽一万行左右，绝不扫全库），或者按主键切片抽 1 万行。返回结果极其精炼：**绝不返回原始敏感业务行记录**，只返回这列的空值率（`null_ratio`）、不重复值估计数、最大最小值，以及低基数列的 **Top-20 高频值与占比**。
   * **实战奇效**：遗留库里最坑人的就是未写进文档的魔法数字。有了 Top-20 频次画像，模型一眼就能看到：`status = 1` 占 82%，`status = 2` 占 16%，突然有个 `status = 9` 占了 2%！不用拉任何敏感数据行，模型马上警觉起来：“这个占 2% 的 `9` 是什么东西？”

### 第三层：语义口径与血缘解析（补全猜不出来的局部公理）

看清了 `status = 9` 存在之后，怎么知道它到底能不能删、算不算有效单？这就进入第三层——补齐“模型权重里天然缺失的私有口径”。

5. **`lookup_local_axioms(entity_or_column_name)`**
   * **它干什么**：按表名、列名或业务实体名去做**精确匹配或前缀索引**（不搞模糊的向量猜词！），直接取出团队沉淀在“局部公理库”里的硬性业务口径——比如明确写死：`orders` 表计算真实营收时必须过滤 `order_type NOT IN (4, 7)` 且排除测试单 `test_flag = 1`。
6. **`trace_object_definition(object_name)`**
   * **背景科普**：这里顺带讲透三个数据库老概念与**数据血缘（Data Lineage）**——**数据血缘**就像追踪一条大河下游的水到底是从上游哪几条支流汇过来的（一个最终指标经过了哪些清洗、合并和过滤）；<strong>视图（View）</strong>是一张保存下来的虚拟查询窗口；<strong>存储过程（Stored Procedure）</strong>和<strong>触发器（Trigger）</strong>则是直接驻留在数据库内部自动运行的一段段历史程序脚本；<strong>ETL（抽取-转换-加载）</strong>则是每天半夜把业务库数据洗一遍倒进分析数仓的搬运流水线。
   * **为什么这招极管用**：很多老公司的 Wiki 文档早就没人更新了，但公司真正跑了几年的**真实业务口径，往往死死固化在老视图、存储过程或 ETL 脚本的 `WHERE` 和 `CASE WHEN` 条件里**。让 Agent 能按需读取引用了目标表的这些历史定义代码，等于直接请出了当年的老架构师当面口述计算口径。

### 第四层：受控只读验证与执行代价探针（先算过路费，再在副本拿 50 行）

综合前三层情报写出一条 SQL 之后，绝对不能直接丢到生产主库上盲跑，必须经过两道安检闸门：

7. **`explain_query_plan(sql)`**
   * **它干什么**：只执行 **`EXPLAIN`（注意：绝不带 `ANALYZE` 实际运行）**。相当于开车上高速前先看一眼高德地图导航算出来的预估路线与拥堵代价，车根本还没发动。工具直接解析数据库优化器给出的执行计划，抽成干净的几项风险指标回传给模型：有没有触发大表全表扫描（`Seq Scan`）？预计扫描多少行？有没有命中分区裁剪？预估总代价（`total_cost`）是多少？如果预计扫描行数越过红线，工具直接退回一句高亮告警，逼着模型自己回去改写过滤条件。
8. **`execute_bounded_query(sql, max_rows=50, timeout_ms=3000)`**
   * **背景科普**：什么是<strong>只读从库（Read Replica）</strong>和 **AST（抽象语法树）**？
     * 生产环境的主库就像商场门口一线收银台，一秒都不能卡；而**只读从库**是后台实时同步出来的一台专门用来查账的镜像副本——即便查账脚本把从库跑慢了，前台顾客依然照常结账。
     * <strong>AST（Abstract Syntax Tree，抽象语法树）</strong>则是源自 20 世纪五六十年代编译器前端语法分析理论的数据结构（和早年 Chomsky 形式语法、Lisp 语法树等一脉相承）。它能把一串平铺的代码文本拆解成严谨的“树状结构”——谁是主查询动作、谁是子查询、有没有隐藏关键字一眼看穿，比用正则字符串匹配去拦关键字靠谱一万倍（正则很容易被注释和大小写绕过）。
   * **Harness 层的三道物理锁死**：即使路由到了只读从库，执行底座依然会强制施加三道不可越界的硬保险：
     1. **AST 语法树安检**：解析 SQL 抽象语法树，只放行纯查询节点（`SELECT` / `WITH`），一旦树里混进了改表、删数据、甚至加行锁提示（如 `FOR UPDATE`），在解析阶段直接物理拦下；
     2. **强制边界包裹**：在模型写的 SQL 外层强行套一层 `SELECT * FROM (<sql>) _sub LIMIT 50`，同时在会话级写死只读事务与 3 秒强制超时熔断（`SET TRANSACTION READ ONLY; SET statement_timeout = 3000`）；
     3. **宽字段自动截断**：如果某行记录里的 `TEXT` / `JSON` / `BLOB` 字段里塞了几兆大日志，自动超过 `256` 字符就截断并标明原始字节数——绝不让一条脏数据撑爆模型上下文。

这 8 个小工具摆在一起，Agent 面对完全陌生的老库再也不用瞎猜了，而是稳稳沿着<strong>“先定子图位置 → 摸清数字分布 → 核对历史口径 → 算清代价再只读小样本试跑”</strong>的安全通道收敛到位。

## 第三层：局部公理库的全生命周期治理——怎么沉淀，怎么防腐烂？

现在走到最后一环，也是最容易在半年后“烂尾”的环节：第 1 篇里我们确立了<strong>“局部公理（Local Axioms）”</strong>（模型看遍全库代码依然会猜错的组织隐性规则）必须写下来。但在真实团队里，大家最怕两件事：
* 一开始靠热情写了份企业规则文档，忙起来三个月没人维护，**文档和代码对不上，过时规则反过来变成毒害 Agent 的毒药**；
* 只指望程序员每逢修个 Bug 就“自觉去更新知识库”，这在激励机制上根本违背人性——赶需求上线还来不及，没人有空天天去补 Wiki。

要让这套“局部公理库”真正能活下来、越用越准，必须把它当成**代码基础设施本身**来治理，走通<strong>“准入筛选 → 物理锚点建模 → 轨迹差分自动挖矿 → CI 活性清理与消解”</strong>四步闭环。

### 第一步：严苛的准入关——“反事实检验”过滤噪音

公理库最值钱的品质不是“大而全”，而是**克制**——每多塞进一条废话，都会吃掉一点模型注意力、多一分规则打架的风险。进库之前，必须过一遍第 1 篇提过的**反事实检验（Counterfactual Test）**：“如果把全部源码和表结构给最强模型看、只撤掉这条规则，它还会不会出错？”

只有四类真正的硬骨头才配入库：

| 公理类型 | 为什么模型看代码也推不出来 | 真实工程实例 |
| :--- | :--- | :--- |
| **1. 语义重载与魔法值** | 字段名字和整数类型极具欺骗性，实际业务含义全靠当年口头约定 | `orders` 表中 `status = 9` 并非订单取消，而是财务跨月对账占位符，统计成交量必须排除 |
| **2. 僵尸资产与逻辑废弃** | 表物理上不仅存在，甚至每天还有历史定时脚本往里写数据，但主链路早已换了 | `user_profile_v2` 表虽每日仍有同步写入，但主业务早已切至 `account_core`，严禁新查询引用前者 |
| **3. 跨边界统计口径** | 业务核算规则分散在部门协议里，没有写进数据库约束或单一函数里 | 计算“企业活跃租户数”时，必须同时满足 `trial_flag = 0` 且剔除内部测试账号 `org_id < 10000` |
| **4. 隐性物理与合规红线** | SQL 语法完全合法，但跑起来会直接拖崩生态或踩进合规禁区 | `audit_logs` 表未在 `created_at` 上建全局索引，任何查询必须携带 `tenant_id` 分区键，否则触发全表扫描锁库 |

### 第二步：结构化建模——把“散文手册”改成“路口警示牌”

人类喜欢读散文式 Wiki，但给 Agent 喂长篇散文是灾难——既浪费开头空间，用向量模糊检索还经常漏召回。

更好的工程设计，是**不在景区大门口发一本 200 页的安全手册让游客全背下来，而是在悬崖栈道口、深水区边缘、高压电箱旁边精准钉上一块“此处水深禁跳”的物理警示牌**——平时不占大脑容量，只有当人真正走到那块地方时才确定性弹出提醒。

落到工程上，每条公理都用带着<strong>物理锚点（Environment Anchors）</strong>的机器可读结构化配置文件（如简洁易读的 YAML 格式）来存。看下面这个真实的示范条目 `AX-ORD-014`（其中 `GMV` 指商品交易总额）：

```yaml
axiom_id: "AX-ORD-014"
# 1. 物理锚点：只有当 Agent 触及下面这些表、列或源码模块时，才自动挂载弹出
anchors:
  tables: ["db_core.orders", "dw_fact.dwd_order_detail"]
  columns: ["status", "order_type"]
  code_modules: ["src/billing/revenue_calculator.py"]

# 2. 公理类别与硬约束级别
category: "SEMANTIC_INVARIANT"
severity: "HARD_CONSTRAINT"

# 3. 机器可读规则：只写无歧义的条件与结论，剔除背景废话
rule: >
  在 `orders` 表中，`status = 9` 代表财务跨月对账冻结状态，不属于有效成交或用户取消；
  任何涉及 GMV 或有效订单量的聚合查询，必须显式包含过滤条件 `status NOT IN (9, 99)`。

# 4. 反事实纠偏警示：正面狙击强模型最容易犯的“行业常识先验覆盖”
anti_pattern: "切勿仅凭 `status > 0` 或 `is_paid = 1` 判定有效营收订单。"

# 5. 责任人与代码活性绑定
owner_team: "billing-core"
last_verified_commit: "a8f92d1"
```

这套结构妙在哪儿？
* **零幻觉精确触发**：只要 Agent 调用 `inspect_table_schema("orders")` 或者打开 `revenue_calculator.py`，底座立刻顺着 `anchors` 自动把 `AX-ORD-014` 贴到工具返回结果里送过去——**平时不花一个 Token，碰到就 100% 召回**；
* **直接狙击先验偏见**：专门设计了 `anti_pattern`（反模式警告）字段，直接针对强模型最容易顺手写错的那句“经验直觉”设路障。

### 第三步：沉淀闭环——不靠程序员自觉写文档，靠“纠偏差分挖矿”

怎么把这些公理攒起来，而不依赖大家下班后苦哈哈地手写文档？最干净的办法是把收集器直接焊进日常流水线里，这就像**师父平时批改徒弟交上来的作业——师父只要拿起红笔改了一处，系统自动把改前改后的对照收进错题本，根本不用师父单独腾出一小时写教学笔记**：

1. **人机纠偏轨迹差分（Human-in-the-Loop Trajectory Diff）**
   这是纯度最高、成本最低的公理来源。当强模型提交了一版语法完美、逻辑自洽的 PR 或 SQL，人类专家审稿时用红笔改了一笔——系统自动对比<strong>“Agent 提交版”</strong>和<strong>“人类修改合入版”</strong>的差异。如果改的不是拼写或算法，而是人类突然在 `WHERE` 里硬塞进了一句 `status NOT IN (9, 99)`、或者悄悄把 `user_profile_v2` 换成了 `account_core`，系统立刻弹出个一键确认草稿：“检测到一处业务口径纠偏，是否生成局部公理保存？”审稿人点一下确认就入库了。
2. **冷启动历史资产挖矿（Query Log & Commit Mining）**
   项目刚起步还一条公理都没有怎么办？直接派强模型离线扫两样现成矿藏：
   * **历史 SQL 审计日志聚类**：跑一圈高频查询日志，如果发现 95% 涉及 `orders` 表的查询里都顽固地带着同一句奇怪的 `tenant_id != 0` 过滤，八成就是一条没人写进文档的铁律；
   * **Git 修复记录挖掘**：专挑代码提交历史里写着 `hotfix`（线上紧急修复）、`口径修正`、`边界兼容` 的提交记录，提取那些当年踩血坑补上去的防御逻辑。

### 第四步：防中毒与最终消解——公理库的宿命是“自己消亡”

如果只管往里加、不管清理，半年后业务重构改了表名，老公理就会变成误导下一代 Agent 的剧毒垃圾。因此，公理库必须像生产代码一样纳进持续集成自动化流水线（CI/CD）管理：

* **CI 符号活性检查（Symbol Liveness Check）**：每次代码合入或者数据库结构发生变更时，自动化流水线顺手扫描所有 YAML 公理里的 `anchors`。一旦发现某条公理绑定的表名、字段名或源码路径已经被重命名或删掉了，系统当场把这条公理打上 **`STALE`（失效）** 状态标签并切断自动注入——绝不允许过期幽灵继续混进模型脑子里，同时逼着 `owner_team` 上来更新或归档。
* **终极目标：把文字规则写进代码，让公理库越用越小**：别把公理库当成永久膨胀的荣誉墙。如果某条 `AX-ORD-014` 天天被触发，最好的工程动作其实是抽空做一次小重构——在代码里把神秘的数字 `9` 命名成语义清清楚楚的枚举常量 `STATUS_FINANCE_RECONCILIATION`，或者干脆在数据仓库里封装一层已经把 `test_flag = 1` 和 `status IN (9, 99)` 全过滤干净的标准宽表视图。**一旦隐性约定变成了显式代码与表结构，对应那条文字公理就可以安全删除——系统里需要靠提示词兜底的隐形坑，也就永久少了一个。**
