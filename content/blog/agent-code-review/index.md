一个工程师让 Agent 修复订单页面。几分钟后，代码写完了，测试也是绿色的，审查 Agent 又说：“没有发现问题。”

工程师看着这句话，手指停在合并按钮上：**我现在究竟知道了什么？**

测试通过，说明运行过的断言没有失败；审查没有发现问题，说明审查者没有报告它认为需要提出的问题。但如果测试没有覆盖退款，如果审查者也不知道公司的退款约定，这两份看起来令人安心的反馈，能回答退款是否正确吗？

上面的订单页面是一个假设场景。问题却越来越现实：Agent 让代码产生得更快，人不可能因为变化速度翻倍，就让自己的注意力也翻倍。那是让人继续逐行阅读，还是让机器审完就合并？

我想先把这两个选项放一边。真正需要追问的是：**一个改动要获得怎样的证据，才能让承担后果的人有理由相信它可以进入下一阶段？这些证据应该由谁提供，又要付出多少代价？**

Claude Code 团队在 2026 年 10 月发表的[工程文章](https://claude.dev/blog/solving-code-review-at-anthropic/)提供了一个值得拆解的案例。他们报告：当年 6 月到 9 月，Claude Code 代码库合并的 PR 数量增长到两倍以上，被回退的 PR 占比下降超过 40%。这是团队披露的同期变化，不足以单独证明某一项措施造成了下降；但它给了我们一个具体问题：当人工阅读减少时，团队用什么补上审查的信息与反馈？

## 一、审查不是多说一次“没问题”，而是取得判断所需的依据

在[《数学基石篇》](/zhangmuchuan/blog/agent-math-foundations/)里，我们把外部真实状态记为 $Z$，模型已经取得的上下文记为 $C$，仅凭这个上下文生成的自评记为 $R$。如果模型参数固定，且本次自评没有接收额外的外部信息，可以写成：

$$
Z \longrightarrow C \longrightarrow R
$$

假设模型的参数和先验固定，采样过程也没有携带关于 $Z$ 的额外侧信息，那么在这个设定下：

$$
I(Z;R\mid C)=0
$$

这个式子回答的是一个很具体的问题：**给定完整的 $C$ 后，这次自评有没有额外引入关于 $Z$ 的外部证据？** 条件独立意味着已知 $C$ 时，知道 $R$ 不再改变对 $Z$ 的条件分布，因此链式法则里的增量项为零。这是模型设定下的信息论结论，不等于实际执行者已经充分利用了 $C$：有限能力的执行者可能第一次漏看了需求，重新检查时才注意到；已有信息能否被利用，与有没有取得新证据，是两笔不同的账。

想象你订了一个蛋糕，嘱咐店家不要放花生。店员做完后，盯着订单和盒子想了一遍，说“应该没有”。如果他刚才漏看了订单上的忌口，现在重新看见了，复查就有用；但光靠订单，他仍不知道厨房实际用了什么。于是他去看配料记录，发现奶油含花生，赶紧拦下蛋糕，询问厨房并安排重做。订单提供比较标准，配料记录提供实际制作的新线索，两者对不上才改变了交付决定。记录也可能填错，因此厨房核实仍有价值。

代码审查也是如此。需求说明提供期望行为，改动和执行结果提供被检查对象，审查者把它们放在一起比较。**测试命令返回退出码是一次运行事实，断言是否覆盖需求则是另一个问题。** 模型在新窗口审查也可能换一个注意角度，或读到原执行者没读过的资料；但新窗口不是独立性的保证。两个 Agent 可能拿着相同的不完整需求，也可能同时漏掉同一条业务规则。

Claude Code 团队描述的做法，是在提交 PR 前让 Agent 运行测试、构建等检查并展示输出，再用新上下文中的子 Agent 看改动；PR 上还会有自动审查和安全审查。这里重要的不是审查者换了几个人，而是每一步到底读取了什么、带回了什么、依据什么标准判断。资料没有证明这些审查能发现所有问题，也没有说自动审查可以替代每个要求人工批准的位置。

## 二、人的注意力为什么不能只看审查前半段的账？

假设蛋糕店每天只接十个订单，店长可以逐个检查。后来订单增加到一百个，他找人检查尺寸、配送时间和配料标记，自己重点处理过敏原不明或特殊定制的订单。一次生日蛋糕送错地址，店长不但要退款，还要协调重做、重新配送，忙了一个下午。若这种事反复发生，他减少逐盒检查省下的时间，就可能被事后处理吃掉；他需要回头看是地址记录、交接还是配送环节出错，再决定在哪里增加检查。对应到代码，逐个 PR 的审查耗时和合并后修复耗时，都属于同一笔总成本。

代码变更也一样。衡量成本不能只看“审查花了多少分钟”，还要看遗漏带来的返工、事故处理，以及误报让作者做出的无效修改。我们在[《第二篇》](/zhangmuchuan/blog/agent-control/)用信息净价值来追问一次行动是否值得：

$$
V(a\mid C_t)=\operatorname{VoI}(a)-\lambda\operatorname{Cost}(a)
$$

这里 $a$ 可以是一轮人工审查、一次自动检查，或一次上线后的观测；$C_t$ 是此刻已有的信息；$\operatorname{VoI}(a)$ 表示行动带来的决策价值；$\operatorname{Cost}(a)$ 包括执行、等待与处理反馈的代价，$\lambda$ 表示成本和风险在当前决策中的权重。《数学基石篇》将 VoI 用反馈信息增量来表达；这里进一步区分两者：知道更多事实未必改变行动，能够改变行动也未必抵得过成本。因此这个式子在本文是**定性比较框架**；若要计算，就必须先把收益和成本转换成可比较的效用单位，不能直接把比特数减去事故损失。

例如，一条类型检查报错可以在合并前廉价指出明确错误；一次资深工程师的审查则可能发现“这个功能方向本身不该做”，但也会占用稀缺注意力。两者并非互相替代：前者擅长执行可形式化的标准，后者可能掌握尚未写进代码的产品目标、组织约束和责任边界。

原文中，团队把每个 PR 的人工批准次数、评论和等待人工的时间作为观察人工投入的指标，同时把回退率与事故率当作护栏。这个设计值得注意：**减少批准次数只是节约审查成本的候选信号，只有结合后果一起看，才能判断成本是否真的下降。** 回退率和事故率也不是完美的真值：有的问题可能没有触发回退，有的长期维护损失可能要很久才显现。它们提供的是监测方向，而非质量已经得到证明。

## 三、多层检查为何有效，又为什么不能把“多”当成“独立”？

回到恒温器：只知道房间现在多少度，还得知道目标温度，才能判断是否需要加热。代码审查也需要两层：**先采集事实，再拿标准比较**。构建日志、测试输出、代码差异是观察材料；需求、项目约定、安全规则是比较依据。材料和标准缺一块，后面的结论就会受限。

原文描述了一个分阶段的系统：PR 前运行检查并复核差异；PR 上运行 CI、自动代码审查和安全审查；有未解决的审查意见时不能合并；风险分类决定是否需要人工批准；合并队列在最新主干与该改动组合后重新运行检查。新功能通常先通过开关向内部开放，再逐步发布，发现问题后可以关闭开关或回退。

以假设的退款修改为例：提交前需求和已有规则进入 Agent 的前馈；它运行测试后，退出码及失败位置作为外源反馈进入 Context。若测试覆盖“退款金额正确”，却没覆盖“已取消订单不能重复退款”，绿色结果不会回答后一个问题。审查 Agent 读取差异与需求后形成意见；如果它又读到了原执行者没看过的退款规则，便可能取得新的外源依据；如果需求本身漏写了约束，大家仍可能共同漏过。审查意见是模型判断，不能和测试输出或原始规则混成同一类事实。

接下来，合并队列把改动与最新主干组合后重跑检查，可能带回单独测试时没有出现的冲突；分阶段上线后的内部使用又可能暴露模拟环境中未观察到的问题。原文要求审查和安全意见在合并前关闭：可以修复，也可以说明理由后关闭误报，因此关闭不等于问题必然已修复。**多层有价值，是因为观察条件、标准和时间点可能不同，而不是因为把同一个问题问了更多遍。**

但如果测试和审查都沿用一份错误需求，或者所有模型都没有看到真实业务规则，增加轮数也可能一起漏掉它。把多个审查者的漏报概率相乘，必须先有独立性等条件；实际共享模型、材料和假设时，不能直接这样算。原文的多 Agent 并行发现、其他 Agent 投票核验，能为过滤意见提供另一轮判断，却不意味着多数票自动变成事实。审查意见仍需要指向具体代码、调用路径或可复现证据。

这也使[《第三篇》](/zhangmuchuan/blog/agent-harness/)里的 $(P,M,H)$ 更容易落到具体工作上：$P$ 是程序能执行的检查，$M$ 是模型对语义和代码关系的判断，$H$ 是人对目标、风险和后果的判断与责任。它们不是三张自动盖章的通行证；每一条反馈都要问清楚：它看到了什么，没看到什么？

## 四、审查得越久，为什么反而可能离交付越远？

设想你请两位朋友帮忙检查搬家的箱子。第一轮他们发现新家地址写错、冰箱尺寸还没量，这些问题值得停下来处理。之后他们每轮都重新检查早已打包的箱子：一轮发现杯子垫纸不够，一轮觉得标签位置不醒目。每项可能都有道理，但你每次都要拆箱、调整、重新封好，搬家车迟迟没出发。限定轮次可以让搬家继续，却也可能漏掉还没发现的重要物品，所以不能只凭“轮次到了”断言东西都安全。

Claude Code 团队披露过一个类似的工程现象：一个 CLI PR 在一夜之间经历了五十多轮审查和修改，最后由作者叫停。团队分析审查者持续指出的代码时，约 59% 在第一轮审查时就已存在。这个比例是针对该分析对象的报告，不等于所有意见都是误报，也不等于所有问题都不重要；它说明反复审查可能不断从旧范围中提出新意见，导致完成边界后移。

把过程放回信息账里。以目标 $Z$ 固定、交接信息完整保留为理想条件，系列中的判据写作：

$$
I_{\text{前馈}}+\sum_k\Delta I_{\text{反馈},k}\geq I_{\text{目标}}
$$

其中目标信息阈值由对 $Z$ 的剩余不确定性容差定义。它帮助我们追问前馈和反馈是否补齐信息缺口，不能单凭不等式宣称现实 PR 的正确性已被证明。旧代码里首次发现的严重错误可能带来有价值的新线索；重复意见不一定再增加信息，误报则可能引入错误判断。每条意见还要消耗理解、核查和修改的成本。若作者是 Agent，一条错误建议可能触发新提交和下一轮审查。**评论变多不自动等于目标所需的证据变多，也不等于收益大于返工成本。**

团队因此设置轮次约束：三轮后请作者重新审视方案；前几轮之后主要复查新差异；要求指出同类问题以便一起处理，并避免重复报告。关键取舍是：限制旧范围的反复扫描，能降低无休止返工，也可能漏掉先前没看到的旧问题。原文同时提到团队另有夜间审查既有代码的做法；这提供了处理旧问题的另一条通道，但不能保证每个遗漏都会被抓到。

因此，“停止”不是因为看到绿色文字就宣布完成，而是结合剩余风险、已取得的证据和继续审查的预期收益作决定。高风险改动可能值得多投入一轮，低风险改动若只剩争议性的细枝末节，继续自动修改可能制造比收益更大的成本。

## 五、人工批准变少，风险去了哪里？

在[《第四篇》](/zhangmuchuan/blog/agent-business/)里，我们用“草稿纸”和“手术台”比较试错条件。草稿纸写错可以擦，手术台上的动作却可能无法低成本撤回。现实系统介于两者之间：同样是代码改动，更正文案与修改自动更新器，潜在影响并不一样。

原文里的团队按改动风险设置不同人工批准要求：低风险变更在自动检查通过后可不要求人工批准，中风险需要一人，高风险需要两人；轻量路径只适用于受信任作者，敏感路径还有固定的人审要求。第二个分类器还会判断某次变更是否需要额外的人；分类器本身也可能误判，固定的人审路径是另一层保障，而非误判不可能发生的证明。模型批准不能冒充要求中的人类批准；批准针对具体提交，之后出现不能保证的新增提交时，需要重新批准。

这一点与“人完全退出”相差很远。即使低风险变更可以没有额外人工批准，发起改动的人仍要对结果负责。更重要的是，低摩擦审查依赖后续的开关、内部使用、分阶段发布、监测和回退。它改变了问题出现时的发现速度与可能损失，但回滚并不能消除一切后果：数据泄露、外部通知或不可逆的业务动作，不一定能靠撤回代码恢复。

这里也出现一个容易忽略的事实过期问题：人批准的是哪一版？如果批准后又追加了提交，或者两个单独通过检查的改动合在一起出现冲突，旧结论就不能自动覆盖新的状态。原文中的提交级批准与合并队列，分别针对这两种时间差重新取得证据。它们不能证明上线后必然安全，却能减少“检查过的东西”和“真正进入主干的东西”不一致的空间。

资料还明确承认，团队当时尚未建立在回退率或事故率变化时自动收紧审批的断路器；工程师希望在更多代码走向零人工合并前拥有它。这一点很关键：监测数字有人看，并不等于系统已经自动完成风险控制。

## 六、谁来审查审查者？

如果自动审查成为重要关口，它本身也会产生错误。审查者漏报，问题可能进入下一阶段；审查者误报，作者可能为不存在的问题改坏代码。于是我们需要把原来的闭环扩大一圈：**不仅审查代码，也要观察审查机制的真实结果。**

原文说，团队收集造成事故的历史 PR、后续修复和回退，由熟悉代码的工程师确认问题及位置，再让审查器每天运行这组评测。团队还观察作者如何处理评论：修复、指出错误、说明行为有意为之，或判断问题不重要；并在已知干净的 PR 上检查会不会提出导致有害修改的建议。

以假设的一次退款事故为例：上线后发现重复退款，团队保存当初的 PR、审查记录、事故现象及修复，再由熟悉代码的人确认缺陷。后来调整审查提示词时，可以让新版审查器重新检查那份历史改动，观察它是否指出相同问题；若回答有争议，再回到原始记录核对。这些信息在事故发生后的调查中是反馈，在以后评测审查器的阶段则成为可读取的依据；是否实际读到、是否仍适用，要看新的执行和项目状态。

这对应[《第六篇》](/zhangmuchuan/blog/agent-memory/)讨论的时间接力：整理后的评测集可以在多次更新中分摊搜索与理解成本，但整理、人工核对及随代码变化维护也有代价。保留原始 PR 和修复，让后来的人能重新判断；只留下“某种代码危险”一句话，就可能丢掉关键条件。

同样，历史事故集只能覆盖已知发生过的问题。每天在旧题上得分提高，不代表新型故障一定会被发现；作者关闭评论，也不自动证明审查者错了。它们提供值得进一步核查的信号。真正的改进需要把意见、回应、实际改动与后果接起来，而不是把一个数字当成终点。

## 七、人少读代码以后，团队怎样保持理解？

代码审查还有第二个工作：让团队知道系统变成了什么样。假设蛋糕店只有机器核对订单，店长从不观察制作过程，短期也许出单更快；等到一批特殊订单出了问题，他可能连厨房最近换过什么原料都不知道。

Claude Code 团队坦言没有为知识共享建立正式流程。他们描述的做法包括：需要了解某个模块时，让 Claude 针对当前代码生成解释；团队也在开放频道交流正在进行的工作。假设工程师接手退款模块，先让模型画出请求经过的函数，再沿解释中的路径读实际代码和相关变更，发现一个旧分支已被新版本替换，于是更新理解再开始修改。解释帮助定位，代码与记录提供可核对的依据；没有主动提问的人，也未必自然知道别人正在改动什么。

这让我们看到人工注意力的另一种用途：不是要求每个人读完每一行，而是在高影响决策、跨模块边界和对后果负责的时刻，确保有人知道目标是什么、依据是什么、系统哪些部分可能受到影响。维护可回查的记录，能帮后续接手的人进入现场；但整理层需要更新，不能替代持续核对。

所以，Agent 写得比人看得快之后，代码审查真正要守住的，是一条从**目标、事实、判断到结果**都能接上的链：清楚审的是哪一版，知道检查能覆盖什么，让不同来源的证据在合适时刻进入判断，并为失误保留发现和恢复的通道。

人类的时间是有限的，模型的审查也不是免费的。好的系统需要不断比较两边的代价：少一次无效的逐行等待，多一份能改变决定的证据；也要承认，有些风险还没有便宜可靠的自动答案，需要人留下来理解、决定并承担后果。
