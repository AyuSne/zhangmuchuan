> 本文结合智能体第一性原理讨论相关工程实践，主要参考[原文](https://claude.dev/blog/solving-code-review-at-anthropic/)。

凌晨一点，你交给 Agent 的重构任务只用三分钟就跑完了，顺手还补齐了八个单元测试。CI 面板全绿，自动化审查 Agent 也在 PR 下面留了一行通过提示：`LGTM，未发现逻辑错误与安全风险`。

这是如今引入 AI 编程后最常见的一幕工作场景。鼠标停在 `Merge` 按钮上时，真正卡住你的问题是：**看着满屏绿灯，你此刻究竟能确认什么？**

如果这段重构漏掉了负数扣款的边界条件怎么办？如果写代码的 Agent 和写测试的 Agent，从一开始就按同一套误解理解了需求怎么办？第二天线上出了资金差错，复盘会上总不能指望一句“自动审查机器人告诉我可以合”来交代。

这就是代码审查眼下面临的结构性矛盾：**代码生成的吞吐量被模型成倍放大，但人类工程师逐行阅读、核对语义的注意力带宽并没有变宽。**

继续沿用旧办法，只会出现两种结果：要么强求人工逐行把关，导致 PR 积压、研发节奏卡死；要么人看不过来干脆闭眼点批准，把本该拦截的风险留给线上故障去暴露。

Anthropic 的核心工程团队在[《How the Claude Code team does code review》](https://claude.dev/blog/solving-code-review-at-anthropic/)中给出了一组很反直觉的数据：
- 在 Anthropic 的主代码库（Monorepo）中，每天落地的变更从 5 月的约 2,500 次增长到 9 月的超过 30,000 次；在独立的 Claude Code 仓库里，**约 90% 的代码由 Claude 编写**；
- 从 6 月到 9 月，Claude Code 仓库合并的 PR 数量翻了一倍以上，但需要**回退（Revert）的比例却下降了超过 40%**；
- 团队的大多数 PR 在合入主干前，**至多只需要一个人审批**（很多时候就是发起变更的本人），而文档修订、纯内部工具等低风险变更在自动化检查通过后不需要人类点击批准即可合并。

代码量翻倍、人工审批变少，回退率却大幅下降。这并不是靠放松要求碰运气，而是把“人类逐行读 Diff”拆成了更符合信息论与控制论的多层防线。

下面我们顺着这套第一性原理，一步步拆解：**当机器写得比人看得快，每一层审查到底在提供什么信息增量，人类又该把有限的注意力留在哪里？**

### 一、 黑屋里的考卷：为什么自我审查与自编自测常常无效？

很多团队接上 Coding Agent 后，最习惯在 Prompt 末尾加一句：“写完以后仔细检查一遍，确认没有 Bug。”表面上看，模型会认真复查十几秒，输出几条检查项，然后汇报“逻辑完整，未发现遗漏”。

但放在[《数学基石篇》](/zhangmuchuan/blog/agent-math-foundations/)的信息论框架下，这种“同源复查”往往是在原地空转。

首先按**公理一（马尔可夫隔离公理）**与**定理一（数据处理不等式 DPI）**，大语言模型的参数权重 $\theta$ 在单次推理中是物理冻结的。设外部真实环境（真实需求意图、运行时物理约束）为 $E$，当前窗口里塞进来的上下文为 $C$，模型基于 $C$ 生成的输出为 $R$，只要没有引入新的外部观测，整个过程服从单向马尔可夫链：

$$
E \longrightarrow C \longrightarrow R \implies I(E; R \mid C) = 0 \implies I(E; R) \le I(E; C)
$$

也就是说，模型输出关于真实世界的信息量上限被当前上下文 $C$ 严格锁死。

进一步把关注焦点收窄到本次具体交付目标：设真实业务需求为随机变量 $Z$，模型在第 $t$ 轮拥有的上下文为 $C_t$，在同一个对话窗口内未接入新观测即生成的口头复核结论为 $R_{\text{自评}}$。依据**定理五（脑内纯复盘增量归零定理）**，因为仍满足单向马尔可夫链 $Z \longrightarrow C_t \longrightarrow R_{\text{自评}}$，直接得到：

$$
\Delta I_{\text{自评}} = I(Z; R_{\text{自评}} \mid C_t) = 0
$$

模型单靠自己再口头复盘一遍，对揭示外部真实需求 $Z$ 的条件互信息增量严格为零。它只能把 $C_t$ 里原本写进去的前提（哪怕是漏了边界、甚至写反了的前提）重新顺一遍，无法凭空长出窗外缺少的事实。

用日常生活里的**考场自查**就能看清这层因果：

> 一位高三学生坐在考场里做立体几何大题。第一步列方程时，他把余弦定理里的正负号记反了。接下来二十分钟他算得很流畅，草稿纸写满两页，得出了一个看起来工整的答案。
>
> 交卷前监考老师提醒“再仔细检查一遍”。这位学生从第一行算到最后一行，每一步加减乘除都核对了三遍，没有发现任何计算笔误，于是放心交卷。问题在于，他用来核对答案的那套错误公式，和他刚才做题时用的是同一份记忆。只要没人把标准公式表递到他桌上，他自己查十遍，答案依然是“我觉得全对”。
>
> *（这个生活类比到“闭门复查查不出前提错误”为止；如果他自己做题时只是某一步加减法粗心算错，复算当然能查出来——工程中真正危险的不是拼写错，而是前提理解偏差。）*

开篇那“八个全绿的单元测试”也是同样的道理。设主 Agent 基于上下文 $C_t$ 形成的理解假设为 $\hat{Z}(C_t)$，它自己编写并运行测试后拿到的结果输出为 $O_{\text{自测}}$。根据[《数学基石篇》](/zhangmuchuan/blog/agent-math-foundations/)的**定理六（自主自测的同源盲区与作弊定理）**，并在本系列此前的分析中进一步厘清：定理六真正依赖的条件是**错误假设同源（共享了同一个 $\hat{Z}(C_t)$）**。当 Agent 对需求的理解存在偏差（$\hat{Z}(C_t) \neq Z$），并且同时掌握“改业务代码”、“改测试断言”和“挑选测试用例”这三项权限时，业务实现与测试断言同源于同一误解，还会顺手绕开负数、空值或跨模块交互等自己没想到的边界。此时测试全绿，只证明代码与它脑子里的错误假设自洽，对暴露需求理解偏差的信息增量依然为零：

$$
I(Z; O_{\text{自测通过}} \mid \hat{Z}(C_t), C_t) = 0
$$

为了打破同源盲区，Claude Code 团队在进入 PR 审查前就先做了两道隔离，对应[《第三篇》](/zhangmuchuan/blog/agent-harness/)的 $(P, M)$ 两根独立基矢：

1. **程序化硬校验 $P$**：不听模型口头汇报“已完成”，必须把真实命令（单测、构建、Lint、类型检查或界面截图比对）跑起来，把冷冰冰的运行输出交回窗口。编译器、测试运行器和类型系统的执行方差严格为零（$\operatorname{Var}(P) = 0$），能立刻给出与模型主观愿望无关的物理反馈。
2. **空白上下文子 Agent 审查 $M$**：用**全新上下文（Fresh Context）**启动另一个子 Agent 来看 Diff。因为新窗口看不到作者刚才一步步妥协和自我说服的对话历史，它不会继承刚才那条推理惯性。

不过这里也要补充一个边界：按本系列此前的分析的校准，**“换一个窗口”只切断了对话历史污染，并没有自动切断用例和假设切分带来的盲区**。如果业务判据（Test Cases）本身也是同一个 Agent 挑着写的，或者审查规则漏掉了跨域场景，第二只眼睛同样看不见那块缺失。因此，核心业务的验收判据与用例选择权必须与实现彻底分离。

### 二、 五十轮拉锯夜战：为什么审查不是轮次越多越好？

引入独立审查 Agent 以后，是不是让编码 Agent 和审查 Agent 自动对话、把所有意见全改完就行了？

Claude Code 团队披露过一个很具象的反面案例：

> 在他们自己的一条命令行工具（CLI）PR 上，作者开着自动化循环让编码 Agent 和审查 Agent 自己对接。一个晚上过去，两个 Agent 来来回回跑了**超过 50 轮**的“提意见—修改代码—再提交—再审查”，直到作者醒来手动喊停。
>
> 事后团队用 `git blame` 追溯审查 Agent 在后续轮次里不断挑出来的问题，发现其中**约 59% 的代码问题从第一轮审查时就已经存在了**。

为什么两个 Agent 会互相卡在原地跑五十轮？用[《第二篇》](/zhangmuchuan/blog/agent-control/)和[《数学基石篇》](/zhangmuchuan/blog/agent-math-foundations/)的**信息净价值方程（Net VoI）**一算，账目就清清楚楚：

$$
V(a \mid C_t) = \Delta I_{\text{反馈}}(a) - \lambda \operatorname{Cost}(a)
$$

其中，$C_t$ 是当前审查所处的上下文状态，$a$ 代表“再发起一轮审查并据此修改提交”的候选动作，$\Delta I_{\text{反馈}}(a)$ 是这一轮审查给本次变更带来的有效缺陷定位信息增量，$\operatorname{Cost}(a)$ 则是付出 Token、时间等待、全量 CI 重跑以及每次改代码新引入回归缺陷的代价，$\lambda > 0$ 是团队把成本和风险折算进信息尺度后的权重系数。

50 轮拉锯之所以把净价值 $V(a \mid C_t)$ 拉进负数，原文揭示了两条完全不同的失效机制，绝不能混为一谈：
1. **对代码风格挑刺（Nit）：决策价值为零，却照样支付全额修改成本**。人类工程师看到一条无关紧要的格式建议，几秒钟就能划掉忽略——因为它并不改变对“代码是否正确”的判断（决策灵敏度为零，$\operatorname{VoI} = 0$）；可编码 Agent 会把每一条评论都当成待办任务，乖乖改代码、推新 Commit、再触发一轮 CI 与重审，白白烧掉高额 $\operatorname{Cost}(a)$。
2. **对首轮就已存在的存量问题（59%）挤牙膏、不断外溢**：发现真正存在的旧 Bug 并非信息量为零（$\Delta I > 0$），但如果首轮没有按类别一次报清、每轮又拿整个变更或周边老代码重读一遍，审查器就会每一轮只挤出一两条原本早就存在的问题，或者把当前 PR 目标 $Z_{\text{PR}}$ 之外的历史代码也拉进战场。每一轮都要支付全量修改和全量 CI 的固定高成本 $\operatorname{Cost}(a)$，换来的却是少量零碎甚至偏离 $Z_{\text{PR}}$ 的意见，$\Delta I_{\text{反馈}}(a) < \lambda \operatorname{Cost}(a)$，净价值迅速转负。

这就像**房子装修时的巡检验收**：

> 第一遍水电检查，监理如果按房间类别一次列全“卫生间缺防水插座、厨房预留线径不够”，工长集中两天改完就清账了。
>
> 可如果监理第一遍只随口指出一个插座问题，而且规定“每改完一处，就把整套房子从客厅到阳台重新全检一遍”：工长改完卫生间再复检，监理这回注意到第一天就装偏了的踢脚线；工长拆了重装，下一次复检监理又翻出第一天就留下的墙角批灰瑕疵，顺带再要求开关面板再调齐 2 毫米。如此拖到第五十趟，最初那笔核心工程账还没收口，墙皮倒在反复折腾中敲坏了好几块。
>
> *（不过装修验收的比喻只到“多轮固定返工成本压过单次纠偏收益”为止；代码比装修更敏感的一层在于，代码模块之间有隐式耦合，第 N 轮顺手修改一行小样式，也可能直接破坏原本正常的另一个模块，让后续 $\operatorname{Cost}(a)$ 涨得比装修还快。）*

看清公式里的每一项变量对应谁之后，Claude Code 团队同时落地的四道收敛限速规则，每一刀都精准切在净价值方程的对应参数上：
1. **按类报错（Flag the Class of Bug）**：发现同类疏漏时要求一次列出全类位置，不再逐行挤牙膏，把原本分散到几十轮的有效 $\Delta I_{\text{反馈}}$ 尽可能集中收拢到前 1~2 轮；
2. **去重过滤（No Repeats）**：已经讨论过或拒绝过的意见不再重复发出，直接切掉 $\Delta I = 0$ 的无效触发；
3. **只审增量差异（Diff-only Re-review）**：几轮过后剥夺审查器通读周边旧代码的能力，视线锁死最新推送的 Diff，防止目标边界从当前 PR 的 $Z_{\text{PR}}$ 向存量历史债务漂移；
4. **三轮上限（Round Cap）**：往复超过 3 轮即停下，提醒作者退一步重审整体方案是否选错了路。这正是方程二的硬终止判据——当 $V(a \mid C_t) \le 0$ 时，继续在局部修修补补已经亏本，必须交回人类 $H$ 重新定方向。

这套收敛改造落地之后，Claude Code 内部 PR 的指标出现了明显改善（见原文披露的对比数据）：

| 收敛观测指标 | 改造前 | 改造后 | 变化方向 |
| :--- | :---: | :---: | :--- |
| 一轮审查修复即通过比例 | 65% | **78%** | 一次到位率明显提升 |
| 需要 5 轮及以上审查比例 | 8.9% | **1.5%** | 长尾拉锯显著压缩 |
| 单个 PR 平均审查轮次 | 2.08 | **1.32** | 人机等待与算力开销同步下降 |

更进一步，Claude Code 团队总结了一个很符合成本梯度的经验：**如果自动化审查器反复指出同一类常规错误，不要继续追加审查轮次，而要回到源头消解**——写进精简的 `CLAUDE.md`、代码所有者维护的 `REVIEW.md`，或者直接固化为确定性的 Lint 规则。后者等价于把原本每次都要靠动态模型（$M$）花钱抓错的环节，直接转化成确定性程序（$P$）里的零成本常态门禁。

### 三、 急诊分诊台的算账：为什么低风险变更不该让人看？

解决完“机器能不能有效审查”和“审查会不会死循环”，接下来就是整篇文章最反直觉的问题：**为什么 Claude Code 团队允许大量 PR 在没有任何人类同事点击批准的情况下直接合入主干？**

在[《第四篇》](/zhangmuchuan/blog/agent-business/)里，我们证明了“草稿纸”与“手术台”必须分治；再结合[《数学基石篇》](/zhangmuchuan/blog/agent-math-foundations/)的**成本梯度（$\operatorname{Cost}(P) \ll \operatorname{Cost}(M) \ll \operatorname{Cost}(H)$）**和**高危操作挂起定理**，就可以从第一性原理推导出这套分级审批制度为什么成立，而不是在看完案例后贴个标签。

在任何代码团队里，人类工程师的时间和清醒注意力（$\operatorname{Cost}(H)$）是最稀缺、最昂贵的验证资源。Anthropic 自己在文中明言：评价审查是否省下了人力，必须同时算**“审查耗时 + 事故修复耗时”**两笔总账。

这就像大医院的**急诊分诊台**：

> 急诊大厅每天进来一大批患者，其中大多数只是普通感冒、皮肤擦伤或开常规退烧药。如果医院立下一条规矩：“为了医疗安全，全院每张处方都必须由神经外科主任亲自问诊签字”，不出半天，主任的清醒精力就会被几百张常规处方耗尽；等傍晚真正送来需要开颅评估的急危重症时，他手头正压着一堆止咳糖浆单子，很难再保持最敏锐的判断。
>
> *（不过这个比喻到“把稀缺人类注意力留给高危对象”为止。医院里感冒病人不会故意把自己伪装成轻微擦伤来逃避主任检查，但代码世界里的变更作者（或 Agent）可能在改文档的 PR 里顺手改掉一行部署脚本——所以软件分诊还必须把“决定谁进哪一档”的权力拿走。）*

回到信息净价值方程来算两极的账：
- **低风险可逆区（草稿纸）**：文档修订、文案调整、或完全包在 Feature Flag 开关后的增量逻辑，一旦出错，几分钟内关闭开关或一键 `revert` 就能复原。通过极小批变更、开关隔离与快速回滚机制，团队把单次误判的外部恢复代价 $\operatorname{Cost}_{\text{误判}}$ 压到极低。此时，确定的自动化 CI（$P$）加上交叉 AI 审查（$M$）就已经足以支撑正净价值；硬再拉一名工程师 $H$ 逐行细读，付出的 $\operatorname{Cost}(H)$ 远大于残余风险收益，$V < 0$。
- **高危核心区（手术台）**：对于一旦出错就带来资金损失、客户端更新瘫痪或构建供应链污染的变更，潜在惩罚代价 $\operatorname{Cost}_{\text{误判}} \to +\infty$。依据**高危操作挂起定理**，净价值对误判风险的容忍度极低（风险折算项 $\lambda \operatorname{Cost}(a)$ 主导全局），同时机器在法律和经济意义上无法成为责任主体，因此必须强制挂起，交由人类 $H$ 亲自核准担责。

于是，Claude Code 团队落地的风险分级矩阵（Risk-based Approval）与它的三条铁律，也就有了严密的理论推导支撑：

| 风险等级 | 典型代码变更范围 | 人类批准要求 | 背后的工程依据与可逆机制 |
| :--- | :--- | :---: | :--- |
| **低风险（Low）**<br>（可逆草稿区） | 文档、文案、纯内部使用功能、被开关完全隔离的增量改动 | **0 人**（CI、AI 缺陷与安全审查全绿即合） | 影响半径窄，Feature Flag 关闭与快速回退把误判恢复代价压到极低 |
| **中风险（Medium）**<br>（常规业务区） | 常规产品功能变更，以及缓存、自动更新器（Auto-updater）、系统 Prompt 等敏感区域 | **1 人**（仅限可信列表内的作者可自批担责；列表外仍需第二人） | 具备外部影响，需要明确责任人核对产品意图与变更范围 |
| **高风险（High）**<br>（高危手术台） | 最高风险的核心代码，以及团队固定划定必须双人审批的少数核心路径 | **2 人**（必须两名工程师独立核准；另有鉴权、计费、CI/发布工作流、安装器等硬性敏感路径一律禁止免人审批） | 潜在后果高度不可逆，必须由多人独立复核并由真实责任人签字担责 |

支撑这套分级不失控的三条约束，每条也正好对应一条理论边界：
1. **分类权剥离作者（判据/门禁隔离）**：风险等级不是作者自己勾选的，而是由系统内置分类器根据实际改动的 Diff 和敏感路径自动定级，并且还有第二道分类器专门复核“这笔改动即便表面档位低，是否仍需额外加一位审稿人”。这正是为了落实**验证隔离**——绝不能让写代码的当事人（或 Agent）自己挑选要过哪一套门槛。
2. **机器批准不得顶替人类名额，且新提交作废旧批准（快照时效边界）**：AI 审查可以通过低风险合并，但在需要 1 人或 2 人的槽位上，任何机器账号都不能签字占位；更关键的是，一旦 PR 在获批后又推入了 Agent 自动修复的新 Commit，或者有人手动解了一次冲突，此前的人类批准立刻作废重审。这恰好对应我们在本系列此前的分析明确的一条原则——**人类审批依赖的是当时看到的代码快照 $C_t$；一旦变更变成新快照 $C_{t+\Delta}$，原批准依据就过期了，必须在落地前对最新状态重新核验。**
3. **可逆性兜底，并坦诚当前短板**：变更拆小、新功能挂在 Feature Flag 后先给内部员工日常使用、发布分 `latest` 与 `stable` 通道逐步推进。不过原文也坦承了一处**尚未补齐的边界**：团队目前还没有建成“一旦回退率或事故指标抬头，系统自动收紧审批门槛”的熔断器（Circuit Breaker）；工程师普遍要求在把零人工合并推广到更多代码前先补上这层自动负反馈保护。

把大量低风险、可快速回退的常规变更交给机器与可逆开关，人类工程师才真正腾得出精力去盯紧高危手术台和架构主线。这就是“合并量翻倍、回退率反而下降超 40%”的原因。

### 四、 四重对账防线：怎么防止机器审查员自己产生幻觉或漏判？

把这么大比例的常规拦截任务交给 AI 审查器，实际落地一定会碰到下一个问题：模型写代码会有幻觉，拿它做审查，难道不会产生大量误报，把评论区变成新一轮干扰吗？

Claude Code 团队针对模型不可靠性搭建的四重机制，放到我们的理论框架里都能看清各自守住的防线，也能看清它们各自的边界：

1. **多 Agent 并行查找 + 独立验证组投票（扩大召回与信噪比过滤）**：
   先派多个审查 Agent 并行阅读 Diff、全库上下文与 PR 意图去搜寻疑似问题——多路采样能突破单次推理注意力的局部局限，先把真实问题的候选召回率拉起来；但召回拉高必然带进一堆格式洁癖和幻觉误报（按第 2 节的计算，误报流给编码 Agent 会触发负净价值的无效返工）。
   于是团队在输出评论前加了一道**隔离的验证组投票**：由另一组不共享第一轮思路的 Agent 逐条复核疑似缺陷，只有多数验证者认为确属真问题才会留下来，纯误报以及仅涉及格式风格、诊断或清理的无效挑刺直接筛掉，留下的按 `Important`（重要）、`Nit`（非阻塞细节建议）、`Pre-existing`（历史既有问题）分类贴出；与此同时安全审查独立执行，任何未解决的缺陷或安全问题都会阻塞合并。团队在自有 PR 上做过 A/B 测试来验证这套过滤器的效果。
   *（需要清醒交代的边界是：按本系列此前的分析对定理六的推广，只要这批并行 Agent 与验证组共享同样的代码库视野和模型先验盲区 $\hat{Z}$，多模型投票依然会一起漏掉“没写进代码库、只存在于外部业务场景里”的缺失需求——它过滤的是孤立幻觉，替代不了独立判据和人类方向核对。）*

2. **合并队列重跑（Merge Queue：防止检查快照与主干合入基线脱节）**：
   PR A 各自测试通过、PR B 也各自测试通过，合进 `main` 却可能互相冲突报错。本质原因是两份改动验证时依赖的**上游环境基线 $E$ 已经改变**，各自拿过期快照 $C_t$ 跑出的全绿结果不能直接外推到并发合并后的新状态 $C_{t+\Delta}$。合并队列强迫每笔代码在真正落盘前先套上当前最新的 `main`，重跑全套确定性校验 $P$，确保测试验证针对的是“即将落地的真实状态”。

3. **把历史事故封存为每日评测集（用 $H$ 标定、$P$ 锁定的标尺校准 $M$）**：
   这里要精确区分两种不同的沉淀路径：如果团队发现一条非常明确的机械规范，直接写成 Lint 规则或单测断言，那是把问题彻底交给了零方差、低成本的 **$P$ 轴运行时门禁**；而 Anthropic 团队把历史上引发事故或回退的 PR 连同修复补丁搜集起来，请熟悉对应模块的工程师（$H$）逐条确认真 Bug 与位置，封存进一个**只读不可篡改的回归评测集（Eval Set）**，每天跑一遍现有的 AI 审查器。
   它并没有在运行时替代 $M$，而是解决我在[《第六篇》](/zhangmuchuan/blog/agent-memory/)中指出的“日志堆进提示词引发信噪比恶化与版本过时”的问题：把曾经付出代价的 $H$ 轴真实教训，转化为客观可重复的标尺，专门用来检验“调整审查提示词、工具或更换基础模型 $M$ 之后，历史错题拦截率是升了还是降了”，不升反降的改动一律淘汰。

4. **不靠逐行读 Diff 传播团队上下文（基于当前源码的实时切片讲解）**：
   传统代码审查还承担着第二个任务：**让团队成员互相看懂彼此新写的代码，维持对整个代码库的心智地图**。当大部分常规 PR 不再由人逐行读过时，这笔认知会不会断层？
   Claude Code 团队的做法很务实：如今团队里也没有人能把整个代码库背在脑子里。读几十天前的一行行零碎改动既费时又容易读到过期状态；每当工程师要改某个不熟悉的模块时，直接让 Claude 围绕眼前准备动手的那一小块（例如“托管配置是怎么检索生效的？”）基于**当前最新源码**花几分钟生成一份切片讲解，或者直接搭一个小可视化页面辅助理解，再结合大家默认在公开 Slack 频道推进工作的透明度来保持对齐。这在信息论上等于放弃低信噪比的过时增量碎片，按当前真实目标 $Z_{\text{当前模块}}$ 按需合成最新、最紧凑的前馈上下文 $C$。

### 五、 结语：守住人必须签字的边界

回到文章开头的问题：既然 Agent 写代码和抓常规 Bug 都比人快，工程师在代码审查里到底还守什么？

把 Anthropic 的实战经验放到[《数学基石篇》](/zhangmuchuan/blog/agent-math-foundations/)里一对照，答案并不复杂：**代码审查的价值不在替编译器复核语法和常规边界，而是在机器不能拍板、也无法担责的地方给出最终决定。**

在 $(P, M, H)$ 验证坐标系里，人类 $H$ 是真实业务意图的源头，也是唯一能在经济和法律意义上承担后果的主体。Claude Code 团队最终明确留给人类的五项工作，正好一分不少地落在这个位置上：
- **决定该不该做**：方向、品位与范围边界（特别是外部团队发来的变更，先确认这件事本身值不值得做）；
- **紧盯高危核心路径**：计费、自动更新器、安装器与 CI 发布工作流；
- **把关架构模式**：那些一旦合入就会被后续 Agent 和同事反复照着模仿的公共代码结构；
- **核验真实证据**：不凭一句 `LGTM` 放行，而是亲眼看跑了什么命令、输出了什么结果、截图是否符合预期；一旦说不清这套检查会漏掉什么，就发起真实的人工审查；
- **承担最终结果**：团队规范只有一句话——**“You land it, you own it.”（你合入的变更，由你负责到底。）** 哪怕代码是 Agent 用三十秒写出来的，确认合并的人，永远是为真实线上后果签名的人。

当代码生成速度提升十倍时，真正能守住质量的不是让人类熬夜逐行通读本可自动验证的改动，而是把防线摆对位置：把确定的门禁交给零方差工具 $P$，把交叉找茬交给隔离并限速的模型循环 $M$ 并守住合并快照一致，把人类有限的注意力留给工具和独立审查都无法拍板的三件事——**需求方向、高危边界与最终责任**。
