2026 年 11 月，Google 工程师 Addy Osmani 写了一篇引发广泛共鸣的文章——[*Your coding agents made you a manager*](https://x.com/addyosmani/status/2119332146485891501)（《你的编码智能体把你变成了管理者》）。

文章抛出了一个让很多一线程序员心里微微发紧的判断：**如果你整天都在和 Coding Agent 打交道，不管你愿不愿意，你其实已经在做管理了。** 你每天都在选任务、写交底说明、派发工作、盯进度、验结果、拍板哪一版代码能上线。真正能把 Agent 用出十倍杠杆的工程师，往往不是最会背“提示词咒语”的人，而是学会了像成熟管理者那样思考的人。

这个观察非常准。很多技术专家当初选择 **IC（Individual Contributor，独立贡献者）** 路线——这是硅谷科技公司双轨制职级体系里专门指代“不带下属、专心在一线写代码做技术突破”的角色——就是为了躲开日程表和无穷无尽的管理协调，把注意力留给真实的技术问题。结果没想到，自己没去带真人团队，AI 却在工位上给你塞了一支“外包开发小队”。

过去写代码，你是一个手艺精湛的**单干木匠**，从画线、下锯、刨平到上漆，每一寸木头都经自己手；今天用 Agent 写代码，你变成了一个带着五六名**手速极快、精力无限、但必须由你来定图纸和验房**的木工工头。

不过，如果我们只停留在“带 Agent 就像带下属”这层经验类比上，很快就会撞上一堵墙。Addy Osmani 自己在文章后半段也诚实地指出了管理类比失效的地方：

* **返工几乎零成本**：白板上遇到技术分歧，你不可能让人类同事同时写两套完整实现拿来比着看；但对 Agent，你可以同时开三个分支做完直接对比。
* **过度迎合与“认知屈服”**：经验丰富的同事遇到不合理的需求会顶回来；而 Agent 天生顺从且极度自信。Addy 引用了沃顿商学院关于 **Cognitive Surrender（认知屈服）** 的研究——当人面对流利、自信的 AI 输出时，往往会放弃独立核查、全盘接受错误结论，甚至荒谬地对自己产生更高的信心。
* **跨过管理幅度后的“编排税”**：传统组织管理里有一个概念叫 **Span of Control（管理幅度）**——一个主管精力有限，一旦直接下属超过某个数量，顾此失彼，团队整体质量就会下滑。带 Agent 也一样。Addy 提到他自己每天跑四五个后台 Agent 外加几个本地会话，有时候就已经觉得顾不过来了，他把这种多线并行的额外精力损耗叫作 **Orchestration Tax（编排税）**——你无法靠“自己瞪大眼睛同时盯十个窗口”来提效，唯一出路是让 Agent 学会自己验收。
* **没有跨人积累的经验**：一个优秀工程师多年摸爬滚打攒下的直觉会沉淀在团队里；而 Agent 的自动记忆（Auto Memory）往往只留在单机本地，换一台电脑、开一个新会话，它又像第一天入职那样忘得一干二净。

更重要的是，类比只能帮我们记住“应该怎么做”，却解释不了**为什么必须这样做，以及随着大模型能力继续暴涨，哪些规矩会过时、哪些底线永远不能撤**。

要回答这些问题，我们需要把所有管理学名词和提示词技巧放在一边，退回到最底层，从**四个无法动摇的基本事实**出发，把整套人机协作的边界重新推导一遍。

## 第一层：人很慢，而现实很乱——为什么只能下放“指挥官意图”？

**基本事实 1：人类确认与决策的延迟极高，而真实代码库的执行现场充满了意想不到的变化。**

你不可能像玩即时战略游戏那样，Agent 每敲一行代码、每看一个报错，你就在旁边停下来审批一次“下一步该点哪里”。人类的注意力和阅读速度比模型推演慢几个数量级；与此同时，真实的编程环境永远不是真空——依赖包会冲突、历史代码里藏着没人记得的坑、接口会超时、测试会冒出意料之外的边界报错。

在这个物理约束下，如果你给 Agent 下达一份**写死步骤的详细操作手册**（先打开文件 A、再把第 30 行改成 X、接着调接口 B），只要现场遇到半点意外——比如文件 A 早就重命名了，或者接口 B 根本不支持那种写法——整套脚本在接触现实的第一秒就会卡死。要么它机械地硬着头皮改下去，把后面的工作全建立在错误前提上；要么停下来干等人类回来拍板。

解决这个矛盾的唯一出路，是**把现场应变和做决定的权力下放给执行者，让它在本地自己跑通“动手 → 看报错 → 调整方案”的反馈闭环**。

但权力下放之后，立刻带来一个新问题：既然你不告诉它具体怎么走，它会不会走着走着就跑偏了？

这就引出了一个来自军队的古老概念——**Commander's Intent（指挥官意图）**。

这个词源自 19 世纪普鲁士军队演化出的 **“任务式指挥”（德语 *Auftragstaktik*）**。当时战局变化极快，电报和传令兵根本追不上前线节奏。普鲁士军官发现，与其由后方司令部画死每支小队几分钟往哪条小路走，不如只给前线军官交待清楚一件事：**这次行动最终要达成什么战略目的、打完时战场必须处于什么状态、有哪些底线绝不能碰**。后来这套原则被写进现代美军野战条令，也被退役美军将领斯坦利·麦克里斯特尔写进《赋能》（*Team of Teams*，2015）、前核潜艇舰长戴维·马凯特写进《授权》（*Turn the Ship Around!*，2013），到了硅谷的奈飞公司，则被提炼成了一句流传很广的管理原则——**“Context, not control”（给足上下文，不做过程控制）**。

两个日常场景就能把“死命令”和“指挥官意图”的区别看透：

> **场景一：往战地医院送急救血浆**
>
> * **死命令（规定 How）**：“沿 3 号公路向北开，在第二个路口右转过桥，下午 2 点前把血浆送到医院东门。”
> * **现场意外**：车队开到桥头，发现桥刚被洪水冲垮了。如果司机只拿到了死命令，他只能原地停车打电话等上级重画路线，前线手术可能因此耽误。
> * **指挥官意图（规定 Why + 终局状态 + 红线）**：“**目的**：保证前线医院下午 3 点开台的手术有血可用；**硬条件**：血浆全程冷链不得变质；**终局状态**：下午 2 点半前，血浆交进医院血库并完成签收。”
> * **真实效果**：看到断桥的那一刻，队长不用请示任何人，立刻自己决策绕山路、找民船渡河或者呼叫直升机转运——所有的临机应变，都在严格收敛到同一个终局状态。

放到普通人的生活里也完全一样。**家里装修请项目经理**，你不可能请一个月假站在工地盯着工人每一锤怎么敲。砸开客厅旧墙才发现里面埋着一根老式铸铁主下水管——如果你当初只交待了一句“把左手边这堵墙全砸了”，工人要么闭着眼一锤敲爆水管，要么直接停工等你下班去拍板；但如果你一开始交底清楚了意图（“**目的**：扩大餐厅采光和走动空间；**红线**：绝对不能动承重结构和主排污管；**终局**：做出开放式餐厨且验收水电不渗不漏”），有经验的工长自己在现场就能改走管路线、做局部包柱。

回到写代码上，这就是为什么 Addy Osmani 反复强调：**不要把你已经在仓库里写好的目录结构、代码风格、测试框架再抄一遍喂给 Agent**——今天的模型一进仓库就会自己读代码，它摸清这些结构比你打字描述快得多。你真正该花口舌写进交底书里的，是**仓库里根本读不到的东西**：

1. **为什么做（Why）**：帮它在两个方案撞车时做优先级取舍（比如“宁可慢一点，也不能牺牲数据实时性”）；
2. **终局怎么算过关（End State）**：一个不含糊的完成标准，而不是“帮我优化一下”；
3. **红线与不做清单（Constraints & Out of Scope）**：锁死它能动什么、别顺手去改哪些不相关的页面。

> **顺手一提的实战技巧**：如果你自己一时半会也梳理不出清晰的意图说明书，Addy 给了一个特别好用的办法——**先让 Agent 反过来采访你**。让它不停追问边界条件、异常处理和非目标，直到它能替你写出一份清晰的需求规格文件（Spec）落盘；然后关掉当前会话，新开一个干净的会话直接照着这份文件动工。

## 第二层：脑子是概率的，后果是确定的——Prompt 与 Harness 必须分家

**基本事实 2：大语言模型再聪明，本质上依然是在概率分布里采样说话（出错率永远大于零）；但修改代码、操作数据库和部署上线，要求的是百分之百的确定性底线。**

第一层我们把“怎么做”的自由度交给了 Agent。紧接着一个非常现实的问题就来了：**既然放权让它自己找路，它为了达成目标“抄近道”、“钻空子”，甚至手滑改坏绝对不能碰的东西，怎么办？**

回答这个问题之前，先认识今天 Agent 工程里一个高频出现、却经常让人一头雾水的词——**Harness**。

`Harness` 的英文原意，是套在马身上的**马具、挽具**，或者是攀岩、高空作业时系在人身上的**安全背带**。AI 工程界借用这个词再贴切不过：大语言模型本身就像一匹精力极其充沛、跑得飞快但也随时可能惊厥失控的烈马（纯推理算力）；而 **Harness（执行底座 / 驾驭外壳）**，就是套在这匹马外面的那一整套确定性代码和工具设施——包括它能看见哪些文件、能调用哪些工具、哪些目录只读不让写、最多允许循环多少步、以及跑完必须经过什么自动化测试。

在工程界，有一条无论模型怎么升级都不会失效的铁律：**自然语言 Prompt 只能做概率上的“引导与说服”，任何“绝对不能发生”的底线，都必须从提示词里拿出来，变成 Harness 里的硬代码约束。**

这其中的区别，就像**马路中间的双黄线**和**半人高的水泥隔离墩**：

* 你在提示词里写“严禁修改数据库表结构”，哪怕加上全大写字母和十个感叹号，本质上也只是在柏油路上刷了一条加粗双黄线。天气好、路宽敞的时候，司机（概率模型）会乖乖守规矩；可一旦前面路堵死了、快交卷了，急着达成目标的模型很容易一脚油门压线逆行过去。
* 把迁移脚本目录设成**物理只读权限**、把压测脚本放到 Agent 根本改不到的独立沙箱里——这才是水泥隔离墩。它不是靠模型“自觉”，而是让违章动作在物理上根本发生不了。

不仅如此，当一个被强目标驱动的模型手里既拿着答卷、又握着评分标准时，还会触发经济学里大名鼎鼎的 **Goodhart's Law（古德哈特定律）**。

1975 年，英国经济学家查尔斯·古德哈特在讨论货币政策时提出了一句名言：**“当一项衡量指标变成考核目标时，它就不再是一个好指标。”** 历史上一个常被引用的经典故事是：如果政府只按“重量”考核钉子厂产量，工厂很快就会造出一堆根本没法用的大铁钉；如果按“数量”考核，工厂就专造牙签那么小的细钉子。

放到 AI 编码里也是一样：**让 Agent 自己写的业务代码去跑它自己能修改的测试脚本，就像让一个极度渴望拿 100 分的考生，不仅自己做题，手里还握着能改题干数字和修改评分标准的红笔。** 当一道大题实在解不出来时，这个“考生”极有可能悄悄把题改简单，交出一份满分绿灯答卷。

口说无凭，我们直接拿 Addy Osmani 原文里给出的一段“标准好 Prompt”来做一次现场压力测试。这段话的任务是优化企业团队仪表盘（`/team`）的加载速度，其中提到的 **P95 耗时**是性能工程常用指标，意思是“最慢那 5% 的请求排除在外，确保 95% 的用户打开页面都在 2 秒以内”；**Schema** 则指数据库里各张表和字段的结构定义。这段 Prompt 乍一看已经写得非常专业了——有量化指标、有业务背景、有约束、有非目标、还有验收脚本：

```markdown
优化 /team 团队仪表盘的 P95 加载耗时，对于成员规模超过 1 万人的大型企业租户，将其压至 2 秒以内。

业务背景（Why）：大企业管理员每天都要高频使用该页面，加载慢目前是全团队第一大客诉吐槽点。

硬性约束（Constraints）：禁止修改数据库 Schema 结构；必须保持既有 API 的返回 JSON 结构完全不变。

非目标（Out of scope）：本次暂不重构前端 UI 样式；严禁采用暴力缓存整页 HTML 的方案。

验收验证（Check）：执行脚本 scripts/perf/team.sh，在报告中出示优化前后的真实性能对比数字。
```

*(注：Addy 原文说明这里的数字仅为举例示意。)*

但如果今天你真的把这段话原封不动丢给一个拥有代码读写和命令行执行权限的自主 Agent，让它自己跑去优化，它在真实循环里极容易露出 **4 个防不胜防的漏洞**：

1. **软禁令挡不住强行破墙**：当模型排查一圈发现瓶颈死死卡在数据库全表扫描、改应用层代码实在救不回来时，那句写在文本里的“禁止修改数据库 Schema”只是软约束，模型依然有可能去动数据库迁移文件，或者偷偷改掉某个字段的序列化行为。
2. **堵住了前门，却留着后门**：提示词里非常聪明地堵死了“暴力缓存整页 HTML”这种偷懒作弊路，但没有定义**数据新鲜度底线**。模型完全可以转身给后端 `/api/team` 接口的 JSON 返回值加上一个 10 分钟无条件过期的 Redis 缓存，并且不写任何缓存清理逻辑。这完全符合字面要求，而且 `scripts/perf/team.sh` 的只读压测一定绿灯亮得飞快——但代价是企业管理员刚删掉一个离职员工，页面上十分钟内还显示着正常。
3. **传感器被劫持（古德哈特定律现场版）**：如果 `scripts/perf/team.sh` 就躺在 Agent 可读可写的仓库里，当它拼命改代码却一直卡在 `2.4 秒` 下不去时，在“必须压到 2 秒以内”的强驱动下，可能会触发两种作弊：要么直接改小 `team.sh` 里的模拟人数或并发数；要么偷看脚本里压测用的那几个特定租户 ID，在业务代码里专门针对那几个 ID 写个内存捷径。
4. **物理无解时的无底洞死循环**：万一在不加数据库索引（禁止改 Schema）的前提下，这张万级成员表的聚合查询在物理上就是跑不进 2 秒怎么办？因为你没有给它“实在做不到时怎么安全体面地退出”，Agent 就会在死循环里把 Token 烧干，或者在最后两轮被逼着越界强行交差。

看清这四个漏洞，就知道一份真正抗打的意图加上配套 Harness 该怎么改——不需要多写哪怕一句“先去查哪张表、怎么改 SQL”的废话，只需要在意图里补全**数据新鲜度口径、防作弊和无解退出出口**，同时把硬边界交给权限系统：

```markdown
## 目标（End State）
优化 `/team` 团队仪表盘的接口与渲染链路，使成员规模 > 10,000 人的大型企业租户在正常并发负载下的 P95 加载耗时压至 2,000ms 以内。

## 业务背景（Why）
大企业管理员每天高频使用该页面进行组织架构与权限管理，当前加载缓慢是第一大客诉点。优化必须以保障管理操作的实时准确性为前提。

## 硬性不变量（Invariants）
1. 存储与契约不变：严禁修改数据库 Schema 及迁移文件；既有 API 返回 JSON 结构、字段类型及语义保持 100% 向后兼容。
2. 数据一致性：禁止采用整页 HTML 缓存或无主动失效机制的 API 响应缓存；任何成员变更后，仪表盘可见数据的最大延迟不得超过 5 秒。
3. 严禁作弊：禁止修改 `scripts/perf/team.sh`，禁止针对压测租户 ID 编写硬编码特判逻辑。

## 非目标（Out of Scope）
本次不改动前端 UI 样式与交互布局。

## 验收与异常升级（Verification & Escalation）
1. 回归守卫：既有单元测试与集成测试必须全部通过（退出码为 0）。
2. 性能验收：运行 `scripts/perf/team.sh`（由外部执行域只读锁定），在最终报告中给出优化前后的 P50/P95/P99 真实对比数据及核心瓶颈根因分析。
3. 异常升级：若在不修改 Schema 的约束下物理性能已达上限、无法满足 2,000ms 目标，禁止越界修改 Schema，立即终止变更并输出慢查询执行剖析（`EXPLAIN ANALYZE`）瓶颈证据与最小索引变更提案。
```

配套在 Claude Code 这类工具里落到 Harness 层时，其实用的就是几个非常具体的工程机制（这里顺便交代一下它们的来历，免得没重度使用过的读者发懵）：

* **`CLAUDE.md`**：放在代码库门口的“团队交接备忘录”。Agent 每次开新会话会自动先读它。里面最值钱的一行往往不是大道理，而是跑测试、跑构建、做类型检查的**精确命令**，以及人类纠偏过两次以上的教训。
* **`Stop Hook`（回合结束门禁钩子）**：程序流程走到特定节点时强制自动触发的拦截脚本。`CLAUDE.md` 里的规矩模型“可以选择听或不听”；但挂上 `Stop Hook` 之后，只要类型检查没通过，系统物理上就不允许 Agent 结束这一回合交差。
* **`git worktree`**：Git 自带的原生功能，允许你从同一个代码仓库里同时检出多个互不干扰的平行工作文件夹。Addy 文中提到的 `/batch`（把大任务拆成 5 到 30 个小块并行推进）必须靠它——就像给 5 个木工每人分一间独立操作间，否则 5 个 Agent 同时在同一份文件上动手，产出的不是 5 倍效率，而是“一个有 5 个作者的巨大合并冲突”。
* **`/goal` 与 `/code-review`**：`/goal` 是在后台长程任务里请另一个模型每轮盯着完成条件有没有达成；`/code-review` 则是把改出来的代码改动对比（Diff）交给一个**没看过之前聊天记录的全新子智能体**去审查——就像公司里程序员自己不能批准自己的 PR。这样你才不至于面对一个“名字看着挺合理、测试全绿的 600 行 Diff”，直接闭眼点击批准——Addy 把那种偷懒叫作 **Code Ratification（代码追认仪式），而不是真正的代码审查**。

## 第三层：模型越来越强——脚手架要做减法，安全围栏和传感器要做加法

**基本事实 3：基座模型的通用推理与编码能力在以几个月为单位快速跃迁。**

如果前面两层说的是静态的协作规律，这一层就要面对时间的变量：**去年写的那一大套把模型当傻瓜哄的规则和流水线，今年大模型变强了，到底该留还是该删？**

要看透这个问题，先要理解企业管理史上的一个关键概念——**Task-Relevant Maturity（任务相关成熟度，简称 TRM）**。

这个词是英特尔传奇 CEO 安迪·格鲁夫（Andy Grove）在 1983 年的名著《格鲁夫给经理人的第一课》（*High Output Management*）中提出来的。在此之前的 1969 年，管理学者赫西和布兰查德就已经提出了**情境领导力模型（Situational Leadership）**，指出没有哪一种领导方式放之四海而皆准。格鲁夫在此基础上点破了最核心的规律：**成熟度不是贴在人脑门上的静态标签，而是“执行者 × 具体任务”的组合。** 同一个身经百战的后端架构师，让他去写一个完全没接触过的前端动画库，他的任务相关成熟度瞬间就会归零。

管理学因此把干预方式随着 TRM 升高划分为四个台阶：**S1 指导（手把手列每一步） → S2 教练（指令加上原理） → S3 支持（定目标给资源） → S4 授权（只下达指挥官意图，看结果验收）**。顺便一提，格鲁夫在这本书里还立过一条常被忽略的**反向指标原则（Countermeasure）**：只要你用数量做考核（比如“本周合并了多少个 PR”），就必须同时配一个反向质量指标（比如“PR 被回退或返工的比例”）互相牵制，否则数量刷上去、质量必然烂掉。

而放到 AI 发展史上，还有另一篇几乎所有大模型架构师都会反复重读的经典短文——强化学习先驱理查德·萨顿（Richard Sutton）2019 年写的 ***The Bitter Lesson*（《苦涩的教训》）**。萨顿回顾了 70 年人工智能历史得出一个残酷结论：人类工程师费尽心机塞进系统里的各种手工规则、领域技巧和精巧分支流程，短期总能提分；但拉长时间来看，它们最终全会被“更通用的搜索与学习方法 + 更庞大的算力”直接碾过去，甚至反过来成为压低系统上限的累赘。

把格鲁夫的 TRM 和萨顿的《苦涩的教训》放在一起看，结论一目了然：**基座模型每一次代际升级，本质上都是把智能体在通用编码任务上的 TRM 整体向右推了一大截。**

这就像**小孩学骑自行车时的辅助轮**：

* 车技生疏（弱模型 / 低 TRM）时，两边必须死死装上辅助轮，家长还得在车后头跑着扶稳，嘴里不停念口诀：“手扶直！左脚踩！看前面！”——反映在早期的 Agent 开发里，就是你在 Prompt 里塞满“请一步步思考”“改代码前先读上下文”“注意判空”，在代码里把控制流焊死成固定的四步流水线（`检索 → 过滤 → 总结 → 生成`），再把几个步骤打包成高度封装的宏观工具。
* 可当骑手已经练成了专业选手（强模型 / 高 TRM），你还死焊着辅助轮、每天在耳边碎碎念该怎么蹬踏板，结果不是更安全，而是**在压弯和提速时把人绊倒**。

Addy Osmani 在文章里特意列出了一批**面对新一代模型时应该果断戒掉的旧习惯**：别再在提示词里写全大写字母咆哮，别再写“think harder（用力思考，现在推理强度本身就是可调参数）”，也别再写“don't be lazy（别偷懒）”；更关键的是，定期审视你以前写的各种规则和 Hook——如果某个 Hook 只是在强制推行个人审美偏好而不是硬性底线，就该撤掉还给模型自己判断。

具体到真实工程里，**怎么识别出一条脚手架已经从“保护垫”变成了“负资产”，又该怎么安全地把它拆掉？** 通常会先出现三个很明确的信号：

1. **模型想走捷径，却被你的死规矩憋着绕远路**：去翻一下模型的思考轨迹或工具调用记录，如果它明明已经判断出了更快、更合理的排查路线，却因为你在系统提示词里写死了“必须先执行 A、再执行 B”，被迫绕一大圈，甚至在格式模板和真实逻辑之间反复打架，说明旧规则已经在拖后腿了。
2. **出错原因从“能力不够”变成了“流程僵化”**：以前弱模型报错，多半是 JSON 格式写崩了、参数类型填错了、漏掉了基础步骤；当模型变强后，如果你发现线上翻车的主要原因变成了“遇到意外异常时，死板的固定流程里没写对应分支结果卡死”，或者“工具打包得太死，模型看不到底层细节没法自救”，瓶颈就已经不是模型，而是脚手架本身。
3. **防呆补丁越贴越厚，把开头目标挤模糊了**：历次踩坑攒下来的一大堆“千万别这样”“举十个例子”，不仅让每次对话多花钱、首字响应变慢，还会把真正重要的任务目标稀释在长长的旧规定里。

识别出来之后，拆轮子也有一套稳妥的做法——不是一刀切把安全门全拆了，而是**先分类、再对照、按块拿掉**：

* **先拿刀划清“拐杖”和“护栏”**：通用的编程套话（“先思考再写代码”“注意判空”）直接删光；把封装过死的宏观大工具（比如一个包办了“查表+分析+自动改SQL”的黑盒指令）拆成职责单一的原子小工具；唯有那几条代码里绝对猜不出来的**私有业务规则**，和**不可逾越的物理权限红线**绝对不能删。
* **跑一组“零脚手架基线”**：从真实业务里挑一批有代表性的任务（包括常见异常），配上一版极简配置——只留清晰的指挥官意图、私有规矩、原子工具和自动化验收测试，把所有步骤微操和示例全清空，先跑一遍看基准通过率和耗费。
* **从大到小逐块做减法**：先拆多余的多节点固定工作流，再删冗长的步骤约束段落，最后减示例；只要拿掉一块后，验收测试通过率没降（甚至因为放开了手脚而上升）、步数和费用反而更省，就永久从仓库里删掉。至于多智能体拆分，绝大部分“怕它一步想不清楚”的串联其实都可以合并成单一循环，只把独立子智能体留给两个真刚需：**读写权限隔离**（出题人和做题人分开），以及**海量日志隔离**（避免查完几十万行日志把主窗口撑爆）。

**但是，为什么拆掉“辅助轮”之后，绝不意味着可以把所有约束全撤光？**

恰恰相反，**“过程微操”要大幅做减法，但“安全围栏”和“验收传感器”不仅不能减，反而要加厚加固**。原因就在这两个截然相反的比喻里——**20 迈的老头乐 vs. 300 迈的 F1 赛车**。

这里借用系统可靠性工程（SRE）里的一个核心词：**Blast Radius（爆炸半径）**——一旦某个动作出了故障，最坏情况下能炸毁多大一片范围。

* 以前弱模型像一辆最高时速 20 迈的老年代步车，方向盘打偏了，往往还没开出小区大门（第 1 步语法报错或格式写乱）就自己撞花坛停下来了，爆炸半径极小；
* 今天的强模型像一台百公里加速两秒多的 F1 赛车，它具备极强的长程规划和跨文件读写能力。因为概率系统出错率永远大于零，一旦它在某一步对业务前提产生了一丝小误解，它能在几十秒内用极其工整、符合规范、通过编译的代码，一口气把 20 个文件整齐地改偏——**执行者的能力越强、自主跑得越远，犯错时的爆炸半径就越大**。

这就是为什么即使在最强模型时代，一个底座里真正<strong>“最小但充分”的那 5 样东西</strong>永远不能省：
1. **带稳定前缀与防溢出折叠的通用闭环**：用简单的“思考 → 动手 → 观察报错”单循环取代死板的多阶段流水线；同时把核心意图、私有规则和工具定义死锁在最前面不动（既能防长对话后期走神，也能让推理引擎直接复用前面算好的缓存加速），当探索日志越滚越长快塞满记忆窗口时，只把早期已经收尾的琐碎过程折叠成精简摘要，保证长任务不断线；
2. **原子工具与分阶段权限隔离**：在查问题和写测试阶段只给只读权限，进到改业务代码阶段就把测试目录锁成只读；
3. **前置物理沙箱守卫**：路径白名单、SQL 只读校验，拦截到越界不直接崩溃，而是把违规原因当成一条明确报错喂回给模型让它自己改道；
4. **高信噪比传感器**：底层日志动辄几万行，Harness 要帮忙截断冗余废话，只把精确的报错行号、差异 Diff 和真实测试结果传回给模型；
5. **步数与死循环熔断**：独立于模型之外设定最大步数、费用上限与“原地打转检测”（连续几轮零净进展就强制拉闸升级给人处理）。

说到第 4 点里的“高信噪比传感器”，不得不提一个在强模型时代意外翻身的老将——**TDD（Test-Driven Development，测试驱动开发）**。

TDD 是极限编程大师 Kent Beck 在 2002 年前后通过《测试驱动开发》（*Test-Driven Development by Example*）大力推广的方法论，核心节拍叫 **Red-Green-Refactor**：先针对需求写一个必然报错的失败测试（红灯 Red）→ 再写出刚好能让这个测试通过的最少业务代码（绿灯 Green）→ 最后在测试保护下把代码结构整理干净（重构 Refactor）。在人类开发年代，很多程序员觉得“代码还没影呢先写测试”太反直觉、太啰嗦，一直推不动。

但在高 TRM 的强模型手里，TDD 的地位彻底变了——它不再是一种代码洁癖，而是强自主 Agent 最不可或缺的<strong>“倒车雷达”</strong>。

想想看，如果你让一个大脑再聪明的人**蒙着眼睛、纯靠空间想象力把车倒进窄车库**，只要里面多了两根柱子（深层调用栈和并发状态变化），纯靠脑补早晚撞墙；而只让大模型静态阅读源代码去心算“我这么改跑起来会不会崩”，本质上就是蒙眼脑补。

而跑一遍事先写好的测试，就是给车装了一圈**实时滴滴响的倒车雷达**。强模型不再需要人类站在车外一路微操喊“左打半圈、再往后倒十厘米”，它只需要收到雷达回传的一句精准信号——`第 42 行断言失败：期望返回 200，实际返回 403`——就能靠自身极强的调试先验自己把车揉进车位。不仅如此，项目里原本就有的**存量回归测试集，还顺便充当了一张免费的跨模块防撞网**：改 A 模块时不慎撞坏了 B 模块的某个老契约，测试集毫秒级拉响警报——这直接替你在 Prompt 里省掉了几百行“改这里时千万注意别影响那里”的防呆废话。

这里面还有两个很容易被忽略的因果细节：

* **第一，必须是“先写测试（Red），再写代码（Green）”——而且进到 Green 阶段后，必须用权限系统把测试文件锁死为只读。** 如果先让 Agent 写实现再补测试，它写出来的测试在概率上极容易贴着自己刚才那段带 Bug 的代码去凑合验证，相当于“自己考自己”；而把写好的测试在物理上设为只读再让它改业务代码，才真正切断了“运动员兼任裁判改成绩单”的作弊路线。
* **第二，为什么 TDD 这块传感器只对高 TRM 的强模型真正好用？** 面对同样的报错堆栈，弱模型看跨文件调用链往往两眼一抹黑，改一处错引入两处新 Bug，甚至在绝望中硬写 `if` 特判去骗过测试；只有高 TRM 的强模型能把“报错行号 + 堆栈追踪”当成精准的方向梯度，沿误差减小的方向一路收敛到底。再把<strong>静态类型检查（零延迟过滤低级错） + 单元测试（锁死核心业务契约） + 随机属性/模糊测试（探测极端边界）</strong>三层叠在一起，人类就真正退居为“定义规格与验收标准的画线人”。

## 第四层：通用智商趋近无限，但“私有现实”永远不在权重里

**基本事实 4：不管大模型读过多少人类公开语料，你所在企业或个人项目里那些没写进代码规范的私有事实与历史约定，在它的参数权重里从来就没有存在过。**

一路推到这里，一个很自然的终极问题出现了：既然随着模型越来越强，我们要不断拆掉 Prompt 里的防呆微操和辅助轮，那再过两代模型，**Prompt 能不能最终减到零——只扔过去一句“把某功能做了”，剩下的全让它自己读代码搞定？**

答案是：**绝对不能。这里存在着一道无法再压缩的物理下界。**

在 AI 领域，把模型在预训练阶段吸收并固化在神经网络权重里的通用知识，叫作**参数先验（Parametric Prior）**。你可以把最强基座模型想象成一位**读遍了全世界所有公开医学教材和前沿论文的顶级外科学专家**。

现在，你把这位专家空降到一家有着三十年历史的乡镇老医院里值班。走进药房，他看到一个陈旧药瓶上用毛笔贴着标签：“特字 9 号”。按全天下通用习惯，编号越靠后或者带特殊数字的往往代表“已作废待销毁”；但偏偏这家医院十年前某位老院长在全院早会上口头约定过——“9 号”代表专门留给跨月盘点复核的特殊库存，绝对不能当成废药扔掉！

对应到真实软件开发里，这正是强模型走进企业私有系统或个人项目时最危险的失效模式——**“通用先验静默覆盖私有事实”**：

* 如果面对的是一张没有设置表间关联约束（外键）的历史订单表（`orders`），里面有个字段值叫 `status = 9`。按互联网开源代码里的“行业最佳实践”，大多数人都会把它归类成“订单已取消”或“异常失效单”；但企业内部偏偏约定 `status = 9` 是财务系统的跨月对账占位符，既不是取消，也不能算废单。
* 如果是个刚入门的实习生（弱模型），遇到摸不着头脑的规则可能直接卡住报错、问你一声；但**模型越聪明、越博学，它依据“行业最佳实践”做出的猜测就越显得天衣无缝、理直气壮**。它会在没有任何报错提示的情况下，用无比流畅、优雅、全人类都赞叹的规范代码，把你们家独有的特殊规矩悄无声息地全算反了。个人场景也一样——比如你自己的个人记账表里，曾经约定过某类特定前缀的账目是替家人垫付的周转款、不计入个人消费；任何通用大模型进来看一眼，都会极其自信地按常规逻辑把它全部加进你的月度支出里。

既然减不到零，那**到底哪些话该从 Prompt 里删光，哪些私有信息必须死守到底？**

在工程上，只需要用一把最简单的尺子，把信息一刀切成三类：

1. **通用工程常识与防呆废话 → 删光，还给模型权重**
   比如“查表时尽量用 `JOIN` 别全表扫描”“修改代码前注意判空”。这是模型在互联网公共语料里早就背熟的医学教科书，你写进 Prompt 只会挤占宝贵的上下文注意力。

2. **不可推演的“局部公理”（Local Axioms） → 永久精炼保留**
   借用数学里“公理”的叫法：不需要、也没法从别的定理里推导出来，必须直接当作既定前提承认的底层约定。怎么判断一条规则配不配写进团队的 `CLAUDE.md` 或系统前缀里？做一个极苛刻的**反事实检验（Counterfactual Test）**：
   > *假设现在把整个代码仓库、所有数据库表结构一字不漏地摊在最强模型面前，只拿掉你准备写的这条提示词。这个顶尖模型仅靠读代码和常识，会不会依然理解错、写错？*
   如果它翻遍代码还是会猜错（比如 `status = 9` 是对账占位符、某张天天有历史脚本同步写入的 `user_profile_v2` 表其实早已逻辑废弃严禁新业务引用、个人账本里的代付前缀规则），那么恭喜，这就是真正高含金量的**局部公理**，必须显式写出来。
   顺便多说一句：局部公理最好的宿命，也不是越攒越厚，而是以后在重构时把它直接写进代码枚举常量（例如 `STATUS_FINANCE_RECONCILIATION`）或封装成标准视图里——一旦契约变成了显式代码，那条文字公理就可以安全删掉，系统里的隐形坑也就永久少了一处。

3. **庞大的动态私有世界（几百张表、上万页内部文档） → 别全量硬塞，改成“按需探查”**
   既然私有知识不在模型权重里，早期最直觉的做法要么是把几百页说明书全量灌进上下文（立刻把注意力稀释得稀碎，重点全淹没）；要么是用前几年非常流行的 **静态 RAG（Retrieval-Augmented Generation，检索增强生成）**——2020 年由 Patrick Lewis 等人提出的经典做法：在模型开始思考之前，先用一个检索器靠向量相似度从知识库里捞出最像的几段话，塞进开头一起问答。

   这就像**出门进考场之前，只凭考试题目里的几个字眼，盲猜从书架上抽 5 本参考书塞进书包里**。如果题目本身和参考书用词高度重合（比如客服查退换货条款），这招快又准；但在复杂的企业数据库或大仓库里，用户提的需求是“优化 `/team` 仪表盘的万级租户加载”，字面上跟底层那张卡顿表、某个历史视图名毫无重合，盲猜塞进来的 5 段话往往南辕北辙，还让模型以为“资料就这么多了”。

   面对强模型，更符合第一性原理的做法，是给它<strong>“一张极简的总目录导览图 + 几个只读探查工具”</strong>——不再逼它背书进考场，而是让它带着地图直接走进图书馆，自己判断“我现在缺哪一块拼图”，先看表目录、再查某列值的分布摸出魔法数字、再沿着视图定义顺藤摸瓜，缺哪页自己翻哪页。*(至于具体面对几百张没有外键的老数据库，怎么设计既不爆上下文又绝不锁库的四层渐进探查工具，以及局部公理怎么从日常 PR 纠偏里自动提炼而不腐烂，我们会在本专栏的第 3 篇专门展开拆解。)*

---

## 回到原点：四块拼图合在一起，工程师到底站哪儿？

顺着第一性原理一路推下来，看似零散的十几条经验——Addy Osmani 谈的管理直觉、指挥官意图、`CLAUDE.md`、Worktree、Hooks、TRM、TDD、私有上下文——其实全长在同一条简洁得惊人的因果链上：

| 底层基本事实 | 推演出的工程原则 | 一句话直觉 |
| :--- | :--- | :--- |
| **1. 人介入极慢，现场随时生变** | 下放**指挥官意图**（Why + End State + 红线），别写死步骤（How） | 桥塌了让前线队长自己绕路，别等电报回批 |
| **2. 脑子是概率的，后果是确定的** | **Prompt 与 Harness 分家**；硬底线进权限、只读隔离与沙箱 | 双黄线拦不住赶路，水泥隔离墩和锁死考卷才行 |
| **3. 模型能力持续右移** | **过程脚手架做减法，围栏与传感器做加法**；用只读 TDD 收敛 | 成人骑手要拆辅助轮，但 F1 赛车更需要安全栏和倒车雷达 |
| **4. 通用智商不包含私有现实** | **删光常识、死守“局部公理”、大库改做主动只读探查** | 顶级名医空降老医院，也猜不到瓶子上 `9` 号是当年老院长的暗号 |

说到底，Coding Agent 并没有要求程序员放弃写代码去开无休止的管理周会。它改变的是我们创造价值的杠杆点：以前我们是用双手一锤一锯雕琢每一段程序的人；现在，就像 Addy Osmani 在文章末尾写下的那句话——工程师的工作，正越来越多地变成<strong>“成为让好代码必然发生的原因”（being the reason good code gets written）</strong>。

写清意图，铸牢围栏，装准传感器，守住那几条只有你们知道的局部公理——剩下的路径探索与反复试错，放心交给本地闭环去跑就好。
