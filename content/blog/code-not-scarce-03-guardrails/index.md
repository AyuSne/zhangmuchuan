在[第二篇](/zhangmuchuan/blog/code-not-scarce-02-discovery/)里，我们从产品探索和交付的差异推导出一个明确结论：在 `Build to Learn`（为了学习而构建原型）的阶段，产品经理用自然语言配合原型工具几天做出一个带数据的软件去试探客户，性价比极高；但一旦项目通过验证、正式进入 `Build to Earn`（交付商业级生产软件）的阶段，就必须面对成百上千个边缘业务规则，以及系统稳定性、数据安全、权限隔离和容错恢复等严格的工程要求。

正是在这个交界处，Marty Cagan 指出了当前 AI 开发最核心的一个技术瓶颈：**“日常自然语言作为工程规格语言，本身存在天生的局限性。”**

今天很多团队已经吃过这个亏：刚开始觉得让产品经理或初级研发直接用大白话跟 Coding Agent（如 Claude Code、Cursor）聊天就能快速开发，前三天确实飞快；但两周之后，代码库里的隐藏 Bug 越积越多，改好一个接口莫名其妙搞挂了另一个模块，测试看起来全绿但真实业务场景一跑就出错，最后资深工程师花在清理和重构 AI 烂代码上的时间，比自己重写一遍还要多。

为什么会出现这种情况？**问题不在模型不够聪明，而在于“商业级软件开发需要严密的确定性约束，而直接用大白话和 Agent 对话却跳过了一整套把模糊意图变成可靠工程的中间机制”。**

这一篇，我们就从第一性原理拆解：**为什么直接用自然语言指挥 AI 写生产代码一定会出问题？专业工程团队该怎么用工程护栏（Guardrails）管住 Coding Agent？以及在这个新前提下，产品经理和研发工程师每天的日常协作到底该怎么重构？**

---

## 一、 从零推导：直接用大白话让 AI 写生产代码，为什么一定会把系统搞乱？

我们先不谈什么软件工程教条，直接拆解一下：当一个开发任务交到人类资深工程师手里，和交到 Coding Agent 手里，中间到底差了哪四道关？

### 1. 日常语言天生喜欢“省略前提”，而代码不能有任何含糊
产品经理说：“用户点确认下单后，如果库存不足就提示下单失败。”
这句话在日常交流里完全听得懂，但写成运行在服务器上的生产代码时，立刻会冒出十几个必须明确的问题：如果两个用户在同一毫秒抢最后一件库存怎么加锁？库存扣减成功但支付接口超时怎么回滚？促销赠品库存不足时主商品还让不让买？这个提示文案要记进审计日志吗？

人类资深工程师看到这句话时，会本能地停下来找你追问，或者依据公司几年的老代码习惯自动补齐；但 AI Agent 不会主动觉得你没想清楚，为了尽快把任务做完，它会顺着概率最高的方式**自己替你把空白假设全部填满**——而且填错了表面上也完全能编译通过。

### 2. 上下文窗口有限，跨模块修改很容易顾此失彼
商业软件不是单个脚本文件，往往包含成百上千个相互关联的文件。如果一次让 Agent 接一个范围很大的任务（比如“把整个账单计费流程重做一遍”），随着对话轮次拉长、读过的文件越来越多，模型很容易忘掉最前面约束过的条件，甚至为了图省事，直接在一个地方写死一段绕过原有安全校验的逻辑，破坏掉其他模块的正常运转。

### 3. AI 为了“尽快交差”，天然倾向于写高耦合代码和“自欺欺人”的测试
如果你让 Agent 写完业务代码之后再补测试，或者不限制它的测试写法，一个极其隐蔽的陷阱就会发生：**它会顺着自己刚才写的实现逻辑去写单元测试，甚至把内部模块全都 Mock（模拟）掉。**
结果就是：每个模块的单元测试看起来全部通过，但模块与模块之间真实传参的字段名早就对不上了；或者业务代码里漏掉了一个关键条件，AI 写的测试刚好也跟着漏掉了这个条件，导致测试体系形同虚设。

### 4. 修 Bug 时靠盲猜乱改，越修越碎
遇到线上报错或测试失败时，人类程序员习惯先看报错堆栈、确认稳定复现路径、排查数据状态；而没有被约束的 AI Agent 往往看一眼报错信息，就直接大段改写代码去尝试碰运气，改一次没过再换一种写法，顺手把本来没坏的逻辑也改乱了。

**推导出核心结论：**
想要让 Coding Agent 在生产级代码库里稳定输出，绝不能指望“把提示词写得更礼貌、更详细一点”。唯一的出路，是**把资深工程师几十年沉淀下来的需求澄清、任务拆分、架构隔离、测试边界和代码审查纪律，变成 Agent 无法跳过的硬性流程护栏。**

## 二、 拆解一线解法：Matt Pocock 的 `skills` 库是如何用工程纪律管住 Agent 的？

在 GitHub 上，知名 TypeScript 教育者与工程师 Matt Pocock 开源了一套专门面向真实工程开发的 `skills` 仓库（包含 27 个正式 Skill 和 6 个实验性 Skill，MIT 协议开源）。仔细读完所有 `SKILL.md` 的原始指令就会发现：**这套库几乎一句都没教 AI “怎么用某种高级语法写代码”，它全部的心思都花在“用严密的工程流程卡死上面那四个漏洞”上。**

哪怕你平时不用这套仓库，把它的设计按研发阶段拆开，也是一份极具参考价值的 AI 工程护栏标准：

### 第一道防线：写代码前强制消除业务和设计歧义（`grilling`、`domain-modeling`、`to-spec`）
* **把需求追问变成一棵有依赖关系的决策树（`grilling`）：**
  普通提示词让 AI “有不清楚的先问我”，AI 要么一次甩出 20 个琐碎问题把人问烦，要么问出一些“必须先确定 A 才能回答 B”的顺序混乱问题。`grilling` 规定：AI 必须把所有待定决策组织成一棵 **Design Tree（决策树）**，每一轮只把前置条件已经确定、当前正卡在边界上的问题（Frontier）拿出来问人，并且每个问题都要附上推荐方案方便人类拍板。更关键的一条职责切分是：**代码库里能查到的客观事实，AI 自己去读代码查证，绝不允许拿来问人；所有产品与设计取舍的决定，AI 绝不允许擅自猜，必须交给人类确认。**
* **实时对齐业务术语，拒绝无效文档（`domain-modeling`）：**
  同一个词在不同业务部门往往意思完全不同。该规范要求 Agent 在讨论需求的过程中实时抓取术语歧义、主动构造极端边界案例去测试业务规则的漏洞，交叉核对代码现状后立即更新团队共享的术语表 `GLOSSARY.md`。而对于工程里的 ADR（架构决策记录），它明确禁止每做个小决定都写一篇长文档——只有同时满足**“难以逆转、未来接手的人看不懂为什么这么选、存在真实技术取舍”**这三个严苛条件时，才需要记录 ADR。
* **动工前必须锁定测试边界（`to-spec`）：**
  生成正式开发规格时，严禁 AI 再重复把用户拉回来重新访谈一遍，而是直接整合已有讨论和代码现状；但它卡死了一道必须人类点头的门——**动工前必须就 Testing Seams（测试边界，即到底从系统的哪个对外接口验证行为对不对）与人达成一致。**

### 第二道防线：把大任务拆成互相隔离的垂直切片（`to-tickets`、`implement-spec`）
* **拒绝按技术层级横切任务，强制垂直切片（`to-tickets`）：**
  传统外包或粗糙的拆分，经常把任务拆成“1. 建数据库表；2. 写后端接口；3. 画前端页面”。这种拆法在 AI 时代极其危险——前两步做完时根本无法验证业务功能到底能不能跑通，而且一步卡住全线阻塞。
  `to-tickets` 强制使用 **Tracer Bullet（端到端垂直切片）** 拆法：每一个任务卡片都必须尽可能包含完整打通的数据与交互路径，能独立交付一项**可被直接验证的系统行为**；每个任务必须小到**能在一个干净的独立上下文窗口内彻底做完**，避免对话太长导致模型失忆；并且必须明确标出任务之间的依赖关系。拆完后，必须先交给人审核粒度和依赖关系，人点头了才准正式进入执行队列。
* **按依赖图并行，并用工作区严格隔离（`implement-spec`）：**
  在实际执行整份规格时，协调系统不是把任务当线性列表一条条跑，而是看成一张 **依赖图（Dependency Graph / DAG）**。没有任何前置依赖的任务才会并发放出，且每一个任务都会分配给一个**全新干净上下文的子 Agent**，并在完全独立的 Git `worktree` 和代码分支里干活，互不踩踏文件。任务做完测试通过后，由专门负责合并的 Agent 汇入集成分支，再根据依赖关系解锁下一批下游任务。

### 第三道防线：用架构边界、TDD 与双维度审查兜住底线（`codebase-design`、`tdd`、`diagnosing-bugs`、`code-review`）
* **先想清楚模块接口，甚至用硬工具锁死架构边界（`codebase-design`、`setup-ts-deep-modules`）：**
  在 AI 时代，“把代码写出来”变容易了，但“把代码拆得结构干净”依然很难。Matt Pocock 强调 **Deep Modules（深模块）** 设计——用尽量窄、尽量简洁的对外接口，把复杂的内部逻辑严严实实藏在模块里面。他还给了一个极好用的检验标准叫 **Deletion Test（删除测试）**：如果删掉一个模块后，原本被它收拢的大量复杂判断瞬间散落回所有调用它的业务代码里，说明这个模块确实创造了架构价值；反之则可能是过度封装的废模块。
  对于关键模块接口，`DESIGN-IT-TWICE.md` 还要求至少派出三个子 Agent 从完全不同的约束视角各自设计一版方案，最后再由人对比择优。更进一步，在实验性的 `setup-ts-deep-modules` 里，他直接引入了 `dependency-cruiser` 静态依赖检查工具，用硬规则禁止外部文件绕过公共入口偷偷引用模块内部文件，而且必须跑一遍“通过—故意写错触发失败—改回通过”的测试序列，证明这条门禁规则本身真的有效。
* **死守公共接口的 TDD 约束（`tdd`）：**
  写业务代码之前，必须先针对刚才约定好的 **Seam（对外公共接口）** 写出失败的测试，再去写让测试通过的最小实现。而且他明确规定：**不鼓励 Mock 自己系统内部的模块**，只允许在调用第三方外部 API、系统时间、随机数等真正的系统边界处使用 Mock——确保测试测的是模块之间真实拼起来的行为，而不是自说自话的假象。
  *(这里有一个非常内行的流程微调值得注意：经典教科书 TDD 要求在每次“红—绿”小循环里紧接着做 Refactor（重构）；但 Matt Pocock 在这套 Skill 源码里特意把重构环节挪到了所有功能写完后的 **Code Review 阶段**，避免 AI 在每写几行代码时就频繁重构、偏离主线。)*
* **先证明 Bug 存在，再准猜原因（`diagnosing-bugs`）：**
  为防止 AI 瞎改代码，这套六阶段排错流程定了一条铁律：**在写出并实际跑通一条能够稳定、快速捕获当前 Bug 的测试命令之前，绝对不允许进入原因猜测和修改阶段。** 确认复现之后，必须先列出 3 到 5 个可被验证或证伪的假设，再去定向加日志排查，最后修好 Bug 留下永久回归测试并清理临时日志。
* **把“代码写得干不干净”和“需求到底做没做对”彻底拆开审查（`code-review`）：**
  这是防止被 AI“表面光鲜的代码”骗过去的关键一步。`code-review` 会同时派出两个互相独立的子 Agent：一个专门拿编程规范和 Martin Fowler 的代码坏味道清单（如重复代码、Feature Envy、Shotgun Surgery、过度抽象）去挑代码的毛病；另一个则完全不管代码漂不漂亮，死死对照最初的业务 Spec 检查有没有漏掉边界需求。**规则明令禁止把这两份报告合并成一个含糊的综合评价或分数**——这样就能一眼看穿“代码极优雅但业务规则写错了”或者“功能勉强跑通但代码已经是屎山”的情况。
* **复盘时优先加自动化护栏，而不是继续堆提示词（`retro`）：**
  每次开发遇到 AI 犯错，复盘时第一反应不是往规则文件里再加五句话叮嘱它下次注意，而是优先思考：**能不能通过加一条 Linter 规则、类型约束或自动化测试脚本，让这类错误在机器层面上就根本提交不上去？**

## 三、 重构产品经理与研发工程师的日常配合：从“丢一份 PRD”，到共同维护一套“可执行的产品上下文”

搞清楚了护栏怎么搭，接下来就必须回答产研日常配合中最核心的问题：**以前产品经理写一份 PRD 丢给研发开评审会，研发排期做完交测试验收；现在有了 AI 帮忙，PM 和工程师每天到底怎么配合？谁拍板什么？**

如果只是变成“PM 用 AI 生成一份 30 页更长的 PRD 丢给研发，研发再贴进 Cursor 里生成代码”，那完全没有解决传统协作的三个老毛病：
1. **信息传递失真**：一线客户知道 100 个业务细节，PM 调研听懂 60 个，写进 PRD 剩 30 个，研发读完理解成 20 个，经过多轮二手压缩，最后做出来的东西经常跑偏；
2. **理解偏差暴露太晚**：业务隐含的例外条件、技术决策对用户交互的影响，往往要等代码全写完联调验收时才爆发；
3. **跨职能之间只靠开会和口头打补丁对齐**，过几个月换人接手，谁也不知道当初为什么要这么设计。

### 1. 看一个极具体的例子：工厂的“紧急订单插单”功能
为了把旧配合与新配合的区别讲透，我们拿前面提到过的真实工厂场景做一个直接对比。

* **传统协作模式是怎么翻车的：**
  PM 在 PRD 里写：“增加订单优先级设置，支持生产主管把紧急订单排到生产队列最前面。”
  研发工程师拿到文档后，顺理成章地在订单表里加了一个 `priority` 优先级字段，改了列表排序逻辑，几天后顺利交付上线。代码逻辑没毛病，界面点击也流畅。
  但送到真实工厂一用就出大事：在车间里，“紧急插单”根本不是改个排序数字这么简单——它意味着原本分配给其他订单的原材料要被临时挪用，另外三个正常订单会因此延期违约（需要计算影响范围和客户赔付风险），库存不足或机台冲突时根本不该允许硬插，而且每次强行插单都必须记录有权限主管的审批审计。结果就是：**技术上“完全按 PRD 做对了”，业务上“彻底没法用”。**

* **AI 时代建议的新协作模式：共同维护一套结构化、可验证的共享产品上下文**
  在新的配合方式下，PM 和研发不再通过“单向交接一份静态大长文档”配合，而是共同在代码/项目仓库里维护一套按需加载、随时随地跟着版本走的共享知识体系（类似于 Matt Pocock 的文档组织和 Saboo 推崇的仓库沉淀）：

  ```text
  product/
  ├── vision.md                     # 产品核心目标与不做什么的边界
  ├── domain/
  │   ├── glossary.md               # 业务术语表（由 PM 与研发共同校准）
  │   ├── business-rules.md         # 真实业务规则与例外情况（L3/L4 调研沉淀）
  │   └── workflows.md              # 关键业务流转状态
  ├── specs/
  │   └── urgent-order.md           # 具体需求规格与测试边界（Seam）
  ├── decisions/
  │   └── ADR-001.md                # 关键技术与业务取舍决策记录
  └── validation/
      └── acceptance-cases.md       # 可直接转化为自动化测试的验收场景
  ```

  回到“紧急插单”这个需求，协作步骤变成这样：
  1. **PM 跑一线拿下真实规则，写入共享业务事实：** PM 到车间和排产员聊完后，把“插单必须先算产能冲突与受影响订单清单、库存不够或无权限时必须拦截、放行后留存审计记录”这些真实规则和证据补进 `business-rules.md`。
  2. **PM、研发与 Agent 三方共同澄清盲区：** 不再开“PM 照着屏幕念 PRD”的沉闷评审会，而是先让 Agent 读取业务事实和现有代码库，由它运行类似 `grilling` 的逻辑主动挑出还没想清楚的冲突点——比如“插单审批时如果原订单已经开始领料怎么处理？”工程师则直接指出技术边界和事务一致性风险，PM 当场拍板业务规则。
  3. **把口头规则写成机器可检查的验收契约：** 双方不再满足于含糊的功能描述，而是直接协同 Agent 产出类似下面的可执行业务验收场景（比如 Gherkin 语法的测试契约）：
     ```gherkin
     Feature: 紧急订单插单
       Scenario: 无权限或产能冲突时的操作拦截
         Given 当前生产计划中已存在未完成订单
         And 当前操作用户没有插单审批权限
         When 用户尝试确认将紧急订单插单至队列首位
         Then 系统必须拒绝该操作
         And 原有生产计划排序与物料分配不能发生任何改变
         And 系统记录一条被拒绝操作的审计日志
     ```
  4. **职责和决策权按“风险与责任”切分，而不是按“AI 能不能做”切分：**
     * **PM 拍板：** 这是不是工厂真实需要的业务规则？哪些例外情况允许放行？上线后真实排产效率有没有提升？
     * **研发工程师拍板：** 后端怎么保证权限校验绝对绕不过去？多用户并发插单时的数据库事务锁和回滚怎么保证一致性？整体架构稳不稳？
     * **Coding Agent 执行：** 在上述双方共同锁定的规则与架构护栏内，由 Agent 去完成垂直切片拆解、代码编写、对应自动化测试生成以及初轮审查。

  **而对于高风险或不可逆的操作**（如修改核心数据库表结构、资金与权限控制逻辑、批量删除迁移老数据），永远设置明确的人工审批卡口，绝不允许 Agent 自行越权合并上线。

### 2. 同样重要的工程清醒：什么时候根本不该动用 Agent？
当团队配齐了强大的 Coding Agent 之后，很容易掉进另一种低效陷阱——**拿大炮打蚊子，不管三七二十一全交给 Agent 去跑。**

Saboo 在《The Only Skills that Matter》里特意把 **“知道什么时候不该用 Agent”** 列为五大核心能力之一。原因很实在：启动一个多步骤的 Coding Agent，需要加载上下文文件、跑几轮规划和检索、等待工具调用、最后人再去评审 Diff 和测试——这套启动与核对的固定成本并不低。

所以日常工程里非常讲究按任务复杂度匹配工具：
* 遇到跨模块、需要探索技术方案的复杂开发，或者需要端到端验证的原型，出动完整的 **Coding Agent + 工程护栏**；
* 如果只是改一下配置文件格式、批量重命名几个变量、或者把一段 JSON 转换成表格，直接交给**轻量级高速模型**一秒搞定；
* 如果是一个你已经一眼看穿原因的一行代码小 Bug，**自己敲键盘十秒钟改掉提交**，远比你花五分钟组织语言写上下文让 Agent 去领悟并验证快得多。

## 四、 前沿实验与现实边界：PM 自己合并 PR、凌晨两点接故障报警，到底什么团队能这么玩？

把工程护栏与产研新分工推到最前沿，我们在第一篇里提到过 Reforge 所观察到的 Laurel 团队做法。放在工程协同的视角下仔细解剖它，会更有启发：

在 Laurel，PM 不只是写可运行的原型，他们甚至会在完善好的代码库里直接借助 Agent 开发和改动产品功能（从最早的前端界面，随着代码库被清理重构得越来越清晰，现在已经延伸到后端功能）。但这绝不意味着没有研发管着乱来——他们的完整流程其实设计得非常精密：
1. **自动化护栏前置拦错**：代码库里有极完善的自动化测试和 Agent 辅助预审，PM 提交 PR（Pull Request）前，绝大多数低级语法错误和基础规范问题已经被机器拦下来了。
2. **研发退居关键把关点**：工程师不再整天自己审查一大堆低质量的代码碎片，而是在最关键的最终 PR 节点做严谨的架构与风险评审，给出修改意见，再由 Agent 把研发的意见改好。
3. **最反直觉的一步——PM 自己点击 Merge（合并上线）**：Laurel 特意不让工程师代点合并，就是为了强迫做功能的人对整个上线过程负责到底，亲眼看清楚代码库里真正容易踩雷的地方在哪。
4. **最硬核的制度配套——凌晨两点 On-call 轮值**：只要是通过这种方式自己构建并合入上线的功能，不管是 PM 还是设计师，全部进入公司线上故障报警轮值表。半夜两点线上系统崩了，报警电话直接叫醒当初点 Merge 的那位 PM。

而在这个架构背后，Laurel 的研发工程师到底在干嘛？JZ 说得很明白：**工程师并没有被边缘化，而是全面转向了做基建、提升系统可靠性、补全自动化测试体系，以及专门针对 Agent 开发的习惯去清理和重构代码库（让代码结构变得模块清晰、文档可读、报错明确）。**

但站在第一性原理上，我们必须极其清醒地界定：**Laurel 的模式能跑通，是有严格前提条件的，绝不是所有公司明天就能照搬的万能公式。**

* **什么团队具备条件尝试让非纯研发人员直接向产品提 PR？**
  必须是代码库历史包袱比较轻（或者愿意投入重兵把基础设施和隔离护栏搭得极其扎实）、回滚机制瞬间生效、单一功能的失误不至于引发灾难性资金或合规事故（或者只先在低风险页面和内部工具里放开），且产品和设计人员本身具备基本的工程边界常识。
* **什么团队绝对不能盲目模仿，必须守住“研发把持生产代码合并权”的底线？**
  在银行核心清算、医疗诊断系统、大型制造业核心排产软件、或者历史耦合极深的大型传统企业架构里，哪怕一个小改动漏掉了一处分布式事务锁或合规审计字段，后果都可能是灾难性的。在这类环境里，**最稳妥、杠杆最高的做法依然是：**
  1. 严格执行第二篇的边界——PM 用 AI 做可运行原型和清晰验证（**Build to Learn**）；
  2. 按照本章第三节的方式，PM 和研发共同维护共享的产品上下文与可执行验收契约（**Shared Spec & Acceptance Cases**）；
  3. 生产级代码的架构设计、测试护栏与最终合并权（**Build to Earn**），依然牢牢握在专业工程师和严格的 CI/CD 门禁手里。

同时也别忘了 Anand 反复敲过的警钟：**在任何规模的团队里，并发的上限永远受制于人类的验证和掌控能力。** 即使有了 DAG 任务图和自动化测试，一旦放任团队同时跑几十个没人盯盘的 Agent，最终必然会陷入“没人说得清项目整体状态到底卡在哪”的失控混乱。

## 本篇小结与下篇预告

如果把第三篇关于工程落地的推导浓缩成三条核心经验，那就是：

1. **大白话直接驱动生产代码之所以会失控，是因为自然语言天生省略边界条件，而商业级代码库容不得模糊猜测。** 解决之道不是祈祷下一代模型自动读心，而是用工程流程管住它——动手前靠决策树和术语表澄清歧义，拆任务时靠垂直切片和工作区隔离避免互相污染，动工与验收时靠面向公共接口的 TDD、深模块边界和双维度独立审查兜底。
2. **产品与研发的新协作方式，不是“传更长的文档”，而是共同维护一套版本化、可执行的产品上下文**（业务规则、决策记录、Gherkin 验收场景），并按风险、可逆性和责任归属重新划定拍板权。
3. **研发工程师并没有被替代，而是从日常重复页面编码中抽身，成为决定整个团队与 AI 生产效率上限的系统架构师和工程护栏建设者。**

走到这一步，我们已经理顺了底层变局（第一篇）、探索与可验证性设计（第二篇）、以及开发护栏与产研配合（第三篇）。但真正在公司和个人工作里跑起来几个月后，所有人都会撞上最后一个极其现实的难题：

**无论是共享产品 Context、研发规则文件 `CLAUDE.md`，还是 PM 用来审需求、总结访谈的自动化工作流，刚开始用时惊艳无比，但用久了之后，规则文件越补越长、新旧规矩互相打架、多 Agent 协作时任务看板和实际进度对不上——整个 AI 系统突然开始越用越笨、越来越乱，这该怎么办？**

这就是下一篇，也是整个系列的收官篇**[《上下文工程与 Agent 系统长期运营篇》](/zhangmuchuan/blog/code-not-scarce-04-operations/)**要彻底讲透的内容：如何把零散的个人经验，真正搭建成一套能自我校验、持续进化、不会随时间腐烂的个人与团队 AI 工作系统。
