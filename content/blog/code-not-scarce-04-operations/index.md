前三篇我们分别推演了[分工重塑（第一篇）](/zhangmuchuan/blog/code-not-scarce-01-foundations/)、[探索原型与可验证性设计（第二篇）](/zhangmuchuan/blog/code-not-scarce-02-discovery/)，以及[生产级开发的工程护栏与产研配合（第三篇）](/zhangmuchuan/blog/code-not-scarce-03-guardrails/)。

但只要你在真实工作里把这套方法连续跑上两三个月，几乎一定会撞上最后一道、也是最让人头疼的坎：

**刚搭好规则、用上 Agent 的头两周，产出非常惊艳；但用了一个多月之后，你发现规则文件越补越长、新旧规矩开始互相打架、几个 Agent 并行干活时任务进度和代码实际情况对不上——AI 突然开始变迟钝、漏掉原本能注意到的细节，甚至越改越乱。**

为什么会这样？因为**写一条好用的 Prompt 解决的只是“这一分钟的一次性任务”，而把 AI 长期用进业务研发流，本质上是在维护一套持续演进的软件与知识系统。**

这一篇，我们就从大模型的基础运行机制出发，一步步推导出：**怎么把个人与团队脑子里的业务认知沉淀成规范的 Context（上下文）资产？怎么防止规则文件越积越乱、越用越笨？什么时候该用单 Agent 循环，什么时候才该上多 Agent 任务板？以及在整套新方法论背后，我们必须保持清醒的几条现实边界。**

## 一、 从零推导 Context 工程：为什么同一个大模型，不同人用出十倍差距？

先把各种时髦说法放一边，从大模型的两个最基本的运行事实出发：

1. **所有人都接入了同一批顶级模型底座**（Claude、GPT、Gemini 等），API 一接就能用，底层推理能力几乎没有秘密；
2. **大模型在每次开启新会话时，默认都是“彻底失忆的”**——它既不知道你们公司的历史技术栈、昨天刚敲定的业务决策，也不知道你们的客户到底在乎什么、过去试过哪些失败方案。

因此，如果两个人同时对着同一个模型输入一句：“帮我做一个处理客户工单并支持升级流转的客服 Agent”。第一个人只写了这一句话，模型就只能按互联网公开资料的平均值，吐出一个客套话连篇、根本没法在真实业务里上线的通用机器人；而第二个人在启动会话前，已经把**真实客户投诉例子、5 星好评案例、明确要求转人工的退款红线、公司内部接口约束以及什么才算“真正解决”的定义**一并交给了模型，模型第一次跑出来的结果就能直接切中要害。

Shubham Saboo 在总结上百个 Agent 项目实战后，把这种决定产出上限的差异归纳为五个具体维度的 **Context（上下文）**——它们不是空泛的背景介绍，全都是可以直接指导模型做判断的硬信息：

* **User Context（用户真实情况）**：不要写抽象的用户画像，而是写具体行为细节。比如：“我们的使用者是想快速验证想法的开发者，拿到项目 10 分钟内跑不起来就会直接关掉网页放弃，他们不会读长篇大论的说明文档。”
* **Domain Context（领域与工程规矩）**：行业和系统里不能踩的硬约束。比如：“多 Agent 系统里，负责拆解协调的 Agent 绝对不允许直接调用底层执行工具，必须派发给专职 Agent 去干。”
* **Historical Context（踩坑史与淘汰方案）**：极其值钱但最容易丢失的团队记忆。比如：“去年二季度我们试过把全部逻辑塞进单条长提示词里，结果长对话下上下文溢出彻底跑偏，所以这次必须做阶段日志拆解。”
* **Quality Context（好坏具体样例）**：用实际例子代替空洞形容词。与其写“回复要专业有温度”，不如直接放进去 3 条拿到客户 5 星好评的真实对话和 2 条收到投诉的糟糕回复，指明差距在哪。
* **Constraint Context（现实硬限制）**：直接决定技术方案选型的条件。比如：“必须兼容免费版 API 的调用频率上限”“交互延迟不能超过 3 秒”。

### 把一次性的对话，变成磁盘上的持久化文件架构
既然单次会话的上下文窗口（Context Window）不仅容量有限、按 Token 计费，而且会话一关闭就会全部清零，那么**把经验留存下来的唯一工程办法，就是区分“单次会话 Context”和“存在硬盘里的持久化 Memory（记忆）”。**

只要你希望 AI 记住一件事，绝对不能只在聊天框里口头叮嘱一句“记住我们以后不准这样写”，而必须**落成项目仓库里的文本文件，并纳入 Git 版本管理**：

1. **团队共享的全局上下文文件**：比如 Claude Code 用的 `CLAUDE.md`、Gemini CLI 用的 `GEMINI.md`、Cursor 用的 `.cursor/rules` 或 `AGENTS.md`。每次研发或 PM 发现 AI 犯了一个典型错误，或者在 Code Review 里纠正了某处逻辑，就顺手把这条规矩补进共享文件里并提交进 Git——这样团队里任何一个人第二天再唤醒 Agent 时，系统就已经自动长了记性。
2. **专职 Agent 的身份与行为底线文件（`SOUL.md`）**：
   不要把角色定义藏在后台看不见的部署配置里，而是作为可见文件放进仓库。里面写清楚这个专职 Agent 的角色定位、它关心什么、**它明确拒绝做什么（Refusals）**，以及正反样例链接。
   *为什么要做成各自独立的 `SOUL.md`？* Saboo 在同时管理 8 个 Agent 时总结过三个血泪教训：
   * **误区一：步骤写得太死（Over-specifying）**：他最初给调研 Agent 规定了“按固定顺序搜这 5 个网站、按死模板输出”，结果漏掉了大量重要信息；后来改成给清晰原则（“只抓取开发者今天就能上手使用的工具、每条结论必须有原始出处、跳过纯公关通稿”），产出质量立刻大幅跃升。
   * **误区二：前两周嫌弃得太早、过早接管（Stepping in too early）**：刚搭建新 Agent 的头两周最痛苦，调研 Agent 一次推来 47 条新闻，真正值得看的只有 7 条，很多人这时候就觉得“AI 不行”直接放弃自己手干了。但 Saboo 把这两周挑出来的垃圾输出当成最宝贵的纠偏数据，往它的文件里补了一句硬规则：“如果读者今天看完这条信息不能直接动手做点什么，直接跳过。”一句话就把 47 条噪声压成了精准的 7 条。这和带刚入职的新员工一模一样，第一个月投入产出比往往是负的，扛过磨合期后，每一次纠正才会变成后续省力的基础。
   * **误区三：用同一套死规矩管所有工种（Treating all agents the same）**：调研型 Agent 需要极度严谨、严禁无来源猜测；但内容创作型 Agent 则需要一定的表达空间，如果拿管调研的那套死板规矩套在写作上，出来的文章就会干瘪得像技术文档没人看。
   *(如果系统发展到需要多个 Agent 在复杂网络里动态互相发现和派活，还可以配合类似 Agent2Agent 协议的 JSON 格式 `Agent Card` 对外声明能力，但起步阶段 `SOUL.md` 已经足够。)*
3. **两层记忆文件系统（解决跨天、跨 Agent 交接失忆）**：
   * **第一层 · 每日过程日志（`memory/YYYY-MM-DD.md`）**：只追加不覆盖的当天流水账（例如“上午 10:30 完成竞品调研，发现竞品 A 按席位收费、竞品 B 按用量收费，已确认采用按用量收费；下午 4:00 阻塞，等待关键词清单”）。当 Agent 1 跑完研究退出后，Agent 3 启动时只要读一遍今天这份日志文件，就能无缝接着往下干。
   * **第二层 · 长期沉淀记忆（`MEMORY.md`）**：经过人或协调层筛选提炼后的持久认知，只存真正关键的产品偏好、重大业务拍板（附带日期）以及反复验证过的规律（例如“带具体案例的初稿通过率明显更高”）。

## 二、 注意力稀释的工程约束：为什么不能把所有规则一股脑全塞进 `CLAUDE.md`？

顺着上面的做法往后走一个月，很多人会自然掉进下一个工程陷阱——**以为把几千行经验、业务规则和踩坑记录全写进默认加载的主文件里，AI 就会变得无所不知。**

结果恰恰相反：上下文文件越堆越长，模型漏掉关键约束的概率急剧升高，前后不同时期写下的规则开始互相冲突，原本只要 10 秒钟能看懂的简单指令，AI 反倒开始左右摇摆、忘掉最基本的底线。

这就是为什么我们在解读 **Matt Pocock 的 `writing-for-agents` 规范**时，会发现他和 Saboo 之间有一个极其关键的互补——Saboo 讲了“怎么把经验沉淀进文件”，而 Matt Pocock 则从工程信息架构上解决了**“怎么防止规则文件膨胀把模型注意力搞垮”**。

他在仓库里定下了五条非常克制的编写原则（也解释了为什么他的 `grill-with-docs` 入口 Skill 只有短短一行调用指令）：

1. **Context Pointer（上下文指针）**：根配置文件（如 `CLAUDE.md` 或主 `SKILL.md`）必须保持极度精简，绝对不要在里面铺开几万字细节。主文件只负责告诉 Agent：**“仓库里有哪些参考文件，在什么情况下它们有用，需要用的时候再去读全文。”**
2. **Progressive Disclosure（渐进披露）**：把特定条件才用得到的详细规范拆到独立的参考文件里（比如在 `tdd` 目录下把主流程、Mock 规范 `mocking.md`、测试样例 `tests.md` 拆开；在 `codebase-design` 下把独立方案对比流程拆成 `DESIGN-IT-TWICE.md`）。不写测试的时候，Agent 根本不用把那几百行 Mock 细则读进当前对话窗口，省下宝贵的上下文注意力。
3. **Single Source of Truth（单一事实来源，SSOT）**：每一条工程或业务规则在整个仓库里只保留唯一一份权威版本，其他工作流通过引用去调用它（就像 `grill-with-docs` 直接调用 `grilling` 和 `domain-modeling`），绝不允许把同一段规矩复制粘贴到五个文件里——否则一旦以后改了其中一份，另外四份立刻就变成了互相矛盾的过期规则。
4. **Completion Criteria（可验证的完成标准）**：每一步操作都要写死客观的结束条件（例如“必须实际跑通测试命令并把输出贴出来”“所有边界决策均已由用户确认”），防止模型在刚写完一半时就抢着宣布“任务已完成”。
5. **Leading Words（精确的专业引导词）**：用含义极精准的行业概念词（如 `Tracer Bullet`、`Frontier`、`Seam`、`Red-Green`）替代一大段模糊的自然语言解释，用极短的文本稳定触发 Agent 对应的行为模式。

## 三、 规则文件用久了必然退化：用 Loop Engineering 对抗“产物漂移（Artifact Drift）”

哪怕把文件结构切得很干净，只要业务在往前跑、项目在迭代，三个月之后依然会出现另一个隐蔽问题——Saboo 在《Loop Engineering for Product Managers》里称之为 **Artifact Drift（规则产物漂移）**。

它的典型症状是：你的 `CLAUDE.md` 不断因为新项目打补丁，你的 PRD 评审清单为了防以前踩过的坑越加越苛刻，你的客户访谈总结模版悄悄带上了半年前某个老项目的特殊偏好，你的评估标准偷偷改过几次但早就没人记得什么时候改的、为什么改。结果一个月后，团队明显觉得 Agent 写的 PRD 变差了、出的调研总结越来越平庸。其实底层大模型并没有降级，**是你喂给它的规则产物在无人看管的情况下悄悄退化了。**

*(顺便提醒一个实操大坑：有些文章鼓励“只要 Agent 犯错，就让 Agent 自己去重写它的 `SOUL.md` 或规则文件”。但如果在没有测试兜底的情况下放任 LLM 自己改自己的系统指令，很容易改着改着把一条极其关键的老原则给删了、或者针对某一次偶发报错加上一条过拟合的死规矩，越改越歪。)*

要让这套系统越跑越锐利而不是悄悄腐烂，就必须把写一次性 Prompt 升级成 **Loop Engineering（带反馈校验的持续改进循环）**——像运维一套真实产品一样去运维你的规则文件：

### 1. 一个可靠的运行循环必须配齐五个要素
任何一个长期跑在业务或产品工作流里的 Agent 循环，缺了下面任何一块都会出问题：
* **Trigger（触发条件）**：明确什么时候启动（例如每周五下午五点自动跑，或者每次有新 PRD 提交审查时触发）。
* **Action（执行动作）**：读取指定输入和指导规则文件，产出一份目标产物。
* **Proof（客观校验依据）**：用什么硬标准判断这次输出比上次更好、或者达到了及格线？
* **Memory（经验沉淀与版本位置）**：确认有效的改动写回哪里保存？
* **Stop Condition（停止条件）——最容易被漏掉、却最致命的一环**：
  很多自动化系统跑崩，不是因为模型笨，而是因为循环里没有设计干净的退出机制。Agent 被要求干活，哪怕今天根本没有有价值的新数据，它也要硬生生编出一份看似满分的总结；或者遇到需求有歧义时不会停，自己顺着脑补继续往下写代码、越改越远。
  **一个合格的工作循环，必须明确允许甚至要求 Agent 在出现以下情况时主动停下来汇报：**“本周没有实质性新信号”“输入证据太单薄不足以下结论”“前置条件被阻塞”“输出未达到质量门槛”或“当前分歧需要人类拍板”。**敢在拿不准的时候说“停”的自动化系统，才敢让它无人值守运行；不会说“停”的系统，你只能寸步不离地盯着它。**

### 2. 产品经理落地第一套闭环：用 Git 管版本，拿“已知样本”做轻量级回归测试
不需要一上来搞复杂的工程框架，产品经理可以从最贴近日常工作的 **Product Ops（产品运营动作）** 起步——比如先别让 Agent 自动替你拍板公司战略，而是搭一个 **每周产品信号汇总循环（Weekly Product Signal Loop）**：

每周五，让 Agent 统一读取本周的客户通话记录、客服工单、销售备注、上线实验更新、埋点数据摘要和升级投诉，产出唯一一份产品信号备忘录。这份备忘录不能写成空洞的总结，而是按硬标准过滤：剥离孤立的偶发吐槽与反复出现的强信号、保留客户原话、对比上周发生了什么变化、明确标出哪些地方证据还不够、判断既有 Roadmap 里的哪些假设被加强或被削弱了。

更重要的是后续的**校验和版本管理机制**：
* **把 GitHub 当作产品规则的版本记忆库**：不要在聊天框里随手改完提示词就丢了。把你的 PRD 审查规范、访谈总结提示词、上线检查清单放进 Git 仓库。每次改动规则文件都有 Commit 记录和 Diff 对比，一旦发现改完后 AI 输出变差了，直接一键回滚。
* **用低成本“已知正反例”做回归评测（PM Evals）**：每次你想修改一份十个人都在用的 PRD 审查规范或调研总结模板时，怎么证明你的修改不是凭感觉瞎改，而是真的变好了？方法极其朴素：
  * 从历史项目里挑出 **3 份公认优秀的 PRD 和 3 份公认写得差的 PRD**，固定作为测试样本集；
  * 每次改完审查规则文件，拿这 6 份固定样本跑一遍，检查它是不是精准揪出了那 3 份差 PRD 里的真问题（比如需求逻辑模糊、缺少业务证据、漏掉核心指标），同时有没有因为规则过严而对那 3 份好 PRD 进行无意义的吹毛求疵。
  * 同理，拿 5 段你亲自做过、心里门清的客户访谈录音测总结规则，或者拿“一次顺利上线 + 一次线上翻车”的两次历史发布记录测上线检查清单，看看改完后的清单能不能准确拦住当年那次翻车的原因。

只有经过固定测试样本验证“确实比上一版更准”的修改，才正式合并进主分支。这样一来，你的规则资产才算真正进入了“越用越准”的轨道。

## 四、 从单兵循环到团队协同：什么时候需要多 Agent 任务板，以及如何防止它和现实脱节？

搞定了单个工作流的稳定性，最后一个工程问题是：**什么时候需要像 Saboo 那样同时开好几个专职 Agent 协作？多 Agent 一旦并发起来，怎么防止系统失控？**

先说一条最重要的底线原则：**永远用能够控制住复杂度的最小方案。**
如果一个任务结构清楚，单个 Agent 带着几样工具、自己执行并自检（观察 → 行动 → 检查结果 → 重复或停止）两三步就能搞定，那就老老实实用单 Agent 循环，千万不要为了赶时髦硬搭一套五六个 Agent 互相传话的复杂架构——每一个新增的 Agent 节点都在成倍拉高沟通损耗、Token 成本和出错概率。

只有当任务跨越多个专业环节、需要持续交接、或者存在大量可独立并行的子任务时，才值得把计划从单个 Agent 的脑子里搬出来，放进更规范的调度结构里。

### 1. 多 Agent 协调的三条基本工程纪律
1. **默认串行，确认完全无依赖才显式并行**：
   很多人刚接触多 Agent 时喜欢一上来同时发五六个任务出去，结果共享状态被互相写乱、日志交织成一团根本没法看。正确的做法是画出依赖关系——比如对比竞品页面时，“调研竞品 A”、“调研竞品 B”、“分析搜索关键词”这三件事互相完全独立，可以安全并行；但后面的“初稿撰写”依赖前面的“调研结论”，“审校修改”依赖“初稿”，这一串必须老老实实串行等待，确保下游绝不会拿着上游还没产出的半成品开工。
2. **用错峰定时检查（Staggered Heartbeats）代替死等或空烧经费**：
   如果多个 Agent 需要异步配合（比如每天早上定时整理情报并触发后续写作），既不能让它们全天死循环轮询浪费 API 费用，也不能让全部 Agent 在整点 `:00` 同时唤醒抢资源。成熟的做法是通过定时任务每隔 30 分钟错峰唤醒（例如 `:00` 唤醒 Agent 1、`:02` 唤醒 Agent 2、`:04` 唤醒 Agent 3），而且检查“当前有没有新派给我的活”这一步只调用最便宜的轻量模型，确认有任务了再切到强模型干正事。
3. **固定流程图 vs. 动态共享任务看板（Dynamic Task Graph）**：
   如果工作流步骤固定不变（例如永远是固定的 1→2→3 步数据处理），用类似 LangGraph 的固定流程图最稳妥；但在真实的软件研发和复杂产品项目里，**绝大多数新任务是在干活的过程中才冒出来的**——比如写新功能时突然发现底层有个老 Bug、或者拆分任务后发现某一块卡住需要临时加个审查步骤。
   这时，最好的结构是像第三篇提到的 Matt Pocock 的 `implement-spec`，或者 Saboo 分享的 FarmTable 那样，建立一个**共享任务看板（本质是一个带原子锁的依赖有向无环图 DAG）**：
   * 看板上的每个卡片是一个明确的任务，箭头代表先后阻塞关系，Agent 发现新 Bug 时直接在看板上新增一张带依赖的卡片；
   * 看板上“当前没有前置阻塞的待办任务数量”，直接决定了你最多能安全并行几个 Agent（只有两个任务就绪时，硬派五个 Agent 上去纯属制造冲突）；
   * 顶层的协调规则甚至可以根据运行信号动态调整团队阵型——比如某个环节连续两次犯同类错误时自动切换更强模型；某个模块报错率升高时临时在“完成”和“发布”之间插进一个审查步骤，稳定后再撤掉；如果发现多 Agent 并发的算力成本高于任务本身价值，就自动收拢回一个强模型单兵解决。

### 2. 血的教训：如何防止共享任务看板和代码现实脱节（Board Drift）？
即便搭出了共享任务看板，多 Agent 协作在真实运行中依然极易踩进三个隐蔽大坑（Saboo 和他的朋友在 FarmTable 实测中全踩过一遍），必须用三条硬规矩提前堵死：

* **坑一：看板排得整整齐齐，但根本没核对实际代码库状态。**
  比如规划 Agent 一口气在看板上拆出 57 个完美任务，结果动手前没去读代码仓库，真跑起来才发现其中三分之一的功能以前其实早就写过了。
  *硬规矩：制定任务规划前，必须强制 Agent 先核实真实代码库和线上业务现状。*
* **坑二：Agent 把任务标成了“Done（已完成）”，但实际功能根本没跑通。**
  比如看板显示 5 个任务全部标为完成，人类一检查发现真正落地生效的只有 2 个——因为对 Agent 来说，“把数据库或 Markdown 里的状态字段改成 Done”只是一次文本编辑，并不代表代码真的写对、编译通过了。
  *硬规矩：严禁把 Agent 自己写的完成声明当真，任务状态流转必须绑定真实跑通的自动化测试或客观验收脚本凭证（Proof）。*
* **坑三：修完顺手活忘了去看板做认领记录，导致任务被重复做两遍。**
  一个 Agent 顺手修掉了个 Bug 但没在看板上原子化认领状态，几分钟后另一个 Agent 又拿起同一张卡片从头改了一遍，直接覆盖冲突。
  *硬规矩：任务认领和状态更新必须原子化写入共享看板，绝不允许留在单个 Agent 的临时上下文里。*

## 五、 全系列收官：用“工作分工图”重构团队，以及必须守住的三条清醒底线

走完这四篇从底层逻辑到一线系统运维的完整推演，如果我们把视角拉回组织和个人的真实处境，其实可以用 Reforge 的 JZ 在《The Executive Builder》里提出的一个极实用工具，把整套体系收归到日常行动上——**用“工作分工图（Work Chart）”取代传统的“组织架构图（Org Chart）”。**

传统公司的架构图上画的只是“谁向谁汇报、谁管几个下属”。而今天真正决定一个团队产出上限的 **Work Chart**，画的是沿着整个产品生命周期（从问题验证、方案设计、原型开发、线上交付到数据复盘），把**人类负责人、专职 Agent、自动化工作流以及共享规则文件**全部摆在一张图上，明确每一块工作到底由谁扛。

无论你是产品经理、研发工程师还是业务负责人，都可以立刻用 JZ 给出的两个问题来审视自己每天的日程表：
1. **这件事需要人类特有的判断力吗？**（例如去业务现场跟客户深聊看微表情、感知跨部门利害关系、凭商业前瞻性追问出下一个核心问题、做出有取舍的产品决定。）
2. **如果不需要，我是不是已经用自动化循环或共享工作流把这些“洗衣服刷碗式的日常杂活”接管出去了？**（例如每周进度汇总、固定格式的客服反馈分类、常规周报、模板化文档整理、基础测试脚本生成。）

自动化掉那些机械重复的日常，不是为了让人闲下来，而是为了**把有限的时间和注意力彻底腾出来，投回到真正决定产品生死的“一线认知、产品品味、验证设计与结果责任”上去。**

*(同时也要清醒记住 JZ 敲过的警钟：在一个依然按旧模式运作、IT 工具受限、审批层级森严的传统大公司里零散用几个 AI 工具，并不会让你自动拥有 AI 原生团队的生产力。如果环境限制让你连一个端到端小功能都无法独立验证和上线，你至少要通过外部社区交流或个人业余实践，亲手完成至少一次从发现问题到真实交付的完整闭环，才不会在旧环境里不知不觉失去手感。)*

### 贯穿全系列的最后三条清醒边界

在四篇文章全部收尾之际，越是看到 AI 和 Agent 带来的巨大效率杠杆，我们越有必要把这三块泼向过度乐观的冷水留在脑子里：

1. **永远区分“AI 原生轻装创业公司 / 开源 Demo”与“复杂存量企业系统”的约束条件。**
   无论 Lovable 全员提交代码的奇迹，还是 Saboo 一个人指挥 8 个 Agent 日产几十篇研究与 Demo，它们的共性都是历史包袱轻、容错率高、业务关联边界清晰。一旦放进强合规监管的银行、医疗核心系统、复杂制造业供应链或拥有十几年历史代码的大企业里，**真正的瓶颈依然是组织利益重组、合规风控和遗留系统耦合**。在这种情况下，强行追求全自动无人并发不仅危险，而且毫无意义——在旧体系里能够打通线下信任、搞清 L3/L4 业务真相，并谨慎地把验证设计和工程护栏一步步引入关键环节的人，才是真正能解决大问题的人。
2. **算力可以并发，但人类的注意力和判断带宽有物理上限。**
   多 Agent 编排听起来像是在电脑前指挥千军万马，但不要忘记 Anand 目睹的真实翻车现场：当团队让工程师同时放任 40 个 Agent 并发运转却没有跟上验证机制时，所有人都被淹没在海量待审核的产出里，最终没人说得清项目到底卡在哪里。**系统的复杂程度，永远不能超过你手头验证机制和人类负责人大脑所能掌控的极限。**
3. **老一辈靠踩坑磨出来的“直觉”，新人未来该怎么获得？**
   贯穿四篇文章，我们反复依赖了几个听起来很高级的词：**Product Taste（产品品味）**、**系统架构眼光**、**一眼看穿 AI 漏洞的直觉**。但请诚实追问一句：今天站在行业里讲这些方法论的人（无论是 Marty Cagan、JZ、Hamel、Matt Pocock 还是 Saboo），他们的直觉全都是过去十几年**亲手一行行写代码、熬夜排查凌晨两点线上崩溃、亲手把产品做砸过无数次**才攒出来的。
   如果今天的新人从入行第一天起，就把写基础代码、做资料整理、写初版 PRD 全部外包给 Agent，跳过了一线亲手试错和修改细节的枯燥磨炼——**当老一辈逐渐退场后，跳过执行层的下一代从业者，到底该靠什么长出足以审查和指挥 AI 的真实判断力？** 这目前依然是一个悬而未决、需要每个技术与产品负责人认真面对的培养难题。

### 全系列四篇总收束

把这四篇长文的所有推导浓缩成最后四句话，刚好构成一个完整、可落地的行动坐标：

1. **找准位置（第一篇）**：当编码实现和普通文档不再稀缺时，退出纯传话和纯搬砖的中间层；深入业务现场拿到未数字化的真实 Context，向“对业务结果负责的问题解决者”或“系统与工程护栏建设者”演进。
2. **用对验证（第二篇）**：用最低成本的实验和带真实数据的可运行原型做 `Build to Learn`，严守 `Vision Prototype` 与 `MVP Scope` 的分叉红线，敢于销毁 80% 不够好的想法，并从产品设计源头为用户和评测提供“溯源、差异对比与小单元核对”。
3. **守住底线（第三篇）**：正视自然语言作为工程规格的局限性，把资深工程师的决策树澄清、垂直切片、工作区隔离、面向接口边界的 TDD 和双维度代码审查固化为 Agent 护栏，并与研发共同维护版本化的可执行产品规范。
4. **长期运维（第四篇）**：像维护软件一样维护你的 Context 和规则文件——通过指针按需加载防止注意力稀释，通过 Loop 的停止条件、Git 版本记录和固定样本回归评测防止规则退化，只在真正需要时才用依赖图和硬测试证明驱动多 Agent 协同。

工具和模型每隔几个月就会换代一次，但隐藏在这些具体做法背后的**第一性原理**——看清真实世界的问题、用最小代价获得可靠证据、为系统建立确定性验证边界、并敢为最终结果承担责任——无论技术再往前演进多少轮，都不会过时。
