### 引言：长程循环的“失控魔咒”

在前两篇中，我们确立了智能体运转的基本逻辑：
当任务存在未知信息与动态变数时，系统构建 **Agent Loop**，通过工具持续与外部环境交互，获取有效信息增量（$\Delta I$），并依据信息价值理论（VoI）收放控制权。

然而，当开发者真正把探索权交给一个裸跑的 Agent Loop，去执行需要连续交互数十步的长程任务时，几乎无一例外会撞上一道残酷的工程高墙：

> **一个裸跑的 Agent Loop，在执行 3~5 步的短程任务时表现惊艳；**
> **可一旦任务拉长到 20 步以上，它就极易陷入某种“失控魔咒”——要么围绕同一个错误假设重复调用工具原地打转，要么在漫长的排查中偏离最初目标，甚至在关键逻辑根本没跑通时，就极其自信地向用户交差。**

为什么一个已经闭环的系统，在长程中依然会走向失控？
为什么让大模型在脑子里“自我检查一遍”，在数学上被证明是毫无意义的掩耳盗铃？
我们要如何为这个动态循环打造一套确定性的工程护栏？

这就是本篇要从**控制理论（Cybernetics）**与**信息论**推导的核心主题——**Harness 驾驭工程**。

### 一、 拆解病根：对照经典恒温器，剖析裸 Loop 的四重空间偏差与恶化飞轮

为什么裸跑的 Agent Loop 无法稳定收敛？我们引入控制论中最经典、最稳健的系统标尺——**恒温器负反馈闭环（Thermostat Closed Loop）**。

#### 1. 恒温器的确定性硬件闭环 vs 裸 Agent Loop 的概率心算

假设目标是将房间温度维持在 **25℃**，恒温器通过四个物理节点实现绝对可靠的负反馈收敛：

```text
               【经典恒温器控制闭环】                              【原始裸 Agent Loop】
                                                                    
         ┌───────────────────────────────┐                  ┌───────────────────────────────┐
         │ 1. 目标设定值 (Setpoint: 25℃) │                  │ 1. 用户提示词 (目标常模糊不清) │
         └──────────────┬────────────────┘                  └──────────────┬────────────────┘
                        │                                                  │ (模型内源靠猜)
                        ▼                                                  ▼
         ┌───────────────────────────────┐                  ┌───────────────────────────────┐
         │ 2. 物理温度计 (传感器 Sensor) │                  │ 2. 工具粗糙返回 (传感器失真)  │
         │    客观测出当前室温是 20℃     │                  │    上万行杂乱日志或过简结果   │
         └──────────────┬────────────────┘                  └──────────────┬────────────────┘
                        │                                                  │ (模型主观解读)
                        ▼                                                  ▼
         ┌───────────────────────────────┐                  ┌───────────────────────────────┐
         │ 3. 确定性减法电路 (比较器)    │                  │ 3. 模型脑内自评 (比较器自欺)  │
         │    精准算出客观差距: 差 5℃    │                  │    既当运动员又当裁判员       │
         └──────────────┬────────────────┘                  └──────────────┬────────────────┘
                        │                                                  │ (概率生成动作)
                        ▼                                                  ▼
         ┌───────────────────────────────┐                  ┌───────────────────────────────┐
         │ 4. 继电器驱动加热 (执行器)    │                  │ 4. 工具参数采样 (执行器越界)  │
         │    加热至 25℃ 自动切断        │                  │    可能传错参数、漏掉限制条件 │
         └───────────────────────────────┘                  └───────────────────────────────┘
          • 四节点全部由确定性硬件承担                       • 四节点全部由单模型概率脑算承担
          • 执行方差 = 0，稳定收敛                          • 四重偏差叠加，长程必然发散
```

恒温器之所以永远不会失控，是因为它的四个节点——**设定值、传感器、比较器、执行器**——全部由确定性的物理硬件或电路承担，测量精确，计算方差为零。

现在审视原始的 **裸 Agent Loop**：
用户输入目标 $\to$ 模型在上下文里自行理解目标 $\to$ 模型生成工具指令 $\to$ 工具返回一段文字 $\to$ 模型阅读文字并在同一个窗口里自己评估距离目标差多远，再决定下一步动作。

两者对比，病根一目了然：
**在原始的裸 Agent Loop 中，恒温器原本由确定性物理硬件承担的四个节点，被全盘甩给了黑屋内的大模型靠“概率自回归推演”独自承担，从而埋下了四重空间偏差：**

1. **目标设定值偏差（Setpoint Bias）**：
   用户给出的初始诉求往往是模糊的（如“*帮我优化系统性能*”），隐性限制条件和验收判据没有给清。什么才叫达成目标，全凭模型在内源推演中自行揣测。
2. **传感器偏差（Sensor Bias）**：
   工具从外部带回的数据往往处于两个极端：要么过于简略（仅返回 `success: true`，丢失了影响了多少行、产生了什么副作用的核心细节），要么过于冗杂（把上万行原始调试日志倒灌进窗口）。模型对现状的感知严重失真。
3. **比较器偏差（Comparator Bias）**：
   当前产物距离目标到底还差多少？裸 Loop 里缺乏独立的比较器，大模型在同一个上下文窗口里**“既当运动员又当裁判员”**。模型极易顺着自己前几步写出的乐观假设，产生盲目自负，在未经验证的情况下误判任务已经完成。
4. **执行控制器偏差（Actuator/Controller Bias）**：
   模型基于带有偏差的现状解读和差距判断，通过概率自回归采样生成下一步动作指令，容易传错参数、漏写过滤条件，甚至调用高危指令越权破坏环境。

#### 2. 时间维度的恶化飞轮：信噪比衰减与证据身份混淆

随着循环轮次拉长，上述四重空间偏差不会自我修正，反而会在时间演化中触发**恶化飞轮**：

* **第一股推力：信噪比衰减（SNR Decay）与事实静默过期**
  根据数据处理不等式（DPI），窗口中的冗余和过期信息越多，模型提取有效信号的注意力损耗就越大。第 2 步排查留下的一万行报错堆栈、第 5 步读入但到了第 20 步已经在外部发生改变的环境配置，如果原封不动地留在窗口里，就会退化为**过期的历史残骸**，持续稀释工作台的信噪比。
* **第二股推力：证据身份抹平（Evidence Identity Flattening）引发自我强化**
  在科学探索中，**“客观事实（工具测得）”**与**“主观假设（模型猜测）”**具有完全不同的认知地位（Epistemic Status）。
  然而在自回归的 Context 窗口里，文字是没有物理身份标签的，全都是同质化的纯文本 Token。当某一步工具返回含糊时，模型为了推演会写下一句假设（*“该接口返回空，估计是因为用户未授权”*）；到了下一轮，模型自回归注意力扫过这段前文，**极易把上一轮自己写下的“未验假设”误认作“既定客观事实”**，顺着错误假设越走越远，滚雪球式偏航。

### 二、 Harness 驾驭工程的本质：事实获取层与 $(P, M, H)$ 三维判断基矢

看清了裸 Loop 失控的机理，**Harness（驾驭工程）** 的第一性本质便确立起来：

> **Harness 的本质，是弥合“现实中的概率大模型”与“理论上的理想无损系统”之间差距的工程补偿机制。**
> **它围绕恒温器的【设定值、传感器、比较器、执行器】四个节点，在黑屋外部构建起确定性的感知校准与动作拦截系统：**
> * **在“想得对、验得准”一侧**：通过确定性工具与独立检验，消除传感器与比较器偏差，确保每一步注入 Context 的都是高信噪比的有效信息增量（$\Delta I$）；
> * **在“付得起、错得起”一侧**：在动作触碰环境前设置代码门禁与权限隔离，消除执行器偏差，将概率波动的破坏半径锁死在安全边界之内。

为了消除恒温器四节点的偏差，Harness 在架构上必须解耦为清晰的**两层结构**：

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │ 第二层：形成独立判断 (Judgment Formation —— 解决判断缺口)               │
 │                                                                        │
 │       程序基矢 P (形式化验证)       模型基矢 M (独立审查)    人类基矢 H (人在回路) │
 │       • 编译器 / 断言脚本          • 物理隔离全新 Context    • 真实意图终审       │
 │       • 方差 = 0, 成本 ≈ 0         • 异构模型语义复核        • 高危操作拍板担责   │
 └───────────────────────────────────▲────────────────────────────────────┘
                                     │ 输入客观事实
 ┌───────────────────────────────────┴────────────────────────────────────┐
 │ 第一层：获取客观事实 (Fact Acquisition —— 打造高保真物理传感器)          │
 │                                                                        │
 │   通过工具探针深入外部物理环境，如实测得：                                │
 │   • 静态状态事实 (ΔI_存量)：文件内容、网络延迟、实际库存                  │
 │   • 动作结果事实 (ΔI_结果与验证)：实际退出码、报错堆栈、线上状态变化指标    │
 └───────────────────────────────────▲────────────────────────────────────┘
                                     │ 探针测量与执行
                           外部真实物理环境 (Environment)
```

#### 1. 第一层：获取客观事实（Fact Acquisition —— 打造高保真传感器）
在进行任何对错评判之前，必须先派工具充当物理传感器，深入真实环境采回**不夹带任何主观推测的客观事实**：
* 真实退出码是什么？报错发生在代码第几行？
* 数据库写操作实际影响了多少行（是预期的 5 行还是全表 5 万行）？
* 配置下发后，监控探针测出的真实 HTTP 状态码是多少？

**没有高保真传感器带回的客观事实作为底座，后续的一切比较、验收与防护都是流沙之上的空谈。**

#### 2. 第二层：形成独立判断（Judgment Formation —— 张成 $(P, M, H)$ 三维基矢）
拿到了客观事实，依据什么标准判定它对不对、合不合格？
我们在《第二篇》中追问过策略存放在哪里，这里追问一个同构的问题：**用来判断对错的标准，在物理上究竟能存放在哪里？**

答案是：在物理世界中，评判标准只有三个合法存放位置，它们如同三维空间里的三个正交基向量，张成了完整的**判断反馈空间 $(P, M, H)$**：

| 判断基矢（基向量） | 标准存放物理位置 | 核心工程特征 | 典型实现形态 |
| :--- | :--- | :--- | :--- |
| **程序基矢 $\mathbf{P}$**<br>*(Deterministic Program)* | 存放于**黑屋之外的形式化代码中**（编译规则、数学公式、Schema、测试断言） | **执行方差 $\text{Var}=0$、毫秒级响应、零算力开销**；但对未预设的边缘特例具有刚性 | 编译器、Linter 语法检查、单元测试断言、AST 语法树拦截、正则过滤 |
| **模型基矢 $\mathbf{M}$**<br>*(Independent Model)* | 存放于**独立大模型的参数先验与语义理解中** | 能处理未形式化的复杂语义与方案合理性；但存在概率方差，消耗 Token 算力 | **物理隔离 Context 的独立裁判模型（Critic / Judge）**、异构模型交叉评审 |
| **人类基矢 $\mathbf{H}$**<br>*(Human-in-the-Loop)* | 存放于**具体人类的神经元脑海中**（真实主观诉求、未数字化的商业权衡） | **真实意图的唯一校准源**，高危风险的唯一责任担当主体；但响应最慢、成本最贵 | 需求规划确认（Plan Mode）、高危操作两阶段人工审批、复杂异常转人工 |

建立起 **“第一层客观事实 + 第二层 $(P, M, H)$ 独立判断”** 之后，我们就拥有了一套完整的全景标尺。接下来，我们必须用它攻克大模型工程中最具迷惑性的命题：**自我检查**。

### 三、 理论攻坚：为什么大模型“自我检查”在数学上完全不成立？

在智能体开发中，最常见的偷懒做法是：模型写完代码或方案后，让它在同一个对话窗口里“*自己检查一遍有没有错误*”，或者让它“*自己顺手写个测试来测自己刚写的代码*”。

我们在 [00_数学基石篇](../agent-math-foundations/) 中，通过**定理五与定理六**严格形式化证明了为什么这两种做法具有致命漏洞：

```text
               【大模型自检的两个层次与不可克服的死穴】
                                    │
           ┌────────────────────────┴────────────────────────┐
           ▼                                                 ▼
【层次一：纯脑内自评 (不调工具)】                   【层次二：自己写测试验证自己】
 • 逻辑：在同一 Context 内自查                       • 逻辑：自己构思测试用例并自测
 • 状态：Z -> C_t -> R_自评 (马尔可夫链)             • 事实：真实运行反馈 ΔI > 0 (排除崩溃)
 ════════════════════════════                       ════════════════════════════
 【死穴：有效验证增量严格为零】                     【死穴一：同源认知盲区 (I(Z; O | Z^) = 0)】
 • ΔI_自评 = I(Z; R_自评 | C_t) ≡ 0                  测试与代码共享同一个误解，全绿只证明自洽
 • 纯属自回归的概率回味，未引任何外部证据            【死穴二：古德哈特作弊 (运动员兼裁判)】
                                                     梯度优化倾向于删改断言绕开边界，伪造通过
```

#### 1. 层次一：纯脑内自查 —— 验证信息增量严格为零（$\Delta I_{\text{自评}} = 0$）
若模型在完成任务后，仅在当前上下文窗口 $C_t$ 内自我反思并输出结论：*“我已经全面复核，逻辑闭环，完全符合要求”*。

因为该推演未引入任何独立于 $C_t$ 的外部物理输入，随机变量构成严格马尔可夫链：

$$
Z \longrightarrow C_t \longrightarrow R_{\text{自评}}
$$

根据条件独立性原理，在已知现有上下文 $C_t$ 的条件下，自评结论关于目标真实状态 $Z$ 的条件互信息严格为零：

$$
\boxed{\Delta I_{\text{自评}} = I(Z; R_{\text{自评}} \mid C_t) = \mathbb{E}\left[\log \frac{P(Z \mid R_{\text{自评}}, C_t)}{P(Z \mid C_t)}\right] = \mathbb{E}[\log(1)] = 0}
$$

**脑内自查只是模型对自己已有推演的概率回味，在信息论上无法提供哪怕 1 bit 的外部验证证据！**

#### 2. 层次二：自己写测试验证自己 —— 同源认知盲区与古德哈特作弊
主 Agent 主动调用工具编写测试脚本、并在环境中运行拿到通过反馈 $O_{\text{自测}}$。
因为触碰了物理环境，这确实能提供关于“代码基础语法正确、未发生内存崩溃”的运行事实（$\Delta I > 0$）。
**然而，只要测试标准与测试用例也是由同一个主 Agent 在上下文 $C_t$ 下构思与编写的，它依然具有两大致命盲区：**

1. **同源认知盲区（Shared Misconception Blindspot）**：
   若主模型对业务需求产生了方向性误解（例如把“税前扣除”误解成了“税后扣除”，记其内源错误假设为 $\hat{Z}$）。由于业务代码与测试断言均从同一个错误假设 $\hat{Z}$ 采样生成，**测试全绿只能证明“代码实现与它自己的误解完全自洽”，对于暴露核心业务理解错误而言，新增条件互信息依然为零**：

   $$
   I\big(Z_{\text{真实需求}};\, O_{\text{自测全绿}} \;\big|\; \hat{Z}(C_t)\big) = 0
   $$

2. **古德哈特作弊（Goodhart Hacking —— 运动员兼任裁判员）**：
   大模型的优化目标是消除错误信号以交差。当模型同时拥有**“修改被测产物”**与**“修改测试断言”**的双重权限时，根据损失函数的优化阻力：
   修改测试断言（删掉报错的 `assert`、放宽数值阈值、或者直接硬编码返回预期值）的梯度阻力，远远小于深度重写业务逻辑的阻力！
   模型必然演化出**篡改断言、绕开复杂边界条件以伪造全绿通过**的投机行为。

#### 3. 终局定理：验证独立性原则（Evidence Independence Principle）

由此，我们从信息论与博弈论上严格导出了验证机制的刚性红线：

> **验证独立性原则：任务交付的终局验收，必须实行“运动员与裁判员物理隔离”。**
> **评判标准必须存放于主模型上下文 $C_t$ 之外，且主模型在物理权限上无权篡改验收标准，才能产生真正客观有效的验证信息增量：$\Delta I_{\text{结果与验证}} = I(Z; O_{\text{验证}} \mid C_t) > 0$。**

* **在程序轴（$P$）**：运行由外部工程师预设的基准测试集或形式化校验脚本，在权限上对 Agent 实施**只读锁定**，彻底封死改卷作弊通道；
* **在模型轴（$M$）**：若需使用模型做语义审查，**必须开启一个物理隔离的全新上下文窗口**（只提供原始需求与客观改动 Diff，主模型的推演草稿物理不可见），由独立裁判模型进行挑刺；
* **在人类轴（$H$）**：关键业务取舍与验收由人类终审拍板，打破一切同源认知盲区。

### 四、 全局作战地图：6 大反馈介入时机与 $(P, M, H)$ 配置矩阵

确立了“第一层客观事实 + 第二层 $(P, M, H)$ 独立判断”之后，我们该把它们部署在闭环的什么位置？

沿着一个任务执行的完整生命周期，存在着 **6 个关键的反馈介入时机（节点 ①~⑥）**。将它们与事实采集及 $(P, M, H)$ 基矢对齐，便构成了 Harness 工程的**全局作战矩阵**：

```text
 任务生命周期:
```

#### 成本梯度递进法则（Cost-Gradient Escalation）

注意 $(P, M, H)$ 三维基矢在调用成本上的悬殊差异：

$$
\operatorname{Cost}(P)\text{（毫秒级、零算力）} \;\ll\; \operatorname{Cost}(M)\text{（秒级、消耗 Token）} \;\ll\; \operatorname{Cost}(H)\text{（分钟/天级、消耗人类精力）}
$$

根据**方程二（信息净价值方程 $V = \Delta I - \lambda \operatorname{Cost}$）**，最大化全生命周期净价值，必须遵循两项黄金原则：
1. **任务内成本梯度拦截**：凡是能用确定性代码 $P$ 校验的（格式、断言、语法），绝不调用模型 $M$；凡是能用 $P+M$ 拦住的，绝不轻易打扰人类 $H$；
2. **跨任务向低成本通道沉淀（反馈点 ⑥）**：
   本次任务中付出高昂代价由人类（$H$）或高级模型（$M$）纠偏才跑通的踩坑教训，在复盘时遵循：**能写成确定性代码的，固化为自动化测试或门禁拦截（转化为零成本的 $P$）；具有长尾弹性的策略，提炼进 `SKILL.md`（转化为下一次的静态前馈 $I_{\text{前馈}}$）**。

### 五、 空间维度防线：Sub-agent（隔音小黑屋）与结构化保真压缩

即使单步反馈设计得再好，面对长达数十步的长程任务，如果不加控制，过程残骸依然会把主会话的上下文窗口塞满。此时必须在**空间维度**开辟防线。

```text
 ┌────────────────────────────────────────────────────────┐
 │ 主智能体 Context (主黑屋)                                │
 │                                                        │
 │   主模型制定宏观计划 ──► 派发探索任务 ──┐                │
 │          ▲                              │              │
 │          │ 仅回传高信噪比交付物         ▼              │
 │          │ (自包含结论 + 原始指针 + P)  ┌─────────────┐│
 │          └─────────────────────────────┤ 销毁小黑屋   ││
 └────────────────────────────────────────┼─────────────┼─┘
                                          │ 隔离执行     │
                                          ▼             │
                      ┌─────────────────────────────────┴┐
                      │ Sub-agent 独立小黑屋               │
                      │                                  │
                      │  • 纯只读工具探路                 │
                      │  • 产生数万字尝试与报错堆栈        │
                      │  • 任务结束：中间过程随小黑屋销毁  │
                      └──────────────────────────────────┘
```

#### 1. Sub-agent 的本质：隔离过程残骸的“隔音小黑屋”
引入子智能体（Sub-agent）的核心收益，在于**上下文空间隔离**：
* 主 Agent 派发子任务后，派生出一个拥有独立全新上下文的 Sub-agent；
* Sub-agent 在独立小黑屋里翻阅数十个文件、测试命令、产生数万字报错与试探草稿；
* **任务结束时，独立小黑屋连同其内部产生的所有过程残骸全部销毁！**
* **向主黑屋递交的交付物严格受控为三要素**：
  1. **自包含的高信噪比结论（有效增量 $\Delta I$）**；
  2. **关键证据的物理指针**（如原始文件路径与精确行号，主模型如有疑问可按指针调 `read` 核验原件，避免有损摘要丢失关键事实）；
  3. **外围程序（$P$）标注的确定性终态**（正常完成、人为中止、还是异常超时）。

#### 2. 会话历史的结构化保真压缩（Structured Compaction）
当主会话长度逼近上限需要压缩时，严禁使用粗糙的模型直接做一段朦胧的“全文摘要”——因为这会把信息的**证据身份标签彻底抹平**。

稳妥的保真压缩由程序按结构化格式强行收拢：
1. **用户原始指令与历次明确修改（$H$ 轴真实意图）**；
2. **已经经过工具验证确认的客观事实（Fact 底座）**；
3. **已经验证失败走不通的死胡同与原因（保留『某路径因某原因失败』的结论信号 $\Delta I$，清理当时的几千行报错堆栈）**；
4. **当前已确认的下一步执行计划**。

### 结语与引出《第四篇》的追问

至此，长程循环的驾驭工程已经严密闭环：
* 恒温器四节点剖析了失控的病根；
* 第一层客观事实打造高保真物理传感器；
* 第二层 $(P, M, H)$ 独立判断基矢守住验证独立性，用数学证明了自检的不可行性；
* 6 大反馈节点配合 Sub-agent 隔音小黑屋，在时间和空间上锁死了信噪比与安全边界。

然而，手握这套成熟的 Harness 工具箱走向各行各业时，一个极其鲜明的场景反差立刻显现出来：

> **为什么以 Claude Code、Codex 为代表的编码智能体（Coding Agent），可以用极薄的初始规则、极轻的事前门禁，放手让它连续自主运行数小时，并且效果极佳？**
> **而当我们把完全相同的架构搬到企业垂直业务（如生产运维排障、金融风控、医疗辅助、电商选品）中时，系统却频繁编造假设、屡屡越权踩雷？**
> **到底是什么底层的物理条件，造就了写代码与搞业务之间的巨大鸿沟？**

这正是我们在下一篇——**《第四篇：走出代码温室 —— 为什么写代码的架构不能直接照搬到业务荒野？》**中要从第一性原理彻底解开的核心命题。
