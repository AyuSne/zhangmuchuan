### 引言：同一套循环架构，为什么一换场景表现就显著分化？

在当前的 AI 工程落地中，存在着一个极其鲜明的对比反差：

一方面，以 Claude Code、Codex 为代表的**编码智能体（Coding Agent）**已经高度成熟。面对复杂的软件重构或 Bug 修复任务，系统往往只需一段极短的初始提示词，就能自主翻阅上百个源码文件、修改代码、执行测试并根据报错自我修正，连续自主运转数小时并稳定交付可用产物。我们在前两篇讨论的诸多最佳实践（如按需加载 Skill、局部精准编辑、子智能体空间隔离），大多是在编程场景中打磨成熟的。

另一方面，当技术团队试图把 Coding Agent 这套极简、高自主的循环架构，原封不动地搬到**企业垂直业务场景**（如生产环境运维排障、金融信贷风控、医疗临床辅助、电商运营）时，却往往遭遇严重的滑铁卢：
要么系统在测试阶段原地打转、编造假设无法收敛；要么上线后因误改生产环境配置、对客户做出违规承诺而引发重大业务事故。

为什么同一套大模型与相同的 Agent Loop 闭环，在不同场景下的表现会产生如此天壤之别？
是大模型“天生擅长写代码，天生不擅长搞业务”吗？

回到我们建立的第一性原理，答案就在于我们在 [00_数学基石篇](../agent-math-foundations/) 中推导出的**期望信息净价值方程（核心方程二）**在获取成本两极的数学收敛：

$$
\mathbf{V(a \mid C_t) = \Delta I_{\text{反馈}}(a) - \lambda \operatorname{Cost}(a)}
$$

> **根本物理原因在于：写代码的世界拥有一个让信息获取成本趋近于零（$\operatorname{Cost} \to 0$）的“天然温室”，动手试错是获取有效信息最廉价的手段；而在真实的垂直业务中，外部反馈获取成本趋向无穷大（$\operatorname{Cost} \to +\infty$），这道成本鸿沟彻底重构了系统的控制权配比。**

本文将从五个场景维度拆解这一物理差异，揭示为什么垂直场景下的潜规则“问不出来只能撞出来”，并给出将业务荒野改造成业务温室的四项基建工程。

### 一、 两个极值收敛：草稿纸模式 vs 手术台模式

审视方程二 $V = \Delta I - \lambda \operatorname{Cost}$，决定一个场景能释放多大自主权、需要多厚护栏的，主要取决于两个底层物理变量：

```text
                           【方程二在场景成本两极的数学收敛】
                                            │
        ┌───────────────────────────────────┴───────────────────────────────────┐
        ▼                                                                       ▼
【极值一：零成本试错极限 (Cost -> 0)】                   【极值二：无穷大成本极限 (Cost -> +∞)】
 • 场景：本地代码开发 (沙箱 + 编译器)                     • 场景：生产运维 / 金融风控 / 医疗
 • 公式：V(a) ≈ ΔI_反馈(a) > 0                           • 公式：V(a_高危) -> -∞ < 0 (试错通道被封死)
 ════════════════════════════                            ════════════════════════════
    【草稿纸模式 (Draft Paper Mode)】                        【手术台模式 (Operating Table Mode)】
 • 初始前馈 I_前馈 极薄，事前门禁极轻                    • 做厚 I_前馈，主循环读写物理分离
 • 放手边做边探 (双重控制 Dual Control)                  • 写前拉满 P+M+H 预审，交由人类 H 拍板担责
 • 靠高频运行编译器断言 (P) 快速收敛                     • 事后通过决策快照进行长周期指标对账
```

1. **极值一：零成本试错极限（$\operatorname{Cost} \to 0$）—— 编码场景的“草稿纸模式”**
   在本地代码开发沙箱中，因有版本控制系统（Git）兜底，写错代码的物理破坏代价为零；同时，编译器与测试套件（形式化验证器 $P$）可以在毫秒级内返回精确到行号的客观报错。代入方程二得 $V(a) \approx \Delta I_{\text{反馈}}(a) > 0$。
   这意味着：**通过“先动手改代码、看编译器报错再修改（双重控制 Dual Control）”，是获取高价值动态反馈（$\Delta I_{\text{结果与验证}}$）最廉价、最高效的手段！**
   因此，系统可以把初始前馈（$I_{\text{前馈}}$）压缩至极薄，事前无需繁琐审批，放手让模型在“边做边探”中自主收敛。
2. **极值二：无穷大成本极限（$\operatorname{Cost} \to +\infty$）—— 垂直业务的“手术台模式”**
   切换到真实生产环境（如线上支付故障排障、核心库运维、信贷放款审批）：
   动作一旦执行（如删库、切断核心网关、划扣资金），在物理与商业上是**不可逆（难以低成本回滚）**的。盲目试错的潜在破坏代价趋向无穷大（$\operatorname{Cost} \to +\infty$），直接导致盲动动作的净价值 $V(a) \to -\infty < 0$。
   这意味着：**“靠先动手做一次试试看、看报什么错再掉头”的通道在物理上被绝对封死！**
   既然不能靠事后试错获取反馈，系统就必须实行**主循环读写分离**——在只读期放开信息探查；在写操作前将前馈与 $(P+M+H)$ 预审拉满，并交由**人类 $H$ 拍板**承担责任。

### 二、 剖析“编码温室”：极简框架 PI 的 4 个基础工具何以统治代码世界？

为了看清代码世界的“温室”是如何喂饱上下文工作台的，我们可以剖析开源轻量级编码智能体框架——**PI（`pi-coding-agent`）**。

在许多业务智能体向系统塞入几十个专用工具、编写上万字提示词的时候，PI 的系统提示词不到 1000 个 Token，**默认只给大模型提供 4 个正交基础工具**，却展现出顶级的任务完成率：
1. `read`（读文件，支持指定行号与文本切片）；
2. `write`（创建新文件或全量覆盖写）；
3. `edit`（精准局部修改，要求原文本在文件中完全且唯一匹配）；
4. `bash`（在本地终端执行命令行）。

为什么 PI 靠这 4 个极其简单的基础工具，就能支撑数小时的长程自主闭环？我们顺着恒温器四节点发出 **5 个场景追问**，答案便彻底显现：

#### 1. 追问 ①（目标与存量传感器）：存量信息完整且不会静默过期
在标准代码库中，所有的业务逻辑、配置依赖、历史提交记录全部以纯文本形式静态保存在文件中（**存量事实 $\Delta I_{\text{存量}}$ 天然现成且数字化**）。更重要的是，本地沙箱具有**状态稳定性**：第 1 步通过 `read` 读入上下文的代码行，只要模型自己不改，到了第 50 步依然完全准确，**绝不会发生“上下文事实静默过期”**。

#### 2. 追问 ②（工具与对象通道）：业务对象高度统一为“纯文本文件”
软件工程的世界里“万物皆文件”，`read/write/edit` 这套以文件为中心的操作抽象打磨了数十年。此外，PI 刻意将 `read/write/edit` 从 `bash` 里拆出来，清晰体现了**用确定性程序（$P$）保护上下文信噪比**的设计：
* 独立的 `read` 限制每次读取在 2000 行内，并附上起止行号与续读偏移量，防止模型用 `cat` 一口气把十万行日志倒灌进窗口；
* 独立的 `edit` 在修改生效前，由代码（$P$）自动校验原文本在目标文件中是否唯一匹配，未读过文件凭记忆胡乱修改会被 1 毫秒拦截。

#### 3. 追问 ③（比较器）：拥有现成、秒级响应的形式化验证器（$P$）
软件工程在 AI 诞生前几十年，就已经建立了全套工业级的形式化验证器（$P$）——语法解析器（Linter）、类型检查器（Type Checker）、编译器（Compiler）与单元测试套件（Unit Tests）。模型改完代码调 `bash` 跑测试，几秒内就能获得由确定性断言（$P$）生成的客观结果：
`File "order.py", line 86, in calculate_tax: TypeError: unsupported operand type(s) for *: 'float' and 'NoneType'`
**运行事实（报错失败） + 精确位置（第 86 行） + 差距原因（浮点数与空值相乘）**被秒级打包送回上下文，直接证伪了上一轮的错误假设。

#### 4. 追问 ④（控制器可逆性）：沙箱回滚使得试错代价归零（$\operatorname{Cost} \to 0$）
底层有 Git 版本控制系统。改坏了十几个文件，一行 `git checkout` 瞬间恢复原状，使得系统能充分利用“双重控制”边做边探。

#### 5. 追问 ⑤（控制器合规性）：沙箱内试错免除外部追责
在本地开发时，模型在沙箱内部报错重试多少次，都不需要向外部监管机构审计担责，概率生成的方差被隔离沙箱安全吸收。

### 三、 走进“业务荒野”：五处信息断层与“波兰尼悖论”

现在，我们将视野转向真实的企业垂直业务场景（如电商供应链、线上生产运维、金融风控、医疗辅助），顺着同样的 5 个追问审视，会发现原本充沛的信息供给链在现实中撞上了**五处断层**：

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │                      【垂直业务荒野的五处信息断层】                     │
 │                                                                        │
 │ 1. 存量断层 (ΔI_存量)：目标模糊，大量规则留在人脑/群聊中未数字化，线上状态每秒在变  │
 │ 2. 工具断层 (Tool)：数据散落各孤立系统，业务对象未关联，工具返回无法改写决策   │
 │ 3. 比较器断层 (ΔI_结果与验证)：缺乏业务编译器 (P)，真实商业结果需数周甚至数月才揭晓│
 │ 4. 可逆性断层 (Cost)：生产写操作不可逆 (删表/划款/承诺)，无法靠动手试错探反馈 │
 │ 5. 合规性断层 (Variance)：强监管要求零容错，操作过程须法定留痕追责            │
 └────────────────────────────────────────────────────────────────────────┘
```

#### 1. 业务对象建模与工具设计的断层：为什么单表工具的 $\Delta I = 0$？
在垂直业务里，工具往往不能直接调用单表 API。
看一个电商排障场景：**“某款露营帐篷近期出现大量漏水差评，判断要不要立刻停止发货？”**
* 如果工程师按照传统 CRUD 思维，只设计了一个单表查询工具 `check_inventory()`，调用后向上下文返回：`“当前在库总库存：1000 件”`。
* 审视这笔反馈：它能指导模型决定“停不停发、停发哪一批、向谁索赔”吗？完全不能！**这笔数据无法越过决策边界改写下一步动作，对当前决策的信息价值严格为零（$\operatorname{VoI} = 0$）！**
* 要产生真正有价值的信息增量 $\Delta I$，必须将业务对象进行**跨系统关联建模**：

  $$
  \text{差评订单} \longrightarrow \text{生产批次} \longrightarrow \text{面料供应商} \longrightarrow \text{出厂质检报告} \longrightarrow \text{在库批次分布}
  $$

  由工具底层程序（$P$）自动关联计算，向模型返回结构化切面：*“90% 漏水差评集中在 B 供应商面料的第 3 批次（当前在库 300 件），其余 700 件为第 1、2 批次正常面料”*。
  **只有完成业务对象关联的工具，返回的反馈才能直接改写下一步停发与追责动作（$\frac{\partial a^*}{\partial O} \neq 0$）。**

#### 2. 深度认知突破：为什么隐性业务知识“问不出来，只能撞出来”？

面对垂直业务中初始规则不全的困境，许多架构师会产生一个看似合理的工程直觉：
*“既然出发时信息不全，那我们在动手前让大模型停下来，发起结构化提问（Plan Mode），让业务人员把规则答齐再动手，不就解决了吗？”*

然而，真实工业界实践证明：**试图靠人机问答穷尽垂直业务潜规则，在认识论上是一场空想。** 阻碍来自四大深层死结：

```text
               【为什么业务潜规则“问不出来，只能撞出来”？】
                                    │
     ┌──────────────────┬───────────┴───────────┬──────────────────┐
     ▼                  ▼                       ▼                  ▼
【波兰尼悖论】      【双向未知之未知】      【组织身份错位】    【商业博弈隐瞒本能】
知识属于默会经验，  模型不知该问什么，      坐在对话框前的人，  涉及灰色利益/特批，
处于“休眠态”，      人不知对方不知道，      非真正懂规则的高管  不可能文字留痕，
抽象提问无法唤醒    问询沦为礼貌废话        代答注入二次偏差    只会给出官方套话
```

1. **波兰尼悖论（Polanyi's Paradox）与默会知识的“情境休眠”**：
   哲学家迈克尔·波兰尼提出：*“我们所知晓的，远多于我们所能言说的（We know more than we can tell）。”*
   企业核心的业务经验大部分属于未经条文化编码的“默会知识（Tacit Knowledge）”，且高度**情境索引（Indexical）**。在抽象对话状态下，这些经验在人脑中处于完全的**休眠态**。只有在面对具体方案“撞车”的瞬间，神经元才会被惊醒反弹：*“不行！3 号仓库绝对不能放面料，因为台风季容易受潮！”*
2. **双向未知之未知（Unknown Unknowns）**：
   高质量提问的前提是提问者能定位分歧坐标。大模型对企业的微观约束一无所知（不知道该问什么）；而业务人员误以为 AI 懂得常识，或者把身边的潜规则当成了理所应当的空气（不知道对方不知道）。**双向盲区导致人机提问沦为礼貌废话，信息增量为零。**
3. **组织身份错位**：
   坐在电脑前下指令、回答模型问询的人，往往是一线初级运营或外包人员；而真正掌握供应链底牌与财务红线的资深专家，根本不可能日常坐在聊天框前当全职打标员。初级员工的盲目代答，反而向上下文注入了二次认知污染。
4. **商业博弈底牌的隐瞒本能**：
   涉及特批返点政策、大客户私下赔付底线等博弈信息，人类专家出于避险本能，**绝不可能在开放对话框中将其变成文字记录**，只会用安全的官方套话应付。

> **认识论核心结论**：
> **隐性业务知识在本质上不是“问出来的”，而是“撞出来的”。**
> 垂直业务 Agent 无法单纯依靠事前问答破局，必须转向用**具象的执行草案去撞击专家神经**，并依托延迟揭晓的真实结果对账，才能把潜规则逼出水面。

### 四、 对症下药：按环境条件在 6 大节点上动态配比反馈

既然不同场景的物理条件完全不同，我们在架构设计时，显然不需要在所有节点把反馈火力全都拉满。

根据我们在《第三篇》确立的 **6 大反馈节点** 与 **$(P, M, H)$ 三维基矢**，反馈力度的配置应当严格遵循以下原则：

$$
\text{环境与工具在哪一环已提供可靠保障} \implies \text{顺势借力，精简护栏（降成本与延迟）}
$$

$$
\text{环境与工具在哪一环存在物理短板} \implies \text{将前馈 } I_{\text{前馈}} \text{ 与 } [Fact + (P, M, H)] \text{ 火力精准配置在该节点}
$$

三个典型场景的配置对比一目了然：

| 维度与场景 | Coding Agent（草稿纸模式） | 生产环境运维 Agent（手术台模式） | 企业合规客服 Agent（精准守门模式） |
| :--- | :--- | :--- | :--- |
| **核心物理矛盾** | 环境信息充沛、沙箱试错成本 $\approx 0$，编译器提供即时 $P$ 轴反馈。**动手试错是获取信息最廉价的手段**。 | 写操作不可逆（破坏代价 $\to \infty$），无现成编译器，**线上状态每秒在变易致 Context 旧事实静默过期**。 | 无后端写操作破坏风险，核心矛盾是**防止外源政策缺失诱发幻觉，以及语言输出不可撤回的违规承诺**。 |
| **事前反馈配置**<br>*(初始 $I_{\text{前馈}}$ 与节点 ①、②)* | **静态前馈极薄，事前门禁极轻**：常规修改无需审批，仅在执行前核对文本匹配，锁定测试文件防篡改。 | **做厚静态前馈，主循环读写物理分离**：写操作前拉满**独立模型挑刺 ($M$) + 形式化预检 ($P$) + 人类授权 ($H$)**。动手前必须**重读最新线上事实**。 | **火力重在输入端外源事实**：高质量 RAG 检索知识库 + 实时订单查询，确保政策事实充分注入。 |
| **事后反馈配置**<br>*(节点 ③~⑥ 验证对账)* | **高频配置 `Fact + P`**：修改完直接跑单元测试，靠秒级代码报错 $\Delta I_{\text{结果与验证}}$ 驱动自愈。 | **落实真实物理环境对账**：下发后**持续轮询生产指标**（事实 + $P$ 阈值），直到监控指标完全恢复。 | **火力重在输出发送前门禁**：回复发出前执行**违禁词代码过滤 ($P$) + 口径审查 ($M$)**；遇超纲诉求平滑转人工 ($H$)。 |

### 五、 终局演进：改造业务土壤的“四项基建工程”

顺着信息完备性不等式：

$$
\mathbf{I_{\text{前馈}} + \sum \Delta I_{\text{环境可提供}} \ge I_{\text{目标}}}
$$

如果一个垂直企业的外部环境能提供的 $\sum \Delta I_{\text{环境可提供}}$ 始终接近于零（存量没数字化、工具提不出有效增量、动手后没有客观验证、做错了无法撤回），那么事前护栏打得再厚，系统也只能退化为“把所有操作拦下来转人工”的低效状态。

要想从根本上释放垂直业务智能体的自主权，唯一的长期路径就是**改造业务土壤本身，通过四项基建工程把业务荒野一步步改造成“业务温室”**：

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │                   【将业务荒野改造成业务温室的四项基建】                 │
 │                                                                        │
 │ 1. 规则纯文本化 (做大 ΔI_存量) ──► 隐性业务潜规则文档化与版本管理，带主动撤销机制 │
 │ 2. 业务对象建模 (打通有效 ΔI)  ──► 跨系统关联核心实体，封装读写分离的标准工具     │
 │ 3. 构建业务编译器 (沉淀 P 轴)  ──► 明确规则形式化为校验脚本，秒级返回精确差距指标 │
 │ 4. 建设仿真沙箱 (将 Cost 压向 0) ──► 提供 Dry-run 预演环境与灰度回滚，解锁双重控制│
 └────────────────────────────────────────────────────────────────────────┘
```

1. **基建一：规则文本化与版本管理（做大 $\Delta I_{\text{存量}}$，消除内源猜测）**
   把原本只存在于资深员工脑海中的业务规则、排障手册、审批边界梳理出来，转化为机器可读的结构化 Markdown 规则树或 `SKILL.md` 路书，并建立类似代码库的**版本管理与过期规则主动撤销（Revoke）机制**。
2. **基建二：业务对象关联与工具封装（打通有效信息通道，替内源减负）**
   彻底告别孤立的单表 CRUD 接口思维。以核心业务对象（如商品、用户、订单）为实体，在数据底层打通全生命周期数据关联，明确界定“工具内部确定性程序 $P$ 算到哪一步”与“返回什么结构化切面给模型决策”，让工具每次返回都能跨越决策边界。
3. **基建三：构建“业务编译器”（将昂贵的 $H/M$ 经验沉淀为零成本的 $P$ 轴脚本）**
   盘点业务专家审查方案时的明确标准（如财务平账规则、配置冲突检测、合规必含字段），将其编写成自动化的校验脚本（**形式化验证器 $P$**）。
   **业务系统每多写一个能秒级返回“某指标违反了某规则”的校验脚本，就相当于给业务环境多装了一个“编译器”，智能体自主迭代修正的能力就增强一分。**
4. **基建四：建设仿真沙箱与回滚机制（将获取信息的试错成本 $\operatorname{Cost}$ 压向零）**
   为生产系统建立“仿真预演环境（Dry-run / 影子测试环境）”，让方案先在仿真环境运行以捕获模拟结果事实；同时为真实变更建立标准的“单机灰度与一键快速回滚接口”。
   当试错代价从“灾难性事故”降为“受控灰度”时，方程二中的 $\operatorname{Cost}(a)$ 显著降低，释放给智能体的自主探索空间便随之成倍放大。

---

### 结语与引出《第五篇》的终局命题

至此，技术与工程层面的推导已经彻底贯通：
* Coding Agent 依托零成本试错沙箱与现成编译器，天然收敛于“草稿纸模式”；
* 垂直业务因写操作不可逆与信息断层，必须收敛于“手术台模式”；
* 长期破局依靠四项基建工程，将业务荒野逐步改造成可控温室。

然而，当我们真正走进一家实体企业，准备动手搭建这座“业务温室”时，技术团队往往会撞上最后一堵、也是最坚硬的一堵现实之墙：

> **在纯数字的代码世界里，存量代码文件和编译报错全是由机器软件自动生成的；**
> **但在真实的公司里，这些数据不会凭空出现在系统里——**
> **谁愿意把自己脑子里的独门经验写成文档贡献给系统？**
> **一线员工为什么宁可应付交差也不愿意认真维护多维表格？**
> **为什么技术上几天就能搭好的工具，在公司推了三个月依然无人问津？**

这正是我们在全系列的收官之作——**《第五篇：垂类落地的最后一公里 —— 为什么替行业造温室，本质是一场组织与利益工程？》**中要攻克的最深层命题。
