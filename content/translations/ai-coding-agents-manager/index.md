> 原文：[Your AI coding agents need a manager](https://addyosmani.com/blog/coding-agents-manager/)；原作者：Addy Osmani；原文发表：2026-01-08

**那些造就优秀 Tech Lead 或工程经理的核心技能，正无缝平移至 AI 辅助编程领域。一旦你开始同时并行调遣多个智能体，你就彻底从“单点调试提示词上下文”质变为了“带领一支团队”。目标清晰度、合理委派、验证闭环、异步沟通——伴随[智能体编排（Orchestration）](https://addyosmani.com/blog/future-agentic-coding/)步入主流，软件研发的工作形态正在经历深刻重塑。**

在不久的将来，我认为最高杠杆率的软件工程师看起来就像是**异步优先的技术管理者（Async-first managers）**，掌舵并驱动着一支并发运作的 AI 编程智能体小舰队。如今，智能体已经能在隔离的沙箱环境中，于后台默默交付富有实质价值的工作，并在最终回传一份可供审阅的成果——通常是一个标准的 Pull Request（PR）。我们当然依然要求严格的质量把关，但整个研发的瓶颈早已不再是“智能体能不能写出代码”，而是变成了：“**我们到底应不应该做这个功能？**”以及“**我究竟能不能高效管好手底下这群同时开工的智能体？**”

我们已经在当下的[实际工作流](https://code.claude.com/docs/en/common-workflows)中看到了这种未来的清晰雏形。Claude Code 的缔造者 Boris Cherny 近期发布的一条[技术推文](https://twitter-thread.com/t/2007179832300581177)在全网病毒式疯传，正是因为它让这种范式转移变得触手可及：他在本地终端标签页中同时挂着 5 个 Claude Code 会话，浏览器里还跑着另外 5 到 10 个，甚至还会直接掏出手机顺手起一个会话，等稍后空闲时再去检查验收。**这就是多智能体编排。**

与此同时，也有不少富有远见的工程师从更审慎客观的角度记录了这种多智能体并行的生活方式。Simon Willison 的[独到见解](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)常读常新：自然的瓶颈向来不是“生成代码”，而是“审查代码”。他依然认可并发派发任务的巨大价值，但前提是你必须对自己的精力与注意力带宽保持绝对诚实，挑选那些不会让你大脑过载的任务。我自己也一直在搭建类似的工作流，深表赞同：**其价值无比真实，但前提是你必须像做管理一样去驾驭它，而不是指望靠魔法。**

这正是心智模型的重大跃迁：**你不再是与单个智能体结对编程（Pair programming），你是在全权管理一支精干的小团队。**

这也解释了为什么那些让一个人成为优秀 Tech Lead、工程经理（EM）或技术负责人的软硬技能，会突然直接等同于“擅长 AI 编程”。因为当 AI 编程走入规模化并发阶段，它就不再是一个写提示词的微观技巧问题，而是一个货真价实的**管理学问题**。

## 全新工作流的心智模型

在我的脑海中，有两条并行运转的工作轨迹。

第一条是**本地高触达、必须保持[人在回路（Human-in-the-loop）](https://addyosmani.com/agentic-engineering/human-in-the-loop/)的深度会话**。专用于架构设计决策、棘手的高难重构、微妙的产品体验权衡、充满歧义的需求澄清，以及任何由技术品味与主观裁决主导的事务。在这些场景下，你与智能体实时结对，随时临机纠偏，并拍板那些高度依赖智能体未曾掌握的宏观上下文的关键决断。

第二条是**在云端或后台完全异步运行的独立会话**。专门承接边界清晰、目标收敛的确定性任务：直截了当的功能开发、拥有既定范式的代码迁移、单元测试批量生成、文档补全更新、依赖库版本升级、小型 Bug 修复以及目标明确的局部重构。你把任务派发出去，随后毫无心理负担地上下文切换去干别的事，等它们跑完再回来集中审阅交付物。

这种划分与当今现代开发者工具的演进脉络完美吻合。云端智能体（如 GitHub Copilot Agent、Claude Web、Codex、Jules 等）明确被定位为可并行化、运行在[安全沙箱（Sandboxed）](https://addyosmani.com/agentic-engineering/sandboxing/)环境中的独立任务单元，能够自主编写代码、执行命令并提交待审阅的变更。

GitHub 的 Copilot 编码智能体同样采用了这套产品框架——它是一个完全异步的后台智能体，会自动开启一个草稿 PR（Draft PR），在后台静默施工，随后主动申请代码审查，允许你在讨论串中留评审意见并让其继续迭代。各家平台都在加速迈向支持同时调度多智能体的“中央任务控制大盘（Mission Control）”，而非仅支持单一实例。GitHub 甚至预先演示了名为“Agent HQ”的统一控制平面，用于在一个中心面板中协调调度来自不同第三方的多个编码智能体，甚至支持让多个智能体针对同一项任务并行开工，以便人类横向比选最优解。

因此，摆在我们面前的核心问题，正在从“哪家大模型写出的代码最好？”转变为：“**我究竟能否像管理一支高绩效研发团队那样，把它们妥善组织起来？**”

正是在这里，管理者的核心素养开始大显身手。

## 为什么管理者的技能让你成为更优秀的 AI 开发者

*(我曾在一本关于[高效工程管理技能](https://leanpub.com/effective-software-engineering-management)的书中对该领域展开过系统性探讨)*

当你真正带过人类工程师团队时，你会通过一次次交学费深刻明白一个道理：**最终产出物的质量，早在最上游就已经被决定了。** 模糊不清的诉求、界定不清的责任归属、缺乏明确的验收标准（Definition of Done）、以及缺失及时的反馈闭环，必然会导致团队陷入无休止的内耗与返工。当你的“团队下属”换成了一批执行速度飞快但缺乏人类常识的非人智能体时，这一定律不仅依然成立，甚至被放大了数倍。

Anthropic 面向 Claude Code 撰写的最佳实践指南中对此说得无比透彻：**前期在需求定义上的具体性，能够实质性提升最终的成功率，并极大减少中途纠偏的折腾。** 即便写在工具文档里，这依然是地地道道的管理学黑话。

以下四项管理技能的平移最为直接有效。

### 1. 清晰界定任务范围：写立项简报，不凭玄学感觉

如果说模糊不清是杀死智能体执行效率的头号杀手，那么你的本职工作，就是将脑海中粗糙的想法轮廓，提炼成一份能够经受住真实编码落地的**立项简报（Brief）**。这正是优秀管理者日常在做的事：将宏观意图转化为切实可执行的具体任务。

一份实用的智能体立项简报应涵盖：
- **预期成果**：当任务彻底搞定后，系统应达到何种理想状态；
- **业务上下文**：本次修改位于代码库的哪个模块，现有已存在哪些可参考的范式；
- **边界约束**：性能指标、安全规范、API 契约、依赖限制、代码风格约定；
- **非目标（Non-goals）**：明确列出哪些事情本次**坚决不干**；
- **验收标准（Acceptance criteria）**：具体可验证的硬性检查（如哪些测试必须跑通、接口必须表现出何种行为）；
- **集成边界提示**：哪些文件绝对禁止擅自改动、系统接缝应该留在何处；
- **验证方案**：我们该如何切实证明它确实做对了。

这正是拿到一个干净利落的高质量 PR，与拿到一千行没人敢碰的烂摊子代码之间的分水岭。

有两个小技巧能让立项简报的产出变得格外轻松：
第一，**明确指引现有范式**——Anthropic 的指南明确建议直接在指令中点名希望智能体效仿或更新的具体文件路径，让其牢牢锚定在真实存在的成熟代码约定上，而非任由其自由发挥捏造新风格。
第二，**将长期稳定的规则沉淀在智能体随时可查的固定位置**。如今这已成为行业通用标准，OpenAI 的 Codex 官方文档详述了如何通过 `AGENTS.md` 文件为智能体确立关于测试命令、代码规范检查规则、依赖管理策略以及文档要求的持久化预期。如果你曾经带过新人入职熟悉代码库，你一定会对这种感觉无比熟悉：在他们动手写下第一行代码之前，先给他们一份清晰的地图、团队守则以及验收标准。

### 2. 委派的艺术：厘清全权放手 vs 亲自把关的边界

面对智能体，一个极具诱惑力但代价惨重的陷阱，是过度委派了那些原本属于人类专属职责的环节：产品真实意图的敲定、API 设计的取舍权衡、系统架构边界的划分、以及长期维护性的考量。

OpenAI 在其《AI 原生研发团队指南》中，将软件开发生命周期的权责精妙拆解为三层：**委派（Delegate）、审查（Review）、全权兜底（Own）**。即便在他们最为乐观的技术展望中，工程师也依然对最终决策与验收把关拥有不可推卸的所有权，尤其是在面对充满模糊性的棘手难题时。

这与智能体编排完美对齐。
- **有些工作你可以彻底全权委派**：拥有详尽严密 Spec 的纯机械编码实现、样板代码重构、配有严密测试把关的用例生成、接口文档补齐、以及低风险的日常维护杂活。
- **有些工作你应当委派，但必须设置关键检查点（Checkpoints）保持人在回路**：任何触碰公共共享接口的修改、任何极易引发合并冲突的代码、任何暗藏微妙产品边界异常的逻辑、以及涉及数据表迁移的改动。
- **而有些工作你坚决不能委派，或者仅委派其去探索备选方案**：系统核心架构设计与全新顶层抽象的定义、极度仰仗个人技术品味的大范围交叉重构、关乎“我们到底该不该做”的产品核心决断，以及关乎安全底线或隐私合规的关键设计。

这与在人类团队中分配任务时的思考肌肉完全一致：你必须时刻清醒地决断谁来负责什么、给予多大程度的自主权是安全的，以及在代码彻底固化之前你希望在哪个关键节点踩下刹车亲自过目。

### 3. 构建早期验证闭环，在最上游截击隐患

带过团队的管理者都明白：最令人心痛的时间浪费，莫过于在流程最后阶段才发现呈上来的成果从根子上就是低劣残次品。你极度渴望早期的反馈循环与质量关卡。智能体也是完全一样的道理——唯一不同的是，智能体能够以惊人的速度批量制造低劣产出。

**自动化验证闭环是破局的终极钥匙**，业界顶尖的工具团队正纷纷将这一理念烙入产品指引之中。Anthropic 的[最佳实践指南](https://www.anthropic.com/engineering/claude-code-best-practices)明确提出同时运行多个 Claude 实例的范式：一个负责编写代码，另一个通过代码审查与自动化测试负责核验，如同两位职责分离的工程师在紧密配合。OpenAI 对 Codex 的定位同样强调工具链闭环：执行命令、跑通测试、自我纠错迭代至全绿状态，最终再提交 PR。

在工程实操中，一个严密的验证闭环应包含：
- 强制要求智能体在结束前全量运行测试套件（或受影响的测试子集），并将执行回显输出完整附在最终汇报中；
- 强制要求改动模块的代码规范检查（Lint）与类型检查（Typecheck）必须全绿通过；
- 强制要求但凡涉及行为逻辑变更，必须同步增加或修改对应的自动化测试用例；
- 强制要求在交付时呈上一份结构化的“PR 交付物数据包（PR packet）”——涵盖改动总结、为何采用此技术路线、涉及文件清单、测试执行方案与跑分结果，以及潜在风险或后续待办。

如果你希望更进一步，可以采用成熟的**双智能体协同范式（Two-agent pattern）**：智能体 A 负责具体编码实现，智能体 B 专门负责从正确性、代码风格、边界异常以及漏写测试等维度展开批判性审查；随后由智能体 A（或另起一个干净的智能体 C）吸收审查意见并重新跑通全套验证。这早已不是天方夜谭的理论推演——Anthropic 在官方指南中已将其作为极力推崇的标准进阶工作流。

管理者的直觉在此处同样不可或缺：你绝不仅仅是在检查代码能不能编译通过，你更是在审视它是否契合团队既定约定、日后是否具备可维护性，以及它是否真正忠实落实了最初的业务意图。

### 4. 异步汇报机制：像对待直属下属（Reports）一样要求智能体

如果你同时在后台并发跑着十几个智能体，你根本不可能有精力逐一翻阅它们那冗长繁杂的对话流水去排查刚才究竟发生了什么。你需要轻量、可固化复用的结构化汇报。这正是将**跨时区异步管理体系**无缝应用于智能体的最佳场域。

确立清晰的汇报节奏与卡点机制：“如果你在 15 分钟内未能取得实质性进展，立刻停下并主动向我汇报当前阻塞点。” 要求其以高度可预测的标准格式提交状态：
- 刚才改动了什么？
- 接下来准备做什么？
- 当前存在哪些潜在风险或阻塞卡点？
- 你需要我为你提供什么支持与决策？

这听起来微不足道，但这正是确保并发任务不至于在暗中偏离航向、而你又无需像直升机父母一样每分每秒在旁盯盘的核心秘诀。如果需要一个生动的现实类比，管理一群并行开工的智能体，极其类似于跨时区带领一支完全分布式的跨国工程师团队：**你在最前端重度倾注清晰度，日常沟通重度依赖结构化文字简报，并把你宝贵的实时注意力，死死保留给最关键的架构裁决与排障疏通。**

## 那些绕不开的真实硬伤（它们全都是管理问题）

### 合并冲突以乘法级速度激增

让并行的多个智能体同时触碰相邻的代码区域，其混乱程度无异于让 5 位人类工程师在完全缺乏沟通的前提下强行修改同一个文件。这绝不是 AI 工具底层出了故障，而是**边界划分与任务拆解的彻底失败**。解法与人类团队的协同如出一辙：用心划定任务边界、隔离工作空间，并预先定义好清晰的接口缝隙。

在工程实操层面，这通常意味着让智能体在完全物理隔离的工作目录或独立分支中开工。[Git Worktrees（工作树）](https://git-scm.com/docs/git-worktree)在此处堪称天作之合——它允许你基于同一个代码仓库在本地同时检出多个互不干扰的独立分支，每个分支独占一个专属物理目录。Claude Code 官方文档明确推荐使用 Git Worktree 来支撑并行会话，确保各个实例之间绝不发生物理写冲突；Anthropic 的最佳实践更给出了基于 Worktree 搭配“一个终端标签页对应一个工作树”的标准化实操手册。即便使用云端 Agent，底层原则也是完全相通的：独立的分支、小步快跑的小型 PR，以及对各个业务模块极其清晰的归属划分。

我最推崇的三条边界红线全部直接借鉴自人类团队协作：
1. **一个智能体只负责一个独立的 PR**，严禁搞跨多智能体的大杂烩巨型 PR；
2. 如果预判两个智能体很可能会修改同一批文件，立刻**重新设计任务切分维度**；
3. 共享的核心底层接口必须由人类主导的第一个前置 PR 率先敲定并合入，随后智能体们再基于这条明确确立的接缝分别向上搭建。

### 技术品味与“到底做不做”，成为真正的终极瓶颈

当把一个功能做出来的边际成本变得前所未有地廉价时，你就会不可遏制地开始什么都想做。这种感觉在初期会让你产生无所不能的高产幻觉，直到某一天你猛然惊醒：你的产品已经彻底沦为了堆满各种杂乱边缘特性的百宝垃圾箱。

这是这场技术巨变中最少被人严肃讨论的暗面：**AI 从未消弭对人类判断力与审美眼光的需求，相反，它将人类技术品味的价值推向了前所未有的至高王座。** 拷问“我们到底该不该做？”，正在变得远远比纠结“我们能不能做出来？”重要得多。

这本质上完全是一项高级管理能力：业务优先级排序、敢于说“不”的决断力、对成功的精确定义、开展轻量小步快跑实验的敏锐度，以及极其迅速果断掐死愚蠢方案的魄力。

如果你希望将这套机制工程化落地，请从敏捷管理学中借用两套黄金工具：
第一，**在制品上限（WIP Limits）**：严格限制你允许同时处于活跃状态的并发智能体流水线总数，防止你自己被随之而来的海量代码审查活活淹没（这正是 Simon Willison 所疾呼的核心痛点）。
第二，**叫停与止损标准（Kill Criteria）**：在动手构建任何新特性之前，先在纸面上清晰写明：一旦触发哪些负向信号，我们将毫不犹豫地彻底叫停并废弃这项需求。

## 享受这趟旅程（为什么这些付出物超所值）

这种“随走随派发（On the go）”的委派效应是无比真实且令人上瘾的。当后台智能体能够完全自主基于代码仓库开工、并在完工后捧回整整齐齐可供审查的成套修改时，你整个人的心智模式会瞬间从“记个待办 Todo 以后有空再写”，一跃飞升为“**立刻把这个点子就地跑起来**”。

我日常的个人开发配置是：常驻 4 到 5 个后台智能体处理中低复杂度的机械任务，同时我自己保持人在回路，在另外 3 到 5 个本地高触达会话中专注于核心架构设计与微妙的产品细节。能够在移动端随时随地下达委派指令，彻底重构了我的个人创意闭环：**闪念点子 → 快速生成实现草稿 → 人工深度审阅 → 闭环迭代交付。**

当你在心底筑牢了质量底线并跑通了整套流程时，整个过程会带来极其强烈的智识愉悦感，因为你的创新闭环被无限拉近压实了。但请务必牢记：**唯有当你像做管理一样去严肃对待多智能体编排、而非将其视作魔术杂耍时，这种愉悦感才可能持久。** 你必须对自己多任务并行与频繁上下文切换的精力带宽保持绝对清醒与诚实。并不是每个人都需要像 Boris 那样在屏幕上同时狂飙 10 到 15 个并发智能体。他的工作姿态更多是作为一个展现工程极限可能性的极端标杆存在，而非强加给每个人的日常硬性指标。

## 一套极简的多智能体编排操作系统

如果你想在日常工作中锤炼一套立竿见影、可复用的极简工作循环：

1. **像管理者一样审慎规划（Plan）**：撰写涵盖明确产出预期、边界约束与验收标准的立项简报（Brief）；
2. **像调度官一样解耦派发（Spawn）**：将任务分发给拥有物理边界隔离的并发智能体；
3. **推行异步监控（Monitor）**：建立轻量结构化汇报机制，快速排障解卡，避免任务中途无谓内耗；
4. **强力推行极限验证（Verify）**：硬性校验测试套件、规范检查、结构化交付数据包，并在必要时引入独立第二智能体交叉审查；
5. **严密把关最终合并（Integrate）**：按照深思熟虑的依赖次序依次合入，警惕破坏模块边界；
6. **持续开展团队复盘（Retro）**：将踩坑教训反哺更新至你的 [`AGENTS.md`](https://developers.openai.com/codex/guides/agents-md/) 与任务核对清单中，确保智能体舰队在下一次起航时更加聪明敏捷。

对于绝大多数一线开发者而言，最舒服的黄金甜区，通常是**身边常驻几个后台智能体处理中低复杂度的杂活，而你自己作为最高裁判坚守人在回路，专注于核心架构与产品神韵**，清醒地维持在自己大脑能够从容承受的上下文切换舒适区之内。

这就是现代多智能体编排（Orchestration）的全部真相。而通往这一境界最快的高速公路，正是去虚心掌握那些让一个人成为顶尖工程领导者的同一套核心能力：**极其清晰的目标表达、艺术般的委派分权、严密的反馈验证闭环，以及卓越的异步沟通素养。**
