> 原文：[How an Anthropic Japan BDR runs his day with a fleet of Claude agents](https://claude.com/resources/articles/how-an-anthropic-japan-business-development-representative-runs-his-day)；原作者：Shahboz Ibragimov；原文发表：2026-10-16

作为 Anthropic 日本团队的业务拓展代表（BDR），我的日常工作是向日本各大企业展示 Claude 如何帮助他们简化并自动化繁琐的工作流。但在今年早些时候，我自己的大部分工作却依然停留在原始的手工阶段：每天早上一坐下来，我都要花上两三个小时对新线索进行分拣流转和资质审查，然后绞尽脑汁撰写一封封日文或英文的跟进邮件；剩下的一点可怜时间，还要忙着更新 CRM 系统——而且往往还拖延了一两天进度。

而现在，我的智能体舰队会在我开始一天工作之前，就默默替我准备好绝大部分产出，我只需要负责把关审阅即可。

我最初搭建的第一个 Claude 自动化流程其实相当简陋，但它确实管用：我一次只把一小块工作交给 Claude，纠正它做错的地方，并将这些修改记录保存下来。日积月累，这套流程逐渐演变成了一组各司其职的智能体，覆盖了我日常工作的各个固定环节。

消息很快在团队内部传开了，同事们纷纷跑来向我索要提示词和技能配置，希望也能搭一套自己的。但当时我能给他们的只有一个压缩包，里面塞满了我的技能脚本以及知识库里的几份 Markdown 文件。他们必须手动把这些文件上传到 Claude，然后还要回答一整轮复杂的初始化配置问题，系统才能勉强跑起来。我自己这边也渐渐吃不消了——每个智能体都对应着一个技能、一项定时任务以及一个本地共享文件夹；由于我习惯在随便打开的某个对话窗口里随手指挥 Claude 修改技能，结果导致同一个技能在各个不同的聊天上下文中被改来改去，追踪演进变得一团乱麻。

我迫切希望能够在一处集中的地方对每个智能体进行统一定义，并清晰查阅每一次修改的完整历史。于是，我决定尝试 [Claude 托管智能体（Claude Managed Agents）](https://platform.claude.com/docs/en/managed-agents/overview?utm_source=chatgpt.com)（测试版）——这是我们在 Claude 平台上推出的端到端托管智能体基础设施。

起初我有些顾虑。官方文档里通篇都是调度计划、工具集成和凭据保险库等技术术语，而我只是一名销售代表，潜意识里总觉得托管智能体是专门给有能力搭建并运维复杂架构的专业开发者准备的。但我最终还是硬着头皮试了试，因为我的智能体原本就已经能跑了，我只需要把它们搬个家而已。

事实证明，我根本不需要成为一名程序员。我只需用大白话清晰描述每个智能体的具体职责，Claude 就会自动为我写出几段简短的配置脚本，我在笔记本电脑的终端里顺手一敲就完成了部署。（如果你打算从零起步，控制台里还贴心提供了开箱即用的[快速入门](https://platform.claude.com/workspaces/default/agent-quickstart?utm_source=chatgpt.com)智能体模板。）自那以后，我再也不需要操心任何底层基础设施的运维。

在这篇文章中，我将深入复盘我是如何设计并验证这支智能体舰队的雏形、为什么最终决定将它们全面迁移至托管平台、Claude Tag 如何无缝接管常规流程之外的突发复杂任务、这套体系如何彻底重塑了我的一周工作节奏，以及我想给那些同样希望借助智能体摆脱单调手工作业的销售同行们的一些真心建议。

## 设计我的智能体舰队

我将自己的全流程工作拆解分配给了多个智能体，并赋予每个智能体单一、清晰的职责。遵循“单一职责原则”让每个智能体的行为都极易推演和排查，尤其是在出现偏差时能一目了然。我还为每个智能体都取了一个日语名字，因为它们日常主要处理日文业务。在内部，我把它们统称为 **Nakama**（在日语中意为“伙伴”、“同伴”，即与你并肩作战的战友舰队）：

- **Furiwake（振分 / “分流”）率先启动**：每天清晨扫描入站线索队列，将每条新线索精准派发给团队中合适的销售代表。它会统筹权衡线索数量、优先级，并检查当天谁在岗值班，确保在我们开启一天工作之前，每一条线索都已明确了负责人。每次运行结束，它都会在专门的 Slack 频道发送一份详尽的移交晨报（录入了哪些线索、分别分配给了谁），让我对任务交接一清二楚。
- **Sabaki（捌 / “分拣处置”）负责分诊属于我的线索**：它会对分配给我的线索进行资质初审，按照预设标准分类，并执行对应的下一步行动（例如针对自服型客户拟定指引回复，或针对重要潜客定制专属的首封沟通邮件）；随后在 Salesforce 中更新该线索的记录，并草拟第一封破冰邮件。草稿的用词和论据全部提取自 *Nakama* 舰队共用的共享知识库——这是一处所有智能体都能自由读写的[记忆存储区（Memory Store）](https://claude.com/resources/articles/claude-managed-agents-memory?utm_source=chatgpt.com)（后文有详述）。
- **Henji（返事 / “回复”）每小时扫描收件箱**：敏锐捕捉客户发来的待回复邮件，并根据上下文语境自动起草日文或英文的回复草稿。它同样汲取了与 *Sabaki* 相同的知识库沉淀。我只需审阅、微调并点击发送。
- **Shoudan（商谈 / “商机维护”）负责同步商机**：它持续读取近期的客户互动记录，并自动将关键进展同步推送到 [Salesforce](https://claude.com/resources/articles/salesforce-in-claude?utm_source=chatgpt.com) 中，彻底告别了手动录入数据的繁琐。
- **Nokori（残 / “收尾复盘”）在每天下班前准时运行**：它会自动扫描我当天的日程日历，通读挂载的会议录音转写文本，对每场会议提炼出核心纪要，并依托相同的知识库草拟后续跟进邮件。

每个智能体都按照既定的[时间计划](https://claude.com/resources/articles/whats-new-in-claude-managed-agents?utm_source=chatgpt.com)有条不紊地运行。此外，舰队中还有第六个关键角色——**Nakama 的协调者（Coordinator）**，它相当于整个智能体舰队的“运营主管”。它的职责是在两次业务运行的间隙，动态更新各个智能体的行为指令以及全局共享知识库。每当我想调整某个智能体的工作方式时，我只需在 Nakama 的 Slack 专属频道里用自然语言随手写出我的要求。为了安全起见，全团队只有我拥有向该频道发布“修改智能体指令和系统提示词”的权限。协调者大约每隔 15 分钟扫描一次该频道，提取我的最新指令并在后台完成自动化配置更新。

## 在 Claude 中快速验证原型

起步阶段其实完全不需要立即上马托管智能体。我最初是在原生的 Claude 桌面/网页环境中完成了整支舰队的雏形验证，当时用到的组件非常朴素：

- **每个智能体对应一项技能（Skill）**：封装了单一任务的具体操作指令；
- **每项技能对应一个定时任务（Scheduled Task）**：免去我手动逐一触发的繁琐；
- **笔记本上的一个共享文件夹作为知识库**：所有技能都会将学到的新知识沉淀回这个文件夹——比如它最初草拟的邮件与我最终发送版本之间的措辞差异，以及在调研过程中顺手查到的最新事实。

当迁移到 Claude 托管平台后：原来的“技能”升级为了智能体的“系统提示词”；原本本地的定时任务无缝转化为[部署层面的原生调度（Scheduled Deployments）](https://platform.claude.com/docs/en/managed-agents/scheduled-deployments?utm_source=chatgpt.com)；而本地共享文件夹则平滑过渡为了云端统一的“记忆存储区（Memory Store）”。如今我依然用大白话提出修改要求，但一切都能集中在一个 Slack 频道内完成，而且对智能体指令的每一次调整都会被记录为一个全新的版本，使每个智能体都拥有一部清晰带编号的配置演进史。我强烈的建议是：**不妨先在 Claude 中轻量起步，一旦智能体多到你凭肉眼难以轻松掌控时，再果断迁移到托管智能体平台。**

## 借助 Claude 托管智能体运转舰队

迁移到托管平台后，有三项能力对我的日常工作流产生了决定性的影响：

### 1. 智能体完全在云端自主运行
智能体严格按照各自的排期运转，无论我的笔记本是开是关，甚至在离线断网状态下也能全天候执行。调度计划本身就是智能体部署配置的一部分。在以前，我虽然也能在本地 Claude 客户端里给技能设排期，但那些定时任务终究只是绑定在我个人机器上的本地进程。而在托管平台上，我在控制台界面里直接配置好执行周期和时区，它就与部署好的指令和工具紧密绑定在一起，完全不需要我在旁边单独挂着复杂的 Cron 定时脚本。

如果某次执行出现了偏差，我只需在控制台里打开该次会话，就能清晰复盘智能体采取的每一个具体步骤。更棒的是，当我在调试某个智能体的新配置时，线上按时跑的定时任务依然会稳定调用当前正式发布的稳定版本，半成品的试验修改绝对不会误伤明天的正式业务。

### 2. Nakama 共享同一套记忆，并在人类的微调中自我进化
所有智能体都在同一个[记忆存储区](https://claude.com/resources/articles/claude-managed-agents-memory?utm_source=chatgpt.com)中进行读写，这意味着任何一个智能体学到的新认知，都能立刻被全舰队共享。智能体会自动对比它们草拟的初稿与我最终点击发送的邮件正文，将两者之间的所有细微出入，总结沉淀为一条条关于“我更习惯如何遣词造句”的风格备忘录；它们还会将从内部文档和官方网站上检索到的最新业务知识一并存档。我在修改 Henji 草拟的一处措辞时，Sabaki 和 Nokori 也会在同一个记忆库中同步吸收，从此再也不会犯同样的毛病。

### 3. 凭据统一交由托管保险库按需赋权管理
我的智能体舰队需要访问我的工作邮箱以及公司 Salesforce 核心数据库，鉴于其中包含高度敏感的客户沟通细节与公司商业记录，我必须将这些访问权限牢牢锁定在安全边界内。所有登录凭据全部保存在[托管凭据保险库（Managed Vaults）](https://platform.claude.com/docs/en/managed-agents/vaults?utm_source=chatgpt.com)中，严密保护着诸如 OAuth 访问/刷新令牌、API Key 以及个人访问令牌（PAT）。每个智能体在部署时仅被赋予其工作必需的最小凭据子集，智能体本身在运行时永远接触不到明文密钥，而且我随时可以一键吊销任何授权。

## 将疑难升级环节交由 Claude Tag 协同接盘

对于 Nakama 产出的大多数标准化成果，我通常只需在收件箱里扫一眼草稿并点击发送，或是顺手浏览一下已经更新好的 Salesforce 记录即可。但总有一些非标事项需要复杂的后续推进——比如梳理客户的版本升级路径、制定复杂的采购审批链路，或是将突发问题升级流转给其他兄弟团队。

面对这类棘手情况，智能体绝不会原地卡壳等待。它们会将任务直接流转给处于公测阶段的 [Claude Tag](https://www.anthropic.com/news/introducing-claude-tag)。Claude Tag 相当于把 Claude 变成了一位进驻我们 Slack 工作空间的“真人同事”：任何加入了该频道的员工（甚至是我麾下的某个智能体），都可以直接在讨论串中 @Claude 发起求助，Claude 就会像一位随叫随到的资深协作者一样在讨论串中接单并展开推进。在工作空间配置妥当后，团队没有任何额外的学习成本——你就像在 Slack 里艾特一位真人同事那样自然地召唤 Claude。

在我的实际日常中，这个协作闭环是这样运转的：某个智能体把需要跟进的事项发到 Nakama 的专属 Slack 频道并 @Claude；Claude 迅速通读整个上下文，检索适用的内部政策与条款规则，清晰梳理出几种可行选项，并草拟好所需的沟通文本；只有在某些关键节点确实需要我把关或签字时，它才会精准 @ 我介入。

如果某件事需要先等待客户或外部团队的答复，Claude 会极其贴心地为自己设置一个未来某一天的定时复查提醒。在下方的真实讨论截图中，Claude 自主设置了一个周二的定时器，届时会自动检查客户是否已经回信、商务条款审批（Deal Desk）工单是否已经出具答复；当提醒时间到达时，Claude 会主动在这两条线索中进行查验，并在原讨论串中同步最新进展；如果发现某一方进度拖延需要催办，它还会自动草拟好得体的催办话术，并 @ 我确认发送。

## 我的工作周发生了哪些颠覆性改变

现在，入站线索回复的大部分草拟以及 CRM 系统的繁琐录入都在无需我亲自动手的情况下有条不紊地完成，我的核心角色彻底转变为了：**专注于那些真正需要人类商业洞察与审慎判断的决策环节**。

一份清晰成文的规则边界明确了各个智能体的行动红线：涉及核心商务报价争议、敏感战略客户或是表述极其模糊的非常规诉求，系统都会自动流转到我案头。由 Henji、Sabaki 或 Nokori 草拟的每一份邮件初稿，都会在正文最顶端附带一段言简意赅的上下文摘要。这让我根本不需要吃力地翻阅十几封历史来回邮件去重新理清前因后果——我扫一眼核心摘要、确认无误、做几处画龙点睛的微调，即可自信发送。

而省下来的这大把宝贵精力，被我全部倾注到了那些智能体目前依然无法胜任的高价值领域：与核心潜客进行推心置腹的深度面对面交流、打磨更具前瞻性的出海拓展策略、推进跨部门的战略级协同项目，以及手把手协助团队里的其他销售战友搭建属于他们自己的智能体舰队。

## 精心设计：让智能体集群的运转极致高效

定时运行的智能体每天都在风雨无阻地执行任务，无论你是否在盯着屏幕看。因此，一旦系统架构设计不合理，资源浪费就会在账单成本和运行稳定性上迅速滚雪球。在实际操作中，最容易踩的坑莫过于：不停地在既有指令上往上层层叠床架屋（而不是及时重构清洗）、给智能体塞入远超其任务所需的冗余上下文，以及不问青红皂白地把所有琐碎任务统统扔给最昂贵的大模型并拉满最高推理强度。

让这支舰队始终保持极高性价比的关键，全赖于整套系统的底层架构设计：

- **每个智能体职责专一**：指令始终高度精简聚焦；
- **定时唤醒、执行完毕即休眠**：绝不在后台空转消耗 Token；
- **共享统一记忆库**：一人纠错、全员受益，杜绝重复踩坑。

另一个决定性的因素在于**模型分层选型机制**。一旦某个智能体的职责被拆解得足够标准化，它往往根本不需要调用最顶级的模型：

- **Furiwake 和 Shoudan**：由于严格按照固定的结构化规则运转，直接选用性价比极高、运行飞快的轻量模型 **Claude Sonnet**；
- **Sabaki、Nokori 以及协调者**：由于任务需要更高级别的语境理解与综合权衡，分配给旗舰级的 **Claude Opus**；其中“协调者”最需要顶级智商，因为它负责动态修改其他智能体的提示词代码，稍有差池就会殃及全盘。
- **高频运行的 Henji 的两全之策**：由于每位客户的发问千差万别，Henji 需要极高的情商与洞察力，但它在整个工作日内每小时都要运行一次，是全舰队调用最频繁的角色。如果每次都无脑调用 Opus，账单开销将极为高昂。为此，我在托管平台中巧妙采用了<strong>“顾问策略（Advisor Strategy）”</strong>：Henji 默认运行在成本极低的 Sonnet 模型上；只有当它在处理过程中遇到了自身把握不准的复杂决策边界时，才会向 Opus 这位“资深顾问”发起求助。作为顾问的 Opus 会通读 Henji 目前的处理进度，发回针对性的行动方案、纠偏建议或终止指令，随后由 Henji 顺畅完成草稿撰写呈递给我审阅。
- **灵活配置推理思考深度（Effort Level）**：除了模型规格，我还针对不同角色单独调配其思考深度参数，只有在面对像 Henji 回复这种极度考验复杂逻辑推理的场景时，才定向拉高思考深度。

## 我的三条核心实战心得

如果让我给每一位想要打造自己专属智能体舰队的朋友分享几条经验，我会总结为以下三点：

1. **不必每一次都死磕完美的详细提示词**：用大白话把任务描述清楚，让 Claude 先去草拟；你在实际输出中动手修正它的偏差，并让系统把这个修改范式固化下来。
2. **知识库的沉淀远比提示词的长度重要得多**：每一次人工微调和过去的成功交互，都要被结构化保存在所有智能体共同的读写区中。让 Claude 从动态记忆中汲取真实上下文，而不是在系统提示词里堆砌冗长死板的条条框框。只用了几百次极低成本的“草拟-修正-沉淀”循环，智能体写出来的邮件口吻就已经和我本人的语言风格如出一辙。
3. **更早、更大胆地给 Claude 放权**：起初，我总是牢牢攥着那些我认为“离开我绝对不行”的任务——比如手动维护知识库、亲自逐字修改每个智能体的配置指令。但当我彻底学会放手后，一切运转得反而更加丝滑。如今，智能体会自主将学到的经验沉淀入知识库，而协调者能完美理解我的自然语言意图并替我修改全员指令。回顾过往，我才意识到自己当初在那些完全可以放手信任智能体的事情上，显得过于保守了。
