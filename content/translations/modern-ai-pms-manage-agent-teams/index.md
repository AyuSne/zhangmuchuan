> 原文：[Modern AI PMs manage AI Agent teams, not prompts](https://x.com/Saboo_Shubham_/status/2017801963195220401)；原作者：Shubham Saboo（@Saboo_Shubham_）；原文发表：2026-02-01

![插画：一位产品经理在深夜的办公室里被一群红色小智能体围绕，屏幕上开着多个任务面板](https://pbs.twimg.com/media/HABwvsbbEAElzeF?format=jpg&name=large)

Claude Cowork 从一个灵感雏形到正式发布，仅仅用了 1.5 周。

这是一支极度精简的微型团队，每位成员日常在后台同时并发跑着 4 到 8 个 Claude Code 实例。

整个团队完全不亲自动手手写一行代码。他们做的事情，是直接指挥这批智能体替他们编写全部代码。

这正是时代的范式大跃迁：**从亲力亲为走向统筹指挥，从埋头写码走向统领舰队。**

Boris Cherny 最初把 Claude Code 当作一个业余项目开发。这是他每天的真实工作流：终端常驻 5 个 Claude 标签页，编号 1 到 5；浏览器端再常驻 5 到 10 个实例；全天候多线程并行跑；一旦哪个 Claude 需要人类输入指导，系统通知便会弹窗提醒。

在短短 30 天内，他合并了 259 个 PR——**纯手工编写的代码为零。**

如今，我几乎在随处看到这种震撼的生产力范式。许多先锋构建者（比如 [Bhanu](https://x.com/pbteja1998/status/2017495026230775832)）同时调度 10 多个智能体，像一支真正的高效人类团队一样严密协同：调研智能体为内容智能体持续输送炮弹；代码智能体静候设计决策落槌；定时任务在清晨 6 点准时唤醒智能体，有条不紊地铺垫一整天的工作。

![Mission Control 控制台截图：11 个智能体在线，任务队列分收件箱、指派、进行中、评审、完成五列，右侧是实时动态](https://pbs.twimg.com/media/HABX86TaQAAAJwF?format=jpg&name=large)

最顶尖的一批构建者，早在几个月前就彻底告别了“单兵智能体”时代。

在我之前写的一篇文章中，我曾探讨过[产品经理如何从需求翻译者转变为问题塑造者](https://x.com/Saboo_Shubham_/status/2008742211194913117?s=20)。当智能体能够吃透一个表述清晰的问题并直接交付出可运行的代码时，产品规格说明书（Spec）本身就成了最终交付的产品。

那一篇讲的还是单智能体协同。而今天这篇文章，探讨的是**如何统御由智能体构成的庞大舰队**。

我负责维护斩获 9.1 万多 GitHub Star 的开源项目 [Awesome LLM Apps](https://github.com/Shubhamsaboo/awesome-llm-apps)，里面沉淀了 100 多套智能体实现。每周我都在打造新智能体，并在第一线近距离观察业界高手的最新打法。

当下最核心的命题早已不再是“我能不能靠智能体提速”，而是：

**“你究竟能够同时统筹调度多少个智能体协同作战？”**

## 从意图编程到舰队统帅

与单个智能体打交道，就像身边跟了一个能力极强的实习生：你向它交代上下文，它动手执行，你审阅把关，随后反复迭代。这种体验确实很强大。

但它在本质上依然是**单线程串行**的——你个人的注意力是全链路最脆弱的单点瓶颈。

**而“舰队模式（Fleet Model）”彻底颠倒了这一逻辑。**

你不再是对着一个智能体发号施令然后苦苦干等；你是在指挥一个由高度专业化分工的智能体构成的矩阵——调研在推进的同时，文案在同步起草，底层代码也在并行编写。

你的心智模型彻底从“并肩协作者”跃迁为“全军指挥官”。

几个月来我一直在为此疯狂试验。早在去年 7 月，我就开源了 VibeKanban，把智能体编排装进了一块直观的看板中。那篇推文之所以引爆全网，是因为那个交互界面瞬间打通了人们的任督二脉：

> “Vibe Kanban 让你能够并行编排多个 AI 编码智能体。在 Claude Code、Gemini CLI、Codex 之间无缝切换，并在统一面板中追踪任务状态。100% 开源。”

产品经理平日里本来就是按拆解任务、分派指派、跟进进展来思考问题的。VibeKanban 不过是把任务的最终执行者换成了 AI 智能体。

几周前，我看到了 AgentCraft：一个宛如《星际争霸》即时战略（RTS）界面的控制台，专门用来统率 Claude Code 智能体，最多支持 9 个智能体同时并发。这种界面让多智能体调度有了打战略游戏的快感：

> “另一个 Claude Code 智能体控制台：用 RTS 界面并发运行 9 个 Claude Code 智能体。我必须重申：多智能体 UI 今年一定会大爆发。”

时代演进的脉络已经无比清晰：我们正在从单智能体提示词微调，极速迈向多智能体宏观编排。让这一切变得直观自然的人机交互界面正在井喷：A2UI、AG-UI、Vercel AI JSON UI……今年多智能体交互界面必将迎来大爆发。

但绝大多数人往往忽视了一个关键洞察：

**一个标榜自己“样样精通”的全能智能体，往往在每一个维度上都平庸至极。**

只有当任务被科学拆解开来时，每个智能体才能拥有高度聚焦的专属上下文；通过其独立的系统 Prompt 和积累的独立记忆沉淀出不可替代的专业深度。它们的协同合力，能够将任何泛泛的通才碾压成渣。

以我自己的内容制作智能体团队配置为例：

- **调研智能体**：检索第一手信源、罗列确凿证据、标注置信度。它的系统指令对事实核验有着近乎偏执的苛求。它从不负责写文章，它只负责掘地三尺调查真相。
- **撰稿智能体**：忠实捍卫我的个人行文风格。它掌握我的风格指南、爆款推文的历史范例以及排版癖好。它从不负责调研，它只专注打磨文字张力。
- **编辑智能体**：从逻辑清晰度与叙事节奏切入审视。基于我过往修改文章的大量正反案例精心调校，负责无情删减废话、敏锐揪出薄弱论证。
- **代码智能体**：仅限技术实现落地。熟知我的专属技术栈偏好、测试准则与工程规范。

各司其职，把一件事做到极致。正是这种严苛的边界约束，赋予了它们无与伦比的专注力。

这宛如瞬间组建起了一支完整的精英产研团队：几分钟内就能完成编制，每月只消耗几百美元 API 额度，无需支付高昂薪资，永不知疲倦，在你熟睡时依然在为你通宵达旦地开疆拓土。

## 实战验证过的四大工程底座

我曾深入研究过数十套多智能体架构。凡是能真正跑通并交付价值的，底层都高度暗合几套通用范式；而中途崩盘的，无一例外都在这些基本功上偷工减料。

### 1. 赋予智能体鲜明的身份定义

每个智能体都需要两层身份体系：

**内在身份（SOUL.md）**：明确它是谁。包括核心价值观、脾气性格与底层立场。

你可能会问：为什么不直接把这些塞进系统提示词（System Prompt）里？你当然可以这么做。但专门独立出 `SOUL.md` 文件有三大决定性优势：

- **存放位置不同**：系统 Prompt 往往属于部署环境的后台静态配置；而 SOUL 文件直接存放在代码仓库中，能纳进 Git 做版本管理，团队所有人都可以提 PR 并进行 Code Review。身份成了白纸黑字的清晰资产，而非藏在黑盒里的隐形脚手架。
- **智能体自身可见**：工作区里的 SOUL 文件是智能体随时可以主动读取、对照引用的客观文档。当它自省时可以说：“根据我的 `SOUL.md`，在未给出原始引用链接前，我坚决不写摘要。”这种自省能力会彻底改变它的行为范式。
- **能够持续演进**：系统 Prompt 往往一成不变，而 SOUL 文件会随着认知升级而不断迭代。智能体甚至可以在获得你的纠错反馈后，自主修改并更新它自己的 SOUL 文件。

一个被明确叮嘱“必须严防死守边界异常”的智能体，就真的能为你揪出那些致命边缘 Bug；一个被设定为“坚决拥护牛津逗号、誓死消灭被动语态”的智能体，就会毫不妥协地执行这些文字标准。约束造就专业。以下是一个典型的 `SOUL.md` 范例：

```markdown
# SOUL.md

**名字：** 调研智能体（Research Agent）
**角色定位：** 深度事实调查员

## 性格特质
怀疑主义者。每一项论点必须附带可信信源。
输出必须附带置信度评级：“基于 3 处权威信源，置信度极高” vs “仅单一信源提及，置信度偏低”。
在直接引用原始语句之前，坚决不擅自进行模糊总结。

## 核心关注点
- 优先采用一手信源，坚决摒弃二手搬运聚合站
- 严格关注时效性（优先采用近 6 个月内的权威资料）
- 敏锐捕捉并高亮不同信源之间的事实冲突

## 坚决不做的事
- 严禁提出无出处支撑的主观臆断
- 严禁使用模棱两可的含糊辞藻（如“有人认为”、“普遍被相信”）
- 当被要求调研时，严禁偷懒直接丢出泛泛的总结

## 标杆产出范例
[附带链接：符合你最高标准的历史调研报告]

## 负面避坑范例
[附带链接：未达标并被退回修改的调研案例及原因剖析]
```

**外在身份（Agent Card）**：明确它能干什么。

这是来自 Agent2Agent（A2A）协议中关于智能体自主发现的核心理念。当各个智能体需要自主寻找协作者时，它们通过标准化的 JSON 卡片对外宣告自身的能力边界：

```json
{
  "name": "Research Agent",
  "description": "专注论点核验与证据挖掘的深度调查专家",
  "capabilities": ["web_search", "document_analysis", "citation"],
  "input_modes": ["text"],
  "output_modes": ["text", "structured_data"]
}
```

**在组建你的第一支舰队时，维护好 `SOUL.md` 就已足够。** 智能体名片（Agent Card）是在团队规模扩大、各个智能体需要全自动互相发现并动态派发任务时才必须引入的进阶工具。先从最简单的抓手做起。

`SOUL.md` 决定了智能体如何独立思考；而 `Agent Card` 决定了外部智能体如何识别并调用它。

通用平庸的智能体只会制造泛泛的垃圾产出；鲜明的身份设定，才是一切差异化价值的源泉。

### 2. 默认串行，明确安全才并行

这是我从无数顶尖多智能体架构中提炼出的最核心军规：

**在未确定绝对安全前，默认全走串行（Serial）；只有在万无一失时，才开启并行（Parallel）。**

绝大多数初学者都会犯过度并发的幼稚错误。他们一口气同时唤醒 5 个智能体，换来的却是一堆彼此穿插污染的日志废料。一旦各个智能体涉及到共享状态，竞态条件（Race Conditions）会瞬间让系统彻底瘫痪。

心智模型必须翻转过来：不要问“我需要对什么加锁”，而是要问：**“当前究竟有哪些工序是真正允许安全并行的？”**

以竞品分析页面制作流程为例：

```markdown
串行链条（必须按部就班等待）：
事实调研 → 初稿撰写 → 编辑审校 → 正式发布

安全并行分支（彼此无数据依赖）：
竞品 A 深度调研 ←→ 竞品 B 深度调研 ←→ SEO 关键词全网分析
```

各个竞品的调研任务彼此毫无交集，尽管放手去并行；但正文撰写完全依赖于调研结论的彻底收敛，这一步必须死死卡在串行轨道上。

**优秀的产品经理能够敏锐洞察依赖关系图并据此精准派单；而在盲目并发中狂欢的人，每天只能把时间浪费在排查竞态冲突上。**

### 3. 双层记忆栈

首先必须厘清两者的本质界限：

- **上下文（Context）**：指模型在单次推理请求中能读取到的信息。高度短暂、受限于上下文窗口长度、且每 Token 成本高昂。
- **记忆（Memory）**：指持久化存放在磁盘上的数据。永久存留、容量无上限、支持结构化检索，跨会话甚至重启后依然完好无损。

AI 会话在默认情况下每次都是“白纸一张”，它对昨天发生的事情一无所知。这本身既是优点（防止历史上下文无序膨胀导致性能滑坡），同时也是致命缺陷（智能体会转头忘掉正在推进的大局）。

经过实战检验的最佳范式，是采用**双层记忆架构**。OpenClaw 在这套设计上落地得极其优雅；实操落地的极简版本如下：

**第一层：每日流水日志（`memory/YYYY-MM-DD.md`）**

全天只增不减（Append-only）的流水账记录。一旦发生值得留存的关键事件，智能体就立刻追加写入：

```markdown
# 2026-01-31

## 10:30 AM - 调研收工
已完成对竞品的商业模式分析。核心洞察：竞品 A 按席位收费，竞品 B 按实际调用量收费。用户明确倾向按量计费模式。

## 2:15 PM - 草稿初审反馈  
初稿已完成第一轮评审。用户希望在定价章节补充更真实的落地测算案例。正在补充实战案例中。

## 4:00 PM - 遭遇阻塞
正等待视觉智能体输出 SEO 关键词分析，待数据同步后即可最终敲定大标题。
```

**第二层：长期核心记忆（`MEMORY.md`）**

经过高度提炼、持久固化的黄金知识库。专门存放战略级重大决策、核心用户偏好以及血泪教训：

```markdown
# 长期核心记忆库

## 核心用户偏好
- 相比长篇大论，极度偏爱言简意赅、直击要害的硬核推导
- 渴望看到可直接落地的代码与案例，拒绝抽象大道理
- 行文风格：口语化、平实亲切、保持短段落快节奏

## 关键里程碑决策
- 2026-01-25：产品最终敲定采用按量付费模式，彻底放弃按席位收费
- 2026-01-28：官网首页首屏直接置顶 ROI 投资回报率计算器
- 2026-01-31：主攻“AI 定价策略”这一高意向关键词集群

## 实战踩坑经验
- 第一版草稿只要塞入真实案例，过审通过率提升 80%
- 用户通常在下午 2 点到 4 点集中审阅内容，重要物料集中在这个时间窗口批量提报
```

**黄金法则：如果你希望智能体真正记住某件事，就勒令它白纸黑字写进文件里。**

智能体在对话中的“心里明白”，绝不可能挺过下一次会话重启。当你交代“记住我们刚才敲定了 X 方案”时，它的正确响应应当是默默拉出对应文件完成持久化写入，而不是随口答应一句随后抛至脑后。

**这为何对多智能体舰队至关重要？** 当智能体 1 跑完调研后，成果应该存放在哪里供智能体 3 调阅？今日的流水日志正是绝佳的交接中枢。智能体 3 启动时只需扫一眼今天的流水日志，瞬间心领神会，无缝承接战局。

这是绝大多数团队在搭多智能体时最常遗漏的底座：他们早早拉满了并行线程，却忘了铺设共享记忆层，导致各个智能体在信息孤岛中各说各话、无法彼此借力。

### 4. 错峰心跳轮询系统

24 小时保持完全在线的智能体会白白烧光你的 API 账单；而彻底休眠离线的智能体又无法及时响应任务。

最优解是：**计划心跳机制（Scheduled Heartbeats）**。

每个智能体通过 Cron 每隔 30 分钟被轻量唤醒一次。它快速扫描是否有人 @ 提到了自己、是否有新派发到名下的待办、浏览公共动态流。如果检测到有待办任务，立即投入执行；如果风平浪静，则打卡报平安并立刻回到休眠状态。

**最核心的工程细节：务必错峰调度（Stagger）。**

```markdown
:00 - 智能体 1 唤醒
:02 - 智能体 2 唤醒  
:04 - 智能体 3 唤醒
:06 - 智能体 4 唤醒
```

如果所有智能体全挤在整点同一秒齐刷刷苏醒，会瞬间引发严重的系统资源挤兑与限流报错。将它们彼此错开 2 到 3 分钟依次排开。

**同时，坚持使用轻量廉价的小模型来跑心跳。** 仅仅是检查“有没有活要干”，根本不需要祭出你最昂贵的大模型，把宝贵的顶级算力留给真正的核心产出。

## 手把手搭建你的第一支双兵舰队

第一天别好高骛远去管 10 个智能体。先从 2 个智能体扎实起步：

### 第一步：初始化工作区结构

在你的项目根目录下搭建如下骨架：

```markdown
my-project/
├── CONTEXT.md           # 所有智能体启动时必读的共享上下文
├── agents/
│   ├── coordinator.md  # 协调者（Coordinator）的人设灵魂文件
│   └── writer.md       # 专项执行者（Writer）的人设灵魂文件
└── memory/
    └── 2026-01-31.md   # 当日的团队共享交接日志
```

共享上下文文件的名称取决于你使用的平台：Claude Code 对应 `CLAUDE.md`，Cursor 对应 `.cursorrules`，Gemini CLI / Antigravity 对应 `GEMINI.md`。核心逻辑如出一辙：这是一个所有智能体在初始化时必读的文件。

编写协调者的灵魂文件（`agents/coordinator.md`）：

```markdown
# 协调者智能体（Coordinator Agent）

## 核心职责
将复杂宏观需求拆解为可独立推进的细分子任务，并精准派发给对应领域的专家智能体。

## 你负责做的事
- 将模糊抽象的需求重构为边界清晰的离散任务
- 将分派指令清晰写入 `memory/YYYY-MM-DD.md`
- 严密辨析哪些工序可以安全并行，哪些必须严格串行

## 你坚决不做的事
- 严禁亲自下场写具体业务代码、起草长篇正文或直接做深度调研
```

### 第二步：双终端并发会话

打开你手头的 AI 编码终端（不管是 Claude Code、Cursor、Gemini CLI 还是 Codex）。并排开启两个终端窗口，全部定位到同一个项目目录，但分别灌入不同的身份指令：

- **终端 1**：挂载协调者身份；
- **终端 2**：挂载专项执行者（如撰稿者）身份。

两个智能体都能实时读取顶层的共享上下文，也都能随时读写 `memory/` 目录下的日志。这就是最轻量但极其稳健的协作层。

### 第三步：跑通第一次跨角色任务派发

在终端 1（协调者）中下发指令：

> “我需要写一篇关于‘AI 智能体编排落地’的技术深度博客。帮我将其拆解为具体任务，并将任务规划简报写入今日的记忆文件中。”

协调者随即生成结构化任务并写入 `memory/2026-01-31.md`：

```markdown
## 10:30 AM - 博客创作任务派单

### 资料调研（可并发推进）
- 检索并提炼 3 套经典的多智能体开源系统架构
- 总结它们在生产环境中最常见的架构公约数

### 文章撰写（必须等待调研数据落盘）  
- 基于调研得出的核心结论完成全篇初稿起草
- 目标：2500 字左右，保持通俗犀利且富有启发性的科技叙事风格
```

随后在终端 2（撰稿人）下达指令：

> “阅读今日记忆文件中的派单要求，立即开始执行。”

撰稿人智能体主动读取文件，汲取关键要点，完成任务后将阶段性产出物回写至记忆库。

如果你偏好可视化操作而非敲击终端标签，也可以直接采用 **[Vibe-Kanban](https://www.vibekanban.com/)** 这类图形化看板来调度多个编码智能体，通过可视化的 Diff 视图进行 Code Review，把精力彻底解放到战略设计与品质把关上。

### 第四步：在真实业务实战中暴露问题

找一个真刀真枪的真实需求推进，而不是玩弄玩具 Demo。

敏锐捕捉系统在哪里开始脱节：
- 智能体之间出现了重复劳动？→ 说明任务简报拆得不够清晰彻底；
- 专项智能体漏掉了关键背景？→ 说明全局共享上下文需要补足对应行业常识；
- 任务交接时信息断层？→ 针对性规范每日日志的交接排版规范。

### 第五步：极其审慎地逐步扩容

只有当两个智能体之间的默契磨合得天衣无缝时，才允许考虑拉入第三个成员。每一个新角色的引入，都会让系统拓扑的协同复杂度几何级飙升。

**多智能体的复杂度，必须靠切实的业务需要一步一个脚印赚出来。**
