## 面向 CI/CD 的 AI 事件应急响应：Anthropic 的 Claude 值班实战

几周前的一个晚上，轮到我值班（On-call）。晚上 10 点，同事在 Slack 上急匆匆给我发来一条私信：某项新上线服务的约 44 个自动化测试用例突然全都不执行了。

换作以往，我只能无奈地暂停手头正在做的事情，心力交瘁地坐到笔记本电脑前，长长叹一口气，然后硬着头皮开启长达一个多小时的痛苦排障与修复拉锯战。但现在，我的工作流彻底变了样：我直接在频道里 @Claude，问它看到了什么。

在这次排障中，Claude 迅速排查出：这批测试用例之所以凭空消失，是因为当天上午开启了一个特性开关（Feature Flag）；它进一步分析确认，直接回滚该开关是绝对安全的。我随即请同事执行了回滚。仅仅 3 分钟后，Claude 便在 Slack 上主动向我汇报：测试跳过规则确实已被彻底清除，系统错误率已顺利回归正常基线。

![为清晰起见，上图根据真实排障对话进行了重绘。](https://assets.claude.com/f5b4aa5251da65b25186018374984cef9d44996d.png)

*为清晰起见，上图根据真实排障对话进行了重绘。*

在过去的几个月里，**Claude Tag 一直作为 Anthropic 内部 CI/CD 基础设施故障的“第一响应人（First Responder）”默默坚守在值班一线**。这不仅极大拯救了我们工程师下班后的个人社交生活，更为每一次突发的 CI 故障提供了瞬时就绪的先锋排查员：在近期所有发生过的故障事件中，每一份首发态势报告（SITREP）全部出自 Claude 之手，**它通常在故障发生后 15 分钟内便能正式发布第一份根因分析**。

在这篇文章中，我们将全景拆解我们所构建的这套系统及其运作机制，以便你也能亲手为自己的团队打造一套，从此告别对值班轮训的无尽焦虑。

## 我们的 Claude 值班架构全貌

在逐一深入探讨事故应急响应的各个具体阶段之前，我先梳理一份全局架构概览，帮助大家在脑海中建立完整的系统图景。

一个合格的 AI 值班智能体，必须具备四大支柱：**记忆能力（Memory）**，以便铭记前序排查进展；**连接与访问权限（Connections & Access）**，以便能够自主深入各大系统调查、理解并采取修复动作；**调度机制（Schedules）**，以便清楚何时应当主动唤醒复查；以及**行动规范指令（Instructions）**，以便确切知晓面对特定场景该执行哪些动作。

[Claude Tag](https://claude.com/product/tag?utm_source=chatgpt.com) 是我们整套值班智能体的核心中枢。Claude Tag 跨越我们的 Slack 值班专属频道维系着连续的记忆，并充当在事故处置过程中逐轮接收人类指令的交互界面。与此同时，Claude 还能对值班频道以及其他关联频道中的突发事件做出亚秒级实时反应。对于周期性的日常例行公事（例如交接班），同样直接在该频道通过自然语言设定排期——比如简单吩咐一句：“每周一上午 9:00 自动执行一次 CI 交接班巡检”。

[Claude Tag 拥有专属的服务账号（Service Account）](https://claude.com/resources/articles/agent-identity-access-model?utm_source=chatgpt.com)，并被赋予了一名合格 Anthropic CI 工程师所必需的工具访问权限（如 Datadog 或 Grafana）。这项权限配置只需系统管理员在频道初期做一次性初始化即可（[详见官方配置指引](https://claude.com/docs/claude-tag/admins/setup-overview?utm_source=chatgpt.com#choose-which-tools-to-connect)）。

除了核心的值班主频道，我们还让 Claude 进驻并全天候守望其他关联频道（只要这些频道将 Claude Tag 添加为成员即可），使它能够实时汲取丰富的环境上下文——例如微服务突发告警、生产配置变更广播，或是核心 PR 的合并动态。

智能体的日常行动准则全部作为技能（Skills）保存在 Git 仓库的 Markdown 文件中。这样一来，团队里的多名工程师可以协同迭代这些规范，我们能像管理普通软件代码一样严谨地管理智能体的行为逻辑。其中还沉淀了关键的告警路由规则、应急处置策略，以及作为自进化闭环一部分的“血泪教训复盘日志”。

搭建这套骨架，实际只花费了我们几个小时而非几天。我们特意在 GitHub 上开源了一套通用脚手架：**[on-call setup kit](https://github.com/anthropics/oncall-kit)**。它能自动将你团队的历史事故复盘，提炼转化为标准的排障分诊 Playbook，并为你留下一个常驻在故障排查频道中、能够自主诊断、升级并持续进化的只读权限 Claude。[你可以通过一份虚构团队的历史数据，在短短十分钟内观摩它的实机运行效果](https://github.com/anthropics/oncall-kit/blob/main/test-fixtures/RUNBOOK.md)。

极简核心步骤摘要（TL;DR）：
- 订阅 [Claude Team 或 Claude Enterprise](https://support.claude.com/en/collections/9387370-team-and-enterprise-plans?utm_source=chatgpt.com) 套餐；
- 组织管理员通过 Claude Tag 将 Claude 引入 Slack 值班频道；
- 管理员在该频道内为 Claude 挂接相应的监控连接器、关联 GitHub 代码仓库，并配置好 [Claude Code Remote（远程控制）](https://code.claude.com/docs/en/remote-control?utm_source=chatgpt.com)；
- 将 Claude 邀请入故障应急频道，指示其全天候监控事故并在触发时立即开展自动分诊。

接下来，让我们深入复盘这套体系在事故处置全流程各个阶段的具体表现。

## 1. 故障检测阶段（Detection）

Claude 不仅彻底颠覆了团队“响应”故障的方式，更从根源上重构了团队在第一时间“发现”故障的敏锐度。在此之前，传统的故障检测面临两大难以调和的顽疾：

首先，人类工程师很难未雨绸缪地针对所有系统始终配置出完美无瑕的静态规则与告警阈值——尤其是在全新服务刚刚上线、缺乏足够的历史流量基线数据时，界定阈值往往只能靠猜。

为了化解这一盲区，针对新上线的微服务，**我们会让 Claude 在最初几天持续分析实时流量数据与流入警报，主动提出补齐告警规则的建议，并对那些过于严苛导致频频误报、或是过于宽泛形同虚设的阈值进行精细微调**。

第二个顽疾则是让每位 SRE 痛苦不堪的**警报疲劳（Alert Fatigue）**：逐一审查核实每一次拉响的警报极其枯燥消耗心力。但与人类不同，Claude 永远不会感到疲倦。

Claude 会不知疲倦地监控各个警报频道中的每一条相关信息，严格对照 [root oncall.md 核心规范文件](https://github.com/anthropics/oncall-kit/blob/main/templates/ONCALL.md) 中的准则进行逐一甄别，精准裁定这究竟是一次可以留到明天天亮再处理的轻微抖动，还是需要立刻通过 PagerDuty 把值班工程师呼叫起床的致命灾难。例如，在吸收了流量数据分析后，规范文件里的一条成熟规则可能是：*“如果错误率超过 2% 持续达 5 分钟以上，且当前不处于已知的系统计划性发布窗口期，则立即呼叫值班人员；否则将其静默记录到 lessons.md 备忘录中。”*

除了上述自动化监控，Claude 值班流程还支持另外两种触发机制：
- CI 团队成员在值班频道中手动汇报异常（正如开头提到的 44 个测试丢失案例）；
- 全公司任何员工通过内部告警系统发起工单。一旦被标记为 CI 基础设施故障，系统会自动为该事件创建专属的临时 Slack 频道，我们的值班 Claude 会瞬间自动接入该频道展开响应。

## 2. 分诊与根因定位（Triage）

让 Claude 从漫天飞舞的告警噪音中做初步过滤只是一碟开胃菜，真正巨大的价值释放来自**事故的深度根因调查**。

**在一次故障事故立项后，Claude 输出首份附带扎实证据链的深度分析报告的中位数耗时仅为 14 分钟；在最快的极速案例中，它在第 4 分钟输出的首份报告里就已经精准锁定了根本原因。**

当警报正式升级为事故事件时，Claude 往往已经在 Slack 频道中准备好了一份有理有据的假设推演供工程师审阅。Claude Tag 会自动拉起一个[动态工作流（Dynamic Workflow）](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code?utm_source=chatgpt.com)：由一个<strong>总控编排智能体（Orchestrator）</strong>挂帅，动态派生出多个**并发执行子智能体（Executor Subagents）**，分头扑向各个系统依赖与事实源展开横向地毯式排查。

对于我们的技术栈而言，这涵盖了 Grafana 指标大盘、底层日志归档、PagerDuty 告警、GitHub 提交历史、Kubernetes 集群状态，以及 Slack 历史事故讨论串——所有这些系统全部通过 [MCP 连接器（Model Context Protocol Connectors）](https://code.claude.com/docs/en/mcp?utm_source=chatgpt.com) 与 Claude 实现无缝咬合。Claude 能够全自动沿着多条可疑线索并发追踪，显著缩短**平均故障恢复时间（MTTR）**。

各执行子智能体将各自领域的勘验发现实时汇总回编排智能体，由后者进行逻辑提炼与事实合成，最终以条理清晰的态势报告（SITREP）直观呈现给人类工程师。

![编排智能体与执行子智能体协同排障流转图。](https://assets.claude.com/64d5b3d1b39aa8a5233ea05ac12c051e1b97f297.png)

*编排智能体与执行子智能体协同排障流转图。*

请注意，编排智能体与执行子智能体绝非盲目乱撞。它们的行动严密受控于调查技能规范，其中包含[针对各类具体 Bug 故障分类的详尽排查参考文档](https://github.com/anthropics/oncall-kit/tree/main/skills/triage)。

例如，一份针对“影子分流差异 Bug（Shadow Divergence Bugs）”、厚达 617 行的专项调查技能，巨细靡遗地编码了我在此类排障中所采取的每一个思考和操作步骤。这份规范是我在此前一次真实事故中，与 Claude 逐轮结对排查后由它根据实战记录直接沉淀生成的。

此外，`lessons.md` 备忘录同样在时刻指引着 Claude 的排查方向。这份 Markdown 文档是一部鲜活的故障编年史，忠实记录着我们曾经解决过的每一次事故：发生了什么、根因是什么、最终如何修复，以及哪些反直觉的暗坑值得后人铭记。Claude 拥有全自动向该文件追加新复盘的权限。**每一次全新的排查调查，都会以首屏精读该文件作为第一步**，因此 Claude 提出的第一个假设推演，往往直接建立在近期刚刚发生过的鲜活教训之上。

如果同一个故障模式反复露头，我们会将其提炼升格为正式的调查技能。在这份文件中，我最喜欢的一条教训恰恰是 Claude 专门针对我写下的。当时我在还没有查看底层监控指标之前，就凭着一份配置文件的表面改动武断做出了主观猜测；如今 `lessons.md` 里醒目地写着这样一条铁律：

> *“先查真实指标，再做理论推测。配置文件只能告诉你可能哪里会出问题；而运行时指标才能确凿证明到底哪里崩了。”*

即便武装了如此丰富的工具与上下文，Claude 也无法保证每一次推断都一次性全对。人类的工程师直觉与一线实战经验依然不可替代。Claude Tag 赋予了团队在排障时开启<strong>“多人协作对战模式（Multi-player mode）”</strong>的从容体验：人类工程师与 AI 中的任何一方，都能在 Slack 中实时修正调查航向，或并肩提出全新的求证假设。

## 3. 故障自愈与修复阶段（Resolution）

如果 Claude 已经能够自主发现异常、完成升级分诊并精准定位故障，那么它能否亲自动手把 Bug 修复？对于不同企业团队，答案可能各不相同；以下是我们在 Anthropic 内部的落地实践。

我们团队绝大多数的发布部署都受控于特性开关（Feature Flag）的保护。我在 Claude Code 中专门创建了一个具备我本人权限的独立运维智能体，有权在这些特性开关的保护下执行渐进式金丝雀发布。

在日常发布的第一阶段，通常由 Claude 负责掌管灰度金丝雀流量：全天候严密盯盘监控指标异动，并根据健康度自主决定将特定特性开关的放量比例动态调大或紧急回滚降级。这套机制本身足以单独写成一篇万字长文，在此暂不展开。

除此之外，Claude Tag 协助团队落实故障消除的核心路径还包括：
- **容器调度决策**：明确提示我们是否需要对 Kubernetes 集群中的特定异常节点执行隔离封锁（Cordon）或工作负载腾退清空（Drain）；
- **动态扩缩容指引**：在面对突发突增的流量洪峰时，给出极其精准的底层基础设施扩容建议（这种情况虽然发生频率不高，但每当 Claude 带着确凿的削峰填谷方案给到你案头时，都会让人无比安心）；
- **全自动生成修复代码 PR**：这是最常见的闭环形态——直接生成包含针对性修复代码的 Pull Request，值班工程师只需快速完成同行审阅并点击合并，即可闪电完成生产环境上线消除故障。

## 4. 效果验收、全员沟通与交接班（Verification & Handoff）

在推进修复上线后，Claude 会调用与前期排障调查相同的 MCP 连接器和指标工具，严密核验该修复是否确实达到了预期成效。根据 `oncall.md` 中的规范铁律，系统会自动在 `lessons.md` 中追加本次事故的复盘报告，并自动生成换班态势纪要。

为了向全公司通报横跨多个事故的宏观全局态势，我们打造了一个名为 <strong>ci-weather（CI 气象站）</strong>的广播智能体。它会自动汇总来自各个独立故障频道的信息、当前代码构建指标、PR 合并队列拥堵程度以及发布延迟数据，随后在面向全公司所有人公开的大群频道中，以科技新闻快报的形式定时播报。如今，其他部门的工程师只需看一眼气象频道就能心中有数，再也不需要因为“CI 是不是又挂了、我手头的 PR 要不要先忍住别合并”等琐事私聊轰炸值班人员。

必须诚实坦白的是：**这份全员通报的文本排版风格，我们经历了好几轮深入的迭代磨合**。让 Claude 一键生成一份充满机械味道的状态小结并不难，但要让全公司上千名工程师读起来如沐春风、清晰易懂，体现的是团队专属的沟通审美与组织温度。**这是纯粹的人性化沟通艺术，绝不是简单的管道拼接。**

![ci-weather 智能体在全公司公开频道发布的每日 CI 态势气象播报。](https://assets.claude.com/41a169c1eb4a8d08db5297034089c893808ab77e.png)

*ci-weather 智能体在全公司公开频道发布的每日 CI 态势气象播报。*

最后，除了 Claude 在 `lessons.md` 中为自己记录的技术日志，我们每周一同样需要一份面向人类工程师的正式交接班报告。Claude 会全自动汇编生成每日与每周的运行复盘总揽，让接棒值班的下一位工程师能够丝滑承接前任的全部排障上下文。

## 范式升华：从“盯着单次事故”到“运维一套事故自愈系统”

在 2021 至 2025 年间，Anthropic 的软件工程师平均每季度向生产环境[交付的代码量实现了令人咋舌的 8 倍暴涨](https://www.anthropic.com/institute/recursive-self-improvement)。虽然我们对代码质量始终坚守极高的质量红线（每个 PR 都有明确的人类责任人、合并必须经过同行审批、所有变更必须跑通全部 CI 门禁），但在由智能体驱动的代码大爆发时代，**唯一能够跟上“智能体编程（Agentic Coding）”爆发节奏的，只有“智能体化持续集成（Agentic CI）”**。

Claude 彻底接管了我工作中最为枯燥折磨的部分——深夜无情的突发惊醒、以及繁杂琐碎的跨部门沟通协调；它让我能够将精力心无旁骛地聚焦在中长期的系统可靠性架构改造上，去推敲那些真正能大幅提升系统稳定性的核心设计。

而整套体系最美妙的地方在于，它没有任何割裂的拼凑感。我们原本就一直在 Slack 里完成所有的值班沟通；而如今，Claude 只不过作为一位极其敏锐、从不疲倦的新同事，默默搬了把椅子，正式坐进了我们的值班室。
