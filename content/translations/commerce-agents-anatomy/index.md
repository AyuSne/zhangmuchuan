> 原文：[A guide to the anatomy of effective commerce agents](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents)；原作者：Ali Shazal、Matthew Koen；原文发表：2026-09-02

在过去的一年里，我们与整个商业领域的众多团队——涵盖零售商、线上集市（Marketplaces）、旅游出行、文娱票务以及电信服务商——紧密合作，基于 Claude 打造了一系列商业智能体（Commerce Agents）。

这些智能体如今已正式步入生产环境；企业客户在落地使用后，不仅见证了用户购物车客单价的显著攀升，也体验到了商家运营效率的大幅提升。它们在底层拥有高度统一且优雅的极简架构：**一个置身于标准智能体循环中的 Claude 模型，外加一套定制技能（Skills）、后端工具集（Tools）以及一套完备严密的评测套件（Evals）。**

本文专为正在构建商业智能体（或各类面向普通消费者的 Agent 应用）的工程师与技术管理人员而写。第一部分聚焦于架构设计（这通常是一次性敲定的根本基石）；第二部分探讨延迟与成本的工程调优；第三部分深入生产实践，全面拆解跨会话记忆、风控安全、评测机制以及如何在大规模组织中跨团队协同推进。

**01**

## 系统架构设计

**由单一大模型运行在标准智能体循环中，搭配覆盖长尾场景的技能集（Skills），并通过工具集（Tools）调用企业现有的业务系统。架构定型，一劳永逸。**

### 什么是商业智能体？

我们将商业智能体定义为：**能够极大简化在线产品目录买卖与交易流程的智能体。**

有的智能体直接面向消费者（C端）：它们负责搜索挑选、比价推荐、智能平替以及装配整个订单。这可以是一个实体零售购物车、一份定制化的旅游行程、一次手机通信套餐的变更、或是演出活动中的选座锁票。有的智能体则面向商家与企业运营（B端）：它们负责解答销售经营指标、策划并执行营销促销活动，以及智能调控库存与商品定价。

![面向 C 端消费者的导购助手与面向 B 端商家的经营分析助手界面示意图](https://assets.claude.com/47781bb901a117a56bcb301ad769a405a42dba62.png)

其核心架构是一个运行在[标准智能体循环（Standard agent loop）](https://www.anthropic.com/engineering/building-effective-agents)中的基座模型：围绕目标进行推理、探查上下文、通过工具执行具体动作、通过技能学习业务流程、在必要时发起澄清反问，并持续观察执行结果，直至最终大功告成。

在这套架构的最前端，**既没有**用来生硬切分会话走向的“意图路由器（Intent Router）”，在后端**也没有**按细分领域堆砌的一堆碎片化子智能体。

### 工程上下文

#### 选技能（Skills），而非子智能体（Subagents）

商业智能体必须在海量商品品类和繁杂的用户意图之间跨越极其广泛的业务能力，这往往会让人忍不住想为每一个垂直领域（Domain）单独设计一个子智能体。

然而在工业实践中，这种多智能体方案被证实是次优的。因为一次商业对话本质上是一个贯穿多轮交互、高度紧密耦合的整体会话，各个意图之间需要大量共享的全局上下文。

在子智能体架构中，顶层的总控调度器（Orchestrator）负责保管购物车暂存状态、用户个性化偏好以及完整的对话历史。

每一次向子智能体发起任务移交（Hand-off），都是一次**伴随状态损耗的操作**。这不仅严重拖累子智能体单次回答的质量，进而损害整体交互体验；而且雪上加霜的是，每一次跨智能体交接都会凭空消耗数倍的额外 Token，并带来数秒的硬性延迟。

此外，真实的商业领域几乎很难做到泾渭分明的物理割裂。一个退换货流程可能同时需要调阅历史订单、当前的购物车以及全量商品目录；采用“一域一 Agent”的方案，要么必须在各个子智能体中全量重复复制这些系统访问权限，要么就必须在任务中途来回倒手交接。

伴随基座模型智力水平的飞跃，它们能够原生驾驭更长的上下文、更多的技能以及更丰富的工具集，以往由于模型能力限制而制定的人工拆分规则，在每一代新模型面前都在迅速消融。

相比之下，[智能体技能（Agent Skills）](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)能够在不付出任何任务移交损耗（Hand-off tax）的前提下，赋予你同样的模块化分域管理与上下文控制能力——因为技能指引是按需直接加载进已经完整持有全部历史上下文的主智能体当中的。

在我们跨越数家大型企业的实际投产对比中：**单智能体配合技能体系的设计，在输出质量上始终全面超越“一个大 Prompt 包打天下”以及“多子智能体分权”两种旧架构，并且往往在单任务交付成本与响应延迟上更具压倒性优势。**

子智能体真正能发挥核心价值的场景，在于总控调度器将其**作为一个工具**来调用，去执行某项高度狭窄、边界闭环且极度受益于拥有专属独立上下文窗口的深层任务。

生产环境中最典型的范例便是“深度研报检索子智能体（Deep-research subagent）”：该子智能体在后台负责深度翻阅大量文档、编写并执行数据分析代码、遍历数据模型并不断试错排除死胡同。所有繁重杂乱的中间过程全部隔离在子智能体内部，最终仅将一份高度浓缩凝练的结论回传给总控调度器。

另一个合理的特例，是某些业务域本身就已经拥有高度定制、完全自主闭环的专属智能体。比如你的医药处方调配或金融合规服务已经运行着拥有独立严苛风控合规边界的专属智能体，此时最佳的架构实践是执行真正的**权责移交（Hand-off）**——让该专属智能体彻底接管任务，并在其自身的交互循环中直接与用户对接，直至事项彻底了结。

这里的关键分水岭在于**会话的主导归属权**：真正的移交（Hand-off）让垂直领域智能体成为与用户直接对话的法定主体；而委派（Delegation）则依然让总控调度器充当二道贩子，在一个单轮交互中将垂直智能体呼来唤去，在每一次机械中转中层层损耗信息。

#### 系统提示词还是技能：按出现频次决定归属

在权衡某组业务指引究竟该放入系统提示词（System Prompt）还是打包为专属技能（Skill）时，最重要的决策依据在于：**智能体需要调用它的频次究竟有多高。** 加载一项技能需要耗费一个额外的模型轮次，因此凡是智能体在绝大多数轮次中都必须仰仗的基础逻辑，通常直接固化在系统提示词中。

当然，这也取决于你的真实业务流量分布，以及自动化评测集所暴露出的行为模式。一个极佳的经验法则是：**凡是覆盖你 1/3 及以上业务流量的核心能力（不论是上线前预估还是上线后实测观测到的），统统写入系统提示词；其余长尾能力全部沉淀为技能。**

如果某项技能能够基于你手头已有的外部先验信号精准预判（例如用户当前是从哪个业务页面点击进来的），我们强烈建议在触发首轮模型调用之前，直接由宿主运行环境（Harness）预先将该技能上下文注入会话，直接省去模型自己判断并加载技能的额外轮次开销。

至于最核心的关键底线——例如安全与法律红线、品牌声誉约束、以及用户的核心生命体征（如严重的坚果过敏史）——**永远必须毫无保留地常驻系统提示词**。

对于商业导购智能体而言，这意味着**商品搜索能力必须常驻提示词**，因为几乎每一场购物会话都会频繁触发检索；而各类长尾特性则交由技能包揽。

在我们开源的[官方参考实现（Reference implementation）](https://github.com/anthropics/commerce-agents)中：
- **导购智能体（Shopping Agent）**：系统提示词内嵌真实性锚定规则（Grounding）、购物车与结账状态机语义、展示渲染规范以及商品搜索工具；长尾技能则划分为：搜索发现（`search-discovery`）、导购决策对比（`purchase-research`）、心愿与规划目标（`planning-goals`）、售后客户关怀（`customer-care`）以及记忆个性化（`memory-personalization`）。
- **商家运营智能体（Merchant Agent）**：同样按业务经营域进行切分，提示词承接经营大盘框架，技能划分为：经营洞察分析（`performance-insights`）、商品上架管理（`catalog-listings`）、库存智能调配（`inventory-operations`）、定价促销策略（`pricing-promotions`）以及营销活动投放（`marketing-campaigns`）。

**常驻系统提示词** *导购智能体*：真实性校验、购物车与结账语义、界面呈现规则、商品核心搜索。

**导购专属长尾技能** *覆盖长尾场景*：搜索发现 · 导购决策 · 规划目标 · 售后关怀 · 记忆个性化

**商家运营专属技能** *按经营业务域划分*：经营洞察 · 上架管理 · 库存调配 · 定价促销 · 营销投放

### 智能体工具体系工程化

我们在[如何为智能体编写高效工具](https://www.anthropic.com/engineering/writing-tools-for-agents)一文中曾全面讨论过工具设计的通用哲学。在商业场景下，尤以以下两点最为致命：

**1. 智能体工具必须直接构建在现有的核心系统与成熟业务逻辑之上。**

一家成熟的商业公司内部必然早已拥有高度成熟的搜索与推荐排序算法、成熟的购物车服务、用户画像中心、仓储库存系统、促销优惠计算引擎以及销售数据仓库；每一套系统都凝结了多年打磨的业务壁垒，并且掌握着大语言模型永远无法直接触碰的深层信号。

智能体的工具应当直接调用这些既有微服务，而不是异想天开地试图在 Prompt 层面去重新实现一套低劣的逻辑。工具的接口边界，正是既有系统严密计算的终点，以及大模型发挥主观洞察力与综合裁决权的起点。

举例来说，当智能体调用 `search_products` 时，后端返回的商品列表应当已经由内部引擎完成好了精细的相关性与商业化重排序；智能体在这个环节的核心价值，是甄别这批候选中究竟哪些最能契合用户当下的真实诉求、决定向前台展示几款商品、以及组织怎样的推介说辞。

**2. 工具的返回值本质上就是给模型看的上下文。**

工具必须只返回模型参与逻辑推理所必需的字段，果断剔除其余无用信息。搜索结果列表里每一行都带上又臭又长的图片 URL，就是最常见的反面教材。

在必要时，工具应当在内部对原始接口回包进行清洗与重塑；当后续动作无法单凭数据表面直接推导出来时，甚至应当贴心地在返回值末尾追加明确的“下一步建议”。

在异常报错场景下这一点尤为关键——模型极度需要明确的业务整改指令，而非冷冰冰的 HTTP 状态码。例如，相比于抛出一个晦涩的 403 错误，不如直接返回一条明确的业务指引：“在查询商品库存可用性时，必须附带有效的商品 ID（Product ID）。”

#### 将 UI 交互组件抽象为工具（Presentation Tools）

绝大多数商业智能体的输出呈现都是富交互组件而非单调的纯文本长篇大论——无论是商品轮播卡片、旅游行程单、演出选座图还是经营对比图表。这意味着智能体在输出端必须吐出严密的结构化 Schema，而非松散的 Markdown。

许多团队在起步时往往习惯于引导模型输出自定义标签（如 `<product_card id="123">`），然后在前端写正则解析。伴随业务复杂度的上升，这种模式必然崩塌：
- 相比于在海量预训练中反复锤炼过的结构化工具调用（Tool calls），模型对你们团队私有标签的理解力要薄弱得多；一旦涉及多层嵌套组件，输出合法性便会直线下滑。单靠提示词根本无法提供严密的数据结构保证。
- 所有标签语法的定义都不得不全量堆积在系统提示词中，每新增一个前端组件都会导致上下文极度膨胀，每一次调整都伴随着引发其他提示词退化的风险。
- 历史会话最终以只有你们内部定制解析器才能识别的怪异格式沉淀在数据库中，加载历史记录时要么需要在前端重新手写极其脆弱的解析流，要么就必须在后台维护两套与模型 API 原生规范不兼容的冗余数据副本。

经受住大规模实战检验的成功范式，是**将每一个 UI 交互组件都定义为一个标准的强类型工具（Presentation Tool）**。模型通过强类型参数发起诸如 `present_products`、`present_itinerary` 或 `present_plan_comparison` 的工具调用；你的服务端拦截该调用、执行参数校验与数据补全，并向前台抛出结构化渲染事件；最终由前端组件库负责优雅绘制。

由于这些前端组件本身就是标准的工具调用，它们天然以原生规范保存在消息数组中，重新加载历史会话时无需任何二次解析转换。其接口定义契约如下所示，并在[官方参考代码库](https://github.com/anthropics/commerce-agents)中完整开源：

![通过定义 presentation 工具将 UI 组件与消息结构无缝联通的架构动画演示](https://assets.claude.com/3f245cfa642f8d8c7a9f7f5841f127d67f27f5dc.gif)

这种设计唯一的工程取舍在于**流式输出的粒度（Streaming granularity）**。在服务端，工具调用的顶层参数通常需要经历一段缓冲以完成结构合法性校验，这会导致在开启流式输出时，富交互组件的子构件会呈分步阶梯式吐出，对前端感知延迟产生一定影响。

为了追求真正的 Token 级别毫秒级流式呈现，可以在工具定义中声明 `eager_input_streaming: true`。这会跳过服务端缓冲，虽然牺牲了服务端的强 Schema 校验担保，但换来了极速的流式体验。

在我们的评测中，Claude Sonnet 及以上级别的模型几乎极少出现 Schema 结构违规；只需在前端加上简单的错误重试保护，即可从容覆盖个别偶发边缘情况。

呈现工具还赋予了智能体一项关键优势：**让它清晰掌握屏幕上究竟展示了什么。** 当顾客随后追问“第一个酒店”或“左下角第三个商品”时，真实的屏幕排版数据早已作为上一次呈现调用的参数完好留在消息历史中。

为了保证这种多模态指代消歧能够顺畅生效，工具参数必须真实映射前端页面的物理布局——按照有序行、卡片轮播的直观层级来组织数据结构，切忌传给前端一个平铺扁平数组然后由前端在私下重新乱序排版。

**02**

## 性能提速与成本极致优化

**双管齐下攻坚延迟：既要通过硬核工程压缩端到端物理耗时，又要通过产品技巧打掉感知延迟；将成本重任托付给缓存机制。这一切优化，绝不以牺牲模型智力为代价。**

在商业世界中，响应延迟直接关乎生死，面向普通消费者的 C 端产品更是容不得半点迟疑。然而在各类 Agent 产品的实操落地中，我们反复观察到一个铁律：**真正能够拉动用户留存、活跃度以及最终购物车客单价的关键驱动力，永远是最终交付结果的质量。**

回答是否切中要害、用户托付的任务最终是否真正圆满搞定，对上述核心商业指标的撬动效应，远胜于毫秒级的细微提速。

因此，应当从两个维度协同攻坚：一方面依靠扎实的后端工程把端到端物理耗时压到最低，另一方面通过巧妙的产品呈现大幅削减用户的**感知延迟（Perceived latency）**（因为看着智能体一步步有序推进工作，在用户感知中等同于进展顺利）。

每个用户的心中都有一杆“忍耐倒计时”，以下技术方案能确保智能体牢牢留在安全线以内，且无需以降低模型智商为代价。

### 压缩任务完成总耗时

任务完成的总物理耗时（Task completion latency），本质上是所有交互轮次中“首字到达至最后 Token 耗时”与“所有工具执行耗时”的累加总和。这为你提供了三个清晰的工程抓手：**减少交互轮数、加快工具响应、提高 Token 生成速度。** 这三个把手有时候彼此制约，因此终极目标是优化三者的总和，而非孤立追求某一项。

- **减少交互轮数**：提前预加载高概率上下文、提升基座模型智力水平，并引导模型并行并发调用互不相干的独立工具。
- **加快工具响应**：持续优化工具底层的后端性能，并在工具参数刚刚生成完毕的瞬间立即提前派发执行。
- **提高 Token 吞吐**：基于全量评测集的系统化拉网测试（Sweep），选定最优的模型及其配置。

#### 减少交互轮数

用户问题的复杂度天然会导致轮数上升，而这往往不受你的控制。提升模型自身的综合智商，并精准注入关键上下文，是帮助智能体以最少轮数达成目标的不二法门：

- **将高概率上下文提前预加载到位**：如果用户是从某个具体的商品详情页唤起智能体，或者商家是从某场营销活动的看板点开助手，直接在会话建立的瞬间把该页面的核心业务数据压入上下文。接下来的对话大概率正是围绕它展开的，直接从上下文作答无需耗费任何额外轮次去临时调接口查数据。
- **果断采用更聪明的模型**：更聪明的基座模型能够更高效地完成任务规划并以极佳的编排发起工具调用，从而在宏观上大幅压缩任务闭环所需的总交互轮数。这种轮数层面的精简，往往能彻底抵消大模型由于体积更大而在单个 Token 生成上稍慢的微小劣势。如果你的业务查询逻辑高度复杂，或者线上监控显示平均每项任务需要 5 轮以上的拉扯，那么“更快的模型”往往恰恰是那个“更聪明的模型”。通过后文所述的“评测拉网测试”能帮你客观选出最优解。
- **引导模型并行调用独立工具**：商业场景往往涉及大量互不干扰的并发操作：比如同时搜寻多款搭配商品、查阅多份售后条款文档、或是从多个数据源汇总近期的销售流水。工具并行调用确保了多个独立查询不会白白浪费额外的交互轮次。在提示词中明确要求模型在单轮内一次性并发抛出多个工具调用，并在一条用户消息中以工具结果数组的形式统一聚合返回（详见[官方并行工具调用指南](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)）。

#### 加快工具响应

- **优化工具底层的后端性能**：有时候一个工具确实需要扇出（Fan-out）查询——比如商家助手的“获取今日经营快报”需要同时从销售、库存与投放三个系统拉取状态。但我们频繁看到的反面模式，是工具代码逐渐沦为了擦屁股拼接缺失后端逻辑的垃圾桶：一个简单的查库存工具，先调商品中心查 SKU，再遍历各门店库存，随后调履约服务查截单时间，最后还在工具自己的代码里手写复杂的平替规则与自提资格过滤。这个工具如今背负了过于沉重的领域知识，规则稍有变动就极易踩坑，并且承担了本该由上游业务中台承载的核心逻辑。遇到这种情况，彻底的解法是在后端沉淀一个专门的高性能聚合微服务接口，然后由智能体工具发起单次轻量调用。
- **工具参数边吐边派发（Eager tool dispatch）**：工具参数在流式输出时也是逐 Token 吐出的，宿主框架完全可以在某个工具的参数刚刚闭合完毕的瞬间，**立刻抢先派发执行该调用**，趁着大模型还在继续流式输出其余并行工具或后续文本块的时间差，在后台静默完成处理。这种极客优化能将原本数秒级的卡顿缩减至短短数百毫秒，[Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview) 已将其列为开箱即用的默认特性。在提示词中引导模型优先输出耗时最漫长的那项工具调用，能将这一并发红利发挥到极致。

![工具参数边流式吐出边提前派发执行的对比动图](https://assets.claude.com/6d1b82ec4129e3eae6932ab4dea06dd3fc1c274e.gif)

### 击碎感知延迟

感知延迟是指用户从发出指令到屏幕上**首次出现有意义的动态反馈**之间所度过的主观时长。在直接面向消费者的交易场景下，任何交易摩擦都会直接导致弃购率攀升与 GMV 损失。以下两项技术无需改动模型，即可在产品层面大幅抹平感知延迟：

- **组件成型即流式上屏**：一次完整的商业结构化回包通常包含 500 到 700 个输出 Token，在不开启流式呈现时，意味着用户要盯着转圈圈的 Loading 动画干等 5 秒甚至更久。在呈现工具的各个子参数流式吐出的过程中，前端应当立即捕获并采取渐进式渐显渲染（Progressive rendering）。
- **把工作过程大大方方亮出来（Show the work）**：在智能体忙于在后台翻阅数据时，用平实质朴的自然语言在界面上打出当前步骤的进度提示（例如：“正在为你搜寻靠近海滩的优质酒店……”）。你可以直接复用工具已有的调用参数（如搜索商品的关键词），也可以在工具定义中增加一个显式的 `user_facing_message` 字段，引导模型顺手写下一句安抚话术。

![左侧传统白屏加载与右侧显示思考进度和流式上屏的对比演示动图](https://assets.claude.com/0a23449decd51d4ed8785a700a1e117db2d3f39f.gif)

在上面的对照实验中，两套面板背后运行着一模一样的基座模型、工具集与提示词，仅仅是宿主框架的前端交互策略有所不同。两者完成任务的物理总耗时完全一致，但用户主观感知到的体验却有着天壤之别。

### 提示词前缀缓存（Prompt Caching）

提示词缓存是你砍掉运行成本的最强核武器，而电商高频流量恰恰是发挥其威力的绝佳土壤。命中缓存的输入 Token 单价仅为冷启动时的 1/10；虽然首次写入缓存需要支付大约 1.25 倍的微小溢价，但只要该前缀被复用哪怕第二次，就已经彻底回本并产生净收益。在并发体量庞大的 C 端应用中，只要设计得当，借助最便宜的默认 5 分钟滑动过期机制，就能轻松刷出极其惊人的缓存命中率。

在我们见过的顶级电商落地案例中，系统缓存命中率常年稳定在 **90% 到 99%** 的极高水准，这也是架构设计伊始就必须确立的硬性基准线。更令人振奋的是，根据实测经验，在 10 万（100K）Token 级别的上下文体量下，读取缓存 Token 的响应速度还能额外带来 **1.5 到 2 倍的物理级提速**，且伴随 Token 数量的膨胀呈现近乎线性的提速增益。

提示词缓存采用的是**最长公共前缀匹配（Prefix-based caching）**。请求在读取缓存时，会严格比对到与历史请求发生哪怕单字节分歧的第一个字符为止。这意味着：**不仅上下文里包含什么内容至关重要，各段内容的物理摆放次序更是具有决定性意义！** 务必将请求严密拆分为三个梯次，严格按照“变动频率由低到高”由前至后排布：

- **全局静态区（Global Segment）**：绝大部分系统提示词与完整的工具函数定义，在全站所有用户的会话中完全恒定一致。这是你最热乎的缓存资产，在大规模并发下几乎永远不会过期。必须确保其在不同会话与不同轮次之间保持**逐字节严格一致（Byte-identical）**，并在其末尾钉上第一个缓存断点（Cache breakpoint）。
- **会话级稳定区（Session Segment）**：特定用户的个性化上下文与本场对话的历史消息。它们在不同用户间互不相干，但在该用户的单场多轮会话中保持高度线性递增与相对稳定。该区段严格排在全局静态区之后。
- **轮次易变区（Volatile Segment）**：任何在单场会话内高频跳变的信息，比如当前精确到秒的时间戳、或是用户刚刚跳转切换的最新页面 URL。**必须将它们死死按在请求的最末端**——要么作为最新一轮用户消息里的标签块传入，要么在支持[会话中途系统消息（Mid-conversation system messages）](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)的模型上，作为系统角色消息追加在消息数组最后。我们在业界见过最惨痛的低级失误，就是把当前时间戳或当前页面 URL 大大咧咧地写在系统提示词的最开头，导致全站每一次网络请求都在第一行瞬间打碎缓存！

![前缀缓存三段式分层排布示意图：全局不变、会话递增、末端易变](https://assets.claude.com/e6fbdecfcdda588a29d70f54cde5c09d17a921aa.png)

在此有两个关键实现细节不容忽视：
第一，技能（Skills）的加载应当作为工具调用的返回值（Tool results）追加在消息流中，而非动态拼接到系统提示词的头部。这样技能的正文便会自然沉淀在会话前缀中，并伴随历史记录一起被平稳缓存起来。
第二，在每一轮交互中，**把你的缓存断点持续向前滚动（Roll breakpoints forward）**：单次请求所允许标记的断点数量是存在硬上限的，因此应将最新的断点始终平移到每轮最新一条用户消息的末尾。这样一来，下一轮交互就能完整从高速缓存中调阅包括庞大搜索回包在内的全部历史沉淀。

![缓存断点在每一轮会话中持续向最新用户消息末尾平移滚动的机制图解](https://assets.claude.com/bdf3f158eeed3dc122c1bb2d04eee5343405ca93.png)

### 模型选型与精细化配置

[模型体积大小与思考力度（Effort level）设置](https://claude.com/resources/articles/claude-model-and-effort-level-in-claude-code)本质上面临着完全相同的权衡公式——**智商水平 vs 延迟与成本**。唯一的选型准则是：**用客观数据指标说话。**

1. **确立底线与核心指标**：明确定义支撑你业务大盘的核心质量红线（任务完结率、回答相关度、真实性准召率）、绝不妥协的评测最低分门槛，以及团队对于 P50/P99 延迟与单次任务成本的刚性预算。
2. **进行全矩阵拉网测试（Sweep）**：让你的全量评测集，跑遍所有备选模型与 Effort 思考力度的排列组合。在起步探索阶段，我们建议商家端 Agent 从 Opus 起步（因其重度依赖深度归纳与复杂多维分析），而 C 端消费导购 Agent 从 Sonnet 起步（因其对前台延迟更为敏感）。如果你已拥有线上真实流量，请务必按真实的查询流量结构进行加权核算。让真实跑分决定选型——有时候，Opus 5 在撬动高价值加购转化任务上展现出的超高胜率，完全能证明其相对 Sonnet 的溢价是超值的；而在另一些场景下则未必。
3. **带着辩证思维审视跑分结果**：有两类现象经常让团队大跌眼镜。第一，提示词往往是高度针对特定模型深度定制的；拿一套给小模型写的提示词直接拉网测大模型，跑分可能严重失真——小模型往往需要保姆级详尽的规约，而大模型早已能举一反三，甚至大模型会因为死板遵守了小模型原本选择性忽略的某条陈旧指令而发挥失常。在全盘推翻某个候选方案前，针对其失败案例进行几轮轻量适配迭代是极具性价比的动作。第二，一个智商更高的配置，在最终端到端耗时上（尤其是在 P90 和 P99 的长尾难案上）**经常反而跑赢智商低但 Token 吞吐更快的模型**，因为高智商模型在复杂任务上的工具规划极度精准，不需要反复试错返工，总交互轮数大幅缩减。

务必以**“单个成功完结任务的综合成本”**而非“单次 API 调用的绝对价格”来算账。一个虽然便宜但需要用户多来回扯皮几轮、甚至频繁跑崩导致重试的弱模型，在商业账本上绝对更加昂贵。当几款模型的综合表现势均力敌、且成本与延迟均在业务承受范围之内时，**果断拥抱更高的智商水平**。唯有卓越的交付质量能够铸就用户的长期留存与信任壁垒，并为未来半年模型能力的持续迭代预留充足的演进空间。

## 生产环境工程化落地

**跨会话记忆、刚性安全体系、严密评测流水线，以及如何在大规模组织中跨部门协同交付：这些才是决定一个商业智能体能否在真实的生产恶劣环境下立足并长盛不衰的生命线。**

### 能够跨越会话的长期记忆（Memory）

你与客户建立的长久信任与亲密互动至关重要。记忆系统正是让智能体能够平滑接续上一次对话的断点、而非每次都像陌生人一样重头再来的核心引擎。一个在 3 月份随口提过自己对坚果严重过敏的食客，绝不应该在 6 月份点餐时还要被迫再交代一遍；一个每周一清晨都要复盘同一份投放报表的运营专员，不应该每次都要手动罗列那些繁琐的参数。

跨越会话的长期记忆绝非凭空产生，而是一套必须由你亲手构筑的工程体系，涵盖三大模块：**事实如何持久化存储、事实如何被提取沉淀、事实如何在交互中被读取。**

#### 记忆的持久化存储

**记忆归属于你的业务数据库，而非大模型的参数权重。**

在用户画像规模极小且只有智能体单方读取的玩具场景下，纯文本 Markdown 文件或许勉强能跑通。但在面对真实的商业洪流时，它很快就会崩盘；最务实的工业替代方案，正是你团队日常运维的现成数据库。一条记忆本质上一条强类型的微型记录：一个确定的 Key（如 `shoe_size` 鞋码、`default_store` 常用门店、`preferred_report_cadence` 偏好报表频次）、一个简短的 Value、所属类别以及提炼出该记忆的原始会话来源。部分通用 Key 由你提前白纸黑字定义到位；其余长尾字段由提取器智能挖掘。数据库架构让记忆即便在千万级膨胀下依然保有极佳的高性能索引能力，能与你现有的会员用户主数据无缝关联（Join），并支持你在特定属性上构建完全确定性的业务规则。

对于商家端的运营智能体，**务必以“具体的人”而非“商户账号”为维度建立记忆索引**。同一个商家后台账号往往有多名运营员工共享操作，每个人必须拥有自己隔离的偏好上下文；且记忆的查阅必须严格遵循该员工真实的系统角色权限（RBAC）——门店店长的助手绝不能回溯跨区域大区经理曾披露的商业事实。

在商业语境下，智能体记忆承载着极其敏感的个人隐私数据。最值得被记住的事实，往往恰恰是法律法规监管最严苛的重灾区，不同主权法域的合规标准天差地别。必须将记忆视作一项严密的**数据安全与隐私治理工程**：
- **明确圈定准许落库的记忆类别**：在底层写入链路上配置独立的校验拦截器（Validator），每一笔入库都必须经过强校验，严禁单纯依赖提示词做君子协定。
- **赋予用户清晰的查阅、修正与彻底注销权**：将记忆的删除彻底打通进企业现有的账户注销与 GDPR/个人信息合规数据抹除流水线中。
- **设定合理的记忆生命周期（TTL）**：几年前的陈旧偏好在今天大概率早已过时甚至产生误导，设置记忆过期淘汰机制有助于保持记忆库的鲜活度。
- **支持按部署集群一键熔断降级**：必须支持单租户或单区域维度的记忆功能硬开关，以便让那些无法承担此类法务合规风险的特定国家与地区在关闭记忆的状态下依然平稳运行基础导购服务。

#### 记忆的异步提取与写入

**记忆的提炼与写入必须在后台完全异步（Asynchronous）执行。**

在每一轮对话结束时，或者在长会话中每隔几轮交互，由一个挂载在独立子线程或后台异步任务中的抽取模型阅读最新的对话流水，在存储中心中完成记忆事实的新建、更新或删除，并在会话推进中维护其专属的工作上下文。

这项设计**不会给前台用户会话带来哪怕一毫秒的额外响应延迟**，并且在我们内部的商业记忆专项评测集上，**取得了高达 13% 的事实召回率提升**！

那种看似显而易见的替代设计——在主智能体上挂一个 `save_memory` 工具让它自己在对话中调用——在面对延迟敏感的商业场景时是一个彻底的反模式：
每一次存储动作都会硬生生抢占前台交互的一个轮次；除非你把整个记忆库全量塞进当前上下文，否则保存前往往还要先读一遍数据库以防重复，凭空多浪费一整轮网络往返。更致命的是，这在每一步都平添了一道心智竞争负担，在我们严谨的评测中，这种注意力分散直接体现为大量核心事实的严重漏记。

将抽取智能体剥离成独立后台，还能让你对其 Prompt 施加极其严苛的定向约束：它**严格仅阅读用户与助手的纯文本言论，坚决屏蔽所有工具回传数据**，这就彻底杜绝了将商品详情里的广告文案或不可信的用户评价误当成用户个人真实特征的荒谬事故。抽取器的提示词会清晰界定什么才是真正的事实（明确表达的尺码、饮食过敏忌口、履约自提偏好、商家日常固化的物化视图），并坚决剔除任何来自商品列表的短暂一次性细节。

![独立的记忆抽取智能体在后台异步阅读文本并落库的架构流程图](https://assets.claude.com/516a22932c1a2eea15f8ad38c385e479e1b37408.png)

#### 记忆的三层阶梯式读取

在需要调阅记忆时，采取清晰的三层分流策略：

- **第一层：全局常驻上下文（Always in context）**。极少数核心事实在每一轮交互中无条件常驻在会话上下文内：包括几乎每一笔订单都要依赖的关键字段，如消费者的默认履约门店、配送偏好，或商家操作员的所属组织架构与角色权限。
- **第二层：按轮次智能预取（Pre-fetched per turn）**。基于触发技能的相同外部先验特征，在每轮交互前定向预拉取相关事实：例如当检测到用户在搜索鞋类时，瞬间预取其过往鞋码与喜爱品牌；当商家询问营销大盘时，定向预取该运营专员习惯调阅的几项核心分析维度。
- **第三层：按需挂载查询工具（Behind a lookup tool）**。其余所有长尾偶发记忆，全部收拢在一个只读的记忆检索工具之后，仅在模型发起明确探查时由其自主调阅。

由于记忆归属于单个用户的私有上下文，所有这些记忆事实在请求排布中**统统归入第二段会话稳定区（Session Segment）**，位于全局静态缓存断点的后方。

### 刚性安全围栏：必须由宿主运行环境（Harness）兜底锁死

系统提示词是安全行为约定的起点，但在商业与金融交易的严酷战场上，**提示词绝不能成为你落实安全的最终阵地！**

这里的失控往往直接伴随着真金白银的财务损失与不可逆转的合规灾难；而写在提示词里的戒律，只需一次刁钻的越狱注入（Jailbreak injection）或一次极端的采样偏差，就会被大模型视若无睹。以下列出的每一条风控红线，**统统由宿主程序（Harness）在代码层刚性卡死**，在面向消费者和商家的两侧端到端统一执行，一次定义，全运行环境无差别生效。

#### 1. 模型仅负责“暂存提案”，由人类或既定策略负责“审核生效”

**任何大模型的工具调用，都绝不允许直接触发真实的资金划扣或直接修改线上商业生产环境！**

下单结算、付款划转、发起退款、调价修改以及营销活动的正式上线，最终全部必须收口于由宿主框架完全掌控的确定性安全操作，绝不假手大模型。

在面向 C 端消费者的链路中，这种设计在架构上是绝对物理隔离的：结账工具所能做的一切，仅仅是向前端抛出一个带有“立即支付”物理按钮的待付款订单组件，而智能体所能触碰的后端 API 中，**压根就不存在任何能够直接发起真实扣款扣费的接口**。

在面向 B 端商家的链路中，任何写入类工具生成的都只是一份带有服务端全局唯一 ID 的**待生效暂存提案（Staged change）**；底层的 `apply_change` 生效接口只会接受那些经过真实管理后台物理按钮点击确认、CLI 明确批准、或者通过 Managed Agents 平台自带的工具确认弹窗明确核准过的 ID 才能放行生效。

在最终点击生效的瞬间，所有风控护栏都会**对照当前最新的实时限额重新执行全量核验**，而非以该提案当初生成时的旧状态为准。不论前端交互形态如何，底层模型永远不变：**大模型所能做出的最危险动作，仅仅是“提出建议（Propose）”**；而最终的放行审批，必须严密嵌入你们企业既有的双人把关机制（Maker-checker flow）之中。

#### 2. 写入与渲染操作仅认“服务端签发防伪 ID”

宿主运行环境会在每场会话中，严格记录服务端向该大模型发放过的每一个合法 ID。**这一私有白名单记录，是任何后续写库工具或前端渲染组件所能接受的唯一合法凭证！**

购物车只认当前会话中服务端真实返回过的商品 ID；商家端工具只接受大模型此前在本次对话中真正查阅过的真实 Listing ID 与营销活动 ID。任何通过其他旁路进来的 ID——无论是大模型凭空幻觉捏造的、用户在聊天框手动粘贴的、还是埋伏在第三方评价暗处的注入 ID——在触碰到底层真实业务接口之前就会被宿主程序直接斩断。

前端 UI 渲染同样受此铁律庇护。呈现工具入参只收 ID，服务端在拦截到调用后，会亲自从数据库中取出最权威的商品、订单或变更明细并填充回传。因此前端卡片上所渲染出的每一个像素，都是服务端亲自核准填充的产物。

这条规则同样严密覆盖了派生子智能体：负责分析数据的商家端子智能体虽然可以读取业务数据，但绝对无权向主智能体的“可写入白名单 ID 库”中注入任何新 ID。

针对关税税费、法定免责声明以及其他受高度监管的法定合规文案，大模型只负责判定针对哪款商品进行披露，而展示出的每一个字都由服务端严格从法务核准的静态文案库中整段提取。这些核心法务字段常驻在商家助手的受保护白名单中，买卖双方任何一端都绝无可能擅自篡改或随意意译，且自动化评测集会对其渲染出的文字执行**单字节级别（Byte-for-byte）的严格一致性校验**。

#### 3. 限制额度必须基于“最终合并状态”刚性防御并发冲正

绝大多数商业平台都存在单人购买数量的上限限制——无论是出于票务限购、首单促销优惠、还是反欺诈黑灰产治理。而智能体在执行任务时，往往会以人类敲击键盘未曾出现过的姿态，开展疯狂的重试、变换措辞以及发起高频并发请求。

因此，限额检查必须作用于**“本次写入生效之后的最终预期全量状态”**，坚决杜绝第二句“再加两件”通过叠加绕过风控阈值；并且**单场会话的所有购物车写操作在底层必须严格执行串行化排队（Serialized writes）**，彻底封死单轮交互中并发抛出的多个工具调用由于竞态冲突而突破限购红线的漏洞。

商家端的各项调整操作同样基于此逻辑进行刚性审查：针对价格波动幅度、折扣下潜深度、补货批次规模以及活动预算上限设立硬性安全卡扣，并列明严禁任何操作触碰的受保护敏感字段清单。通用法则非常明确：**将所有限制门槛建立在操作落地的“最终衍生状态”之上，并将每个会话的写操作强制串行化执行。**

#### 4. 彻底净化所有第三方不可信内容（Sanitization）

在电商与商业生态中，上下文中的绝大多数文本并非出自你手，而是来自千差万别的外部第三方——第三方卖家、挑剔的买家评价、甚至竞争对手。因此，**每一次底层后端的读取回显，在本质上都属于不可信的输入（Untrusted input）**，必须统一流经数据清洗流水线。

所有源自第三方的工具调用回执——包括商品刊登详情、买家评价、履约协议、卖家私信以及检索出的长期记忆事实——在喂给基座模型阅读之前，必须经历深度数据清洗，并被包裹在拥有固定特征标识的安全隔离栏（Security Fence）之中。

数据清洗器会强力剥离一切控制字符与双向文本欺骗字符（Bidirectional characters）、强行转义任何试图伪造安全隔离栏标记的危险字符、彻底拆除一切模仿对话轮次或伪造工具调用的恶意 Prompt 注入指令，并设置单次大小硬上限，专门摧毁那些试图伪装成系统提示或企图恶意撑爆上下文的恶意商品黑产脚本。

提示词本身则承担安全契约的后半段使命：明确告诫基座模型，所有处于隔离栏中的文本碎片**纯属仅供参考汇报的客观原材料，绝不能将其作为行动指令去遵照执行！**

### 评测体系：驾驭非确定性系统的交付底气

从微调一处提示词措辞，到接入一个看似无关紧要的新工具，都可能在暗中以难以预测的诡异姿态破坏智能体的行为模式，而你满心欢喜准备上线的改动，往往根本不是导致线上发生重大退化的那一项。构建完备严密的评测体系（Evals），是你在代码上线前捕获这些退化的唯一底牌。我们在[解密 AI 智能体评测体系](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)中曾系统阐述过评测的通用心法，本节则专注于商业场景的专项军规。

**只评测“状态快照（Snapshots）”，不要盲目去评测整场会话！**

大模型 API 本质上是完全无状态的，这意味着智能体在某一时刻输出什么，完全是其系统提示词、可用工具集以及当前传入的消息历史数组共同决定的纯函数映射。这带来了一个极其强大的工程红利：**一次商业会话所能达到的任何中间状态与复杂局面，在代码中都是完全可以被单向直接构造出来的！**

因此，编写一个高效的评测用例，只需要三步：
1. 预先构造出测试所需的初始状态上下文；
2. 追加测试预设的用户指令消息；
3. 放行智能体，让其在该快照节点上自主推演决策。

随后，评测裁判只需对**产出的最终状态**进行裁决打分：核验最终生成的业务状态，以及呈现给用户的回包结构（包括最后那次写操作的入参合法性）。在绝大多数工程实践中，**我们强烈反对去给“智能体究竟走了哪条路线才达成这一目标”进行死板打分**——这类过程导向的评测极其脆弱且作茧自缚，剥夺了模型探索更优路径的灵活性。

至于**“由两个模型双向演戏的模拟用户评测（Simulated-user evals）”**（即由一个模型扮演挑刺用户、另一个模型扮演客服、再由第三个裁判模型对整场聊天漫游打分），在工业级量化度量中是一个极其劣质的工具。两个非确定性黑盒系统互相碰撞，不仅需要指数级庞大的样本量才能消除方差、每次运行成本高昂，而且裁判极难做出客观裁决，一旦发生失败甚至很难归因究竟是谁的责任。模拟用户评测唯一的价值，是在开发初期做个大体的“体感抽检（Vibe check）”或探查未知盲区；一旦借助模拟对练发现了新的漏洞案例，**立刻将其固定为单一状态快照（Snapshot）的精准测试用例**！

#### 专门设计极端恶劣环境下的极限压力用例

绝大多数团队的评测套件之所以形同虚设，是因为他们未能对注入的初始上下文进行严谨的极限压力测试。一个高质量的测试 Case，必须精确包含诱发缺陷的先决条件，而不仅仅是交代一句话需求。如果某个 Bug 只有在第一轮经历过高密度的多次工具调用后才会暴露，或者只有在会话前文存在自相矛盾的背景下才会诱发，那么一个从干干净净的空白上下文起步的用例在任何配置下都会轻松通关全绿，根本无法提供任何有价值的测试信号。

我们发现业界绝大多数评测套件都充斥着大量这种“岁月静好”的纯净用例。请务必确保你的用例库中有相当一部分用例，是故意从漫长、混乱、甚至充满前后矛盾的恶劣历史上下文中启动的！

#### 全面覆盖商业智能体评测的五大核心维度

严密的评测套件，必须兼顾针对“期望达成行为”的正向测试，与针对“严禁逾矩行为”的反向拦截测试。

**针对每一个正向用例，都请同步编写其对应的反向孪生用例**：有“应当受理”的用例，就必须配对有“坚决拒绝”的用例；有“应当直接代办”的用例，就必须配对有“必须主动反问确认”的用例。缺少反向负样本，是我们在各类评测库中看到最普遍的通病。

必须全量覆盖以下五大核心领域：

1. **占据绝大多数日常流量的大盘核心用例（Core requests）**：任何此类用例的退化都会直接重创全网基础盘。涵盖简单属性查询、包含多重筛选条件的复杂检索、商品与资费套餐详细对比、以及跨多个意图的复合诉求。针对问答类用例，必须严格核验输出的所有价格、库存可用性与关键参数是否均能原封不动地回溯至底层接口返回的数据源，并核查智能体在数据缺失时是否能够诚实告知，而非凭空胡编乱造。
2. **重度依赖上下文的用例（Context-dependent requests）**：例如指代屏幕上刚刚渲染出的特定商品、承接前几轮交互中留存的筛选约束、以及基于现有购物车实施的追加或删减动作。记忆系统的有效性测试同样归属此类：检验记忆事实是否被精准提取、是否在后续会话中成功调阅、并且是否切实改变了智能体最终的作答策略。
3. **触碰资金与品牌合规红线的风控用例（Safety and brand cases）**：一旦发生漏网将直接招致巨额罚单或公关危机的致命场景。包括尝试提示词越狱注入、尝试越权刺探他人隐私数据、以及法务强制监管用语的单字节严格校验。请将注入反测严格拆解为两类专项用例：一类是用户自发在输入框发起的用户侧直接注入；另一类是潜伏在商品标题、用户差评或外部网页碎片中，企图借助工具回包发起暗度陈仓的**数据面间接注入（Data-plane injection）**。
4. **交互契约与组件呈现测试（Interface evaluations）**：确保智能体唤起了完全匹配业务预期的正确前端交互组件、严格遵循了商品限购上限，且在最终渲染给消费者的自然语言文案中，绝对不会遗漏暴露任何内部系统 ID 或死板字段名；同时充分覆盖接口超时与空数据兜底表现。
5. **跨越多个复合业务域的综合用例（Cross-capability requests）**：例如一位商家运营提问：“如果我把这款商品直降 15%，现有库存能撑得住接下来的爆发需求吗？” 这既是一个极其典型的定价促销问题，又是一个库存周转测算问题。唯一完美的正解，是将降价方案暂存为提案，同时紧密附上对应的库存消耗模拟推演；而只做了降价计算却忘了看库存，或者只报了库存却忽略了调价影响的答案，统统属于不及格的残缺回答。单按各个业务域孤立编写的用例根本无法揪出这类毛病，因为各自的裁判只负责给自己的半拉子逻辑打分。必须针对那些需要相邻能力紧密交织的业务场景编写专项复合用例，对答案的两半同时进行严格打分。

#### 联手业务专家（SME）共建用例，把每一次真实线上故障沉淀为基准

请深度联手那些在线下一线亲历各种业务事故与客诉反弹的领域专家（SME）——包括产品经理、法务专家、商家运营、一线资深客服以及品类类目经理——共同打磨评测用例。**真实的线上故障，永远是全世界最顶级、最值钱的评测案例**；在起步阶段，每个关键业务流沉淀出 50 到 100 个典型快照用例是一个极佳的基准水位。

生产环境的日志脱敏实录是源源不断孕育新用例的最佳沃土，尤其是那些让人哭笑不得的刁钻长尾案件。编码智能体同样极其擅长基于现有模式批量推演生成更多的边界样本与对抗性变体。在我们开源的[官方参考仓库](https://github.com/anthropics/commerce-agents)中，内嵌了一个基于 Claude Code 深度定制的评测撰写插件技能，完美复刻了这套推荐的最佳实践流程。

#### 大型企业组织中的跨团队协同发布之道

在一家大型商业集团中，智能体的底座是由无数个工程团队共同托举起来的。搜索团队、交易结算团队、计价促销团队、营销平台团队、智能客服团队以及商品主数据平台，各自独立运维着智能体所依赖的微服务底层，每个团队都拥有自己独立的发版节奏，且随时都可能需要为智能体追加或修改一个工具、一项技能、或是一段系统提示词。

与边界森严的传统微服务架构截然不同：**智能体内部根本不存在用于自我封闭的物理模块边界！** 计价团队对提示词或工具做出的细微调整，会瞬间与结算团队共同挤在同一个上下文窗口内翻滚。

面对这种痛点，很多架构师最容易犯的错误就是因噎废食，试图按照行政组织架构将系统拆得稀碎，给每个事业部单独搞一个独立的子智能体。正如前文第一章所详述的，这种架构在交付质量与体验上往往会带来灾难性的退化。我们在这里给出历经大厂实战检验的多团队防退化协同规范：

- **权限权属严格对齐现有业务系统**：每一项技能和每一个工具在组织中必须确立**唯一的单一归属团队（Single owner team）**。例如，计费团队全权负责促销工具集与定价技能，客服团队全权负责订单售后工具集与客户关怀技能。共享的系统提示词建立平台级法定 Owner 负责维护通用基座骨架，各业务域专属段落由对应的领域团队独立维护。
- **改动必须与用例绑定提交，CI 实行精准分层跑测**：任何团队在提交一项新技能或新工具变更的同时，必须连带提交其配套的全套评测用例（包括反向负样本用例以及与相邻技能之间的边界摩擦用例）。在每一个 PR 提交时都全量跑完数千个庞大的评测用例既不现实也过于烧钱，因此应当从评测库中精选出一套高效的 CI 拦截子集：该集合必须包含大盘最高频用例以及全部核心安全用例；在此之上，根据本次 PR 改动的代码范围**实施精准定向测试**——修改某项技能，则仅触发其自身用例及其相邻技能的边界用例；修改某个工具，则仅跑调用了该工具的关联用例；而一旦有人动了全局共享的系统提示词，则必须强制执行全量全矩阵拉网测试。我们建议设立基于多次试验平均胜率的硬性卡点，并对缓存命中率以及单轮交互成本设定红线。此外，每天夜间以及每次全站正式发版之前，全量评测套件必须完整跑通一次，绝大多数跨团队暗度陈仓的逻辑冲突正是在这一夜间大盘扫描中被及时捉拿归案的。
- **将智能体纳入全站统一的发布日历排期之中**：智能体是一个高度集成的单一交付发布单元，一次糟糕的上线改动会在瞬间同时席卷全站所有用户。对提示词与技能的变更，必须首先切给小规模灰度人群（Canary cohort）进行金丝雀试跑验证；必须在底层架构上保留“无需重新发布代码即可通过开关秒级下线某个故障技能”的热熔断机制；并且在双十一、大促黑五等年度核心高峰期到来之前，必须像冻结底层核心交易系统一样，对智能体实施严格的**全站封版冻结（Freeze）**。

关于在人机协同中如何理顺组织分工，亦可参阅我们的专项论著：[如何构建高效的人机协作团队](https://claude.com/resources/articles/building-effective-human-agent-teams)。

## 展望未来

通读至此，你会发现本文所探讨的核心精髓，**绝大部分其实都与底层的 AI 模型本身无关**。工具承接的是你早已在线上稳定运行的核心中台，技能固化的是你原本就在推行的标准作业规程，评测用例是你将产品需求文档（PRD）以测试代码形式进行的白纸黑字呈现，而宿主运行环境（Harness）所刚性锁死的风控法则，本就是你面向任何外部客户端都必须坚守的安全红线。

基座模型必将持续进化迭代；而当下一个更加聪明的基座模型横空出世时，本文所阐释的优雅架构，允许你仅仅通过一次配置变更配合一次全量评测拉网测试，就能以极低成本平滑完成升级换代。其余所有的业务基础设施全部岿然不动，持续稳定运转。

同样重要的是，请在产品矩阵的长远演进路标上放开想象力。这一套深厚的技术架构，其生命周期将远比当前屏幕上一个小小的浮动聊天窗口（Chat panel）长久得多。完全相同的智能体架构，可以无缝迁徙至语音交互场景；它甚至可以在航班价格跳水的瞬间，赶在用户开口之前便主动发起关怀与动作预判。对于已经拥有完备评测套件与稳健工具体系的团队而言，探索这些全新的交互形态，仅仅是多写几个前端展示层组件的轻巧工程而已。

更长远来看，未来光顾你线上店铺的大量访问流量，将不再仅仅是拿着手机刷屏幕的自然人，而是代表人类顾客自主前来挑选采购的“用户端代理智能体（Buyer Agents）”。今天为了约束你自己的智能体而精心打磨的这一整套溯源核验、提案暂存以及双人把关审批流程，恰恰也正是未来你能安全放心地向外部全网智能体敞开底层商业能力大门的核心基石！

商业的历史，向来重奖那些能够把交易摩擦降到最低的先驱。智能体正在让这一切变得前所未有的轻松通达。欢迎查阅我们的[全套开源参考工程实现](https://github.com/anthropics/commerce-agents)，包含面向消费者与面向商家的双端完整智能体源码，以及覆盖零售、出行、通信与泛娱乐领域的开箱即用可运行示例。
