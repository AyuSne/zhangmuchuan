在 Claude Code 团队，我们绝大多数代码（约 90%）都由 Claude 编写，[也由 Claude 审查](https://claude.dev/blog/solving-code-review-at-anthropic/)。到了这个量级，“如何让智能体用证据验证自己干的活”就变得极其关键。

验证闭环（verification loop）是把更多工作委派给 Claude 的基石。没有它，你同时最多只能跑一两个 Claude——因为所有东西都得你自己核对。有了它，几十上百个并行跑都不成问题。

原因很简单：给智能体一条[验证自己产出物](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills)的路子，是提升质量最有效的办法之一。在针对结构化文件生成的内部测试中，让一个独立的评分器（grader）按评分量表（rubric）给 Claude 的成果打分，相比标准的提示词循环，[任务成功率最高提升了 10 个百分点](https://claude.com/blog/claude-managed-agents)，而且难题上的收益最大。

过去验证起来很昂贵的东西——测试、基准（benchmark）、规格（spec）、真实的端到端跑一遍——现在让智能体去做，成本低到可以随手要求。和写代码一样，测试、基准、规格它也能飞快生成。而且一旦生成，这些测试和基准就是以软件形式运行的，可以高频重复执行，几乎不再额外烧 token。

你还可以用验证结果反过来提升智能体在这类任务上的表现，把闭环真正合上。比如某个智能体反复栽在一个“检查日志里有没有用户数据”的测试上，你就可以加一个 hook，或者往 CLAUDE.md 里写一条更明确的规则，避免以后再犯。这样（基本上）能防住同一个坑踩第二次。

那么，既然验证是“高速产出优质代码”的关键，你该用哪几类测试？又该如何把它们铺到整条流水线上？本文回答这两个问题，同时分享 Claude Code 团队自己的一套做法。

## 并非所有测试都生而平等：值得投入的三类测试

不管你选哪类测试，有几个坑都得躲开。

测试要是不稳定（flaky），你等于在训练智能体“看到红灯就重跑”，而不是去修那段坏掉的代码。测试要是太慢，智能体就会少跑几批，问题反而更难定位。越是重的测试，越应该放在代码提交之前跑。

下面是我认为最值得投入的三类测试。

**端到端测试（E2E）**

如果只能押注一类，就选端到端。这类测试描述的是真实的用户操作流：把商品加进购物车、下单结算、跳到确认页。

端到端之所以好用，在于它很难被糊弄——整个功能要么能用，要么不能用。它还有明确的完工标准，并且能具体告诉你哪里坏了。

![对比示意：单元测试失败只留下一句「Error: Timeout after 30s」；端到端测试失败则给出步骤追溯（注册、加购、结算、确认页）、失败截图，以及「结算这一步因为支付表单没加载而一直置灰」的具体说明](https://pbs.twimg.com/media/HXT0UI1aEAABki1?format=jpg&name=large)

单元测试可能只会甩给你一句 “Error: Timeout after 30 seconds”，而端到端测试能给你一张截图，外加一句坏在哪的说明。

单元测试确实更快、也更少抖动，但它可以全绿而功能照样坏掉。因为智能体和这份测试本身，谁都没真正吃透完整任务。

做端到端时，最有效的做法是让智能体在真正跑起来的系统上有手也有眼。你可以写一个 skill，用 [CDP](https://chromedevtools.github.io/devtools-protocol/)（**Chrome DevTools 协议**）、模拟器或 API 测试框架把应用启动、驱动起来，再顺手检查。

功能地图（feature map）可以同时充当智能体的导航图和评分量表：它通常从用户视角罗列功能，并写明操作路径、快捷键、选择器以及预期结果。

**属性测试：那些不该被攻破的约束**

很多测试是围绕“你事先想到可能出错的地方”写的。属性测试盯的是人容易漏掉的边界情况——而那恰恰是智能体最常翻车的地方。

做法是：先写下一句你认为绝不会失败的断言，然后交给属性测试库（JS/TS 用 [fast-check](https://fast-check.dev/)，Python 用 [Hypothesis](https://hypothesis.readthedocs.io/en/latest/)，Rust 用 [proptest](https://proptest-rs.github.io/proptest/) 等）生成成千上万个输入，专门来证明你错了。

几乎每个软件项目里都藏着一堆这样的属性：

- **往返编码**：“X 编码之后再解码，应该还是 X。”解析与序列化同样适用。
- **不变量**：必须永远成立的事，比如“账户余额绝不能变成负数”。
- **幂等性**：同一动作（迁移、归一化、重试）做两次和做一次效果一样。
- **等价性**：优化后的代码和朴素但正确的代码，结果必须一致。

属性测试库是让智能体没法偷懒的好工具：它给出的边界情况，不带写原始代码那套偏见。在重写场景里它尤其有用——此时规格早已和生产行为脱节，不再是可以信赖的验证来源。

**差分测试：把旧系统当标准答案**

在[大规模迁移](https://claude.com/resources/articles/ai-code-migration)这类“功能应当保持不变”的场景里，差分测试格外好用。它的做法是：把同一批输入同时喂给旧系统和新系统，看结果是否不同。一旦不同，就说明有 Bug 或不兼容变更等着你去修。

差分测试的关键，是喂随机生成的输入，或者生产流量的采样。此外还要做两件事：把空白字符这类无关因素归一化掉；再维护一份“已批准变更”清单，用来放过那些新环境本就该和旧环境表现不同的地方。

## Claude Code 团队如何思考验证

我们此前写过 Anthropic 内部[代码审查是怎么跑的](https://claude.dev/blog/solving-code-review-at-anthropic/)，这篇想把镜头再拉近一点，讲讲我们究竟如何验证自己的工作。

**验证就是真的把改动跑起来**

把应用端到端跑一遍，比测试本身更重要。没人会在没进模拟器试过的情况下就发一个 iOS 改动，对 Claude 也是同样的要求。

Claude 可以像人、或者像 QA 工程师那样把整个应用测一遍。Web 改动让它用 Claude 的 Chrome 扩展，移动端给它一个 iOS 或 Android 的 MCP，桌面端用 computer use，后端就要求它在本地把服务跑起来。

要把“怎么启动模拟器、怎么跑起应用”固化成规则，就建一个叫 verify 的 skill：放在仓库的 `.claude/skills/` 目录下，尽可能贴近相关代码，需要几个就写几个。Claude 知道该在提交改动之前先用上 verify。

然后，值得在这套 verify 上继续投精力，把它做得又快又稳。让 Claude 自己反复迭代、压测它。这就是你的冒烟测试台，必须做到铁打不动。

一旦给 Claude 一条端到端冒烟测试的路子，效果会好得多。你会看到它像人一样自己来回迭代，更快抓到真正的错误。在 Anthropic，几乎所有改动都是这么测的。

**测试挂了，就得人类接手**

没人能读完每一处改动，所以我们把“失败”当作一种判断依据：哪些地方需要人接手。Claude 会跑检查，并尝试修掉所有挂掉的地方；如果三轮之后还在挂，它就停下来，把人拉进来。

**代码所有者自己写检查**

谁的代码谁负责写检查，并一直打磨到“检查挑出来的问题，和所有者本人会挑的一致”。当某项检查把审查者叫来时，它应当说明理由，省得审查者自己对着 diff 猜。

**可靠性检查由 diff 触发**

我们维护着一份 39 条的可靠性检查清单。每一条都带三样东西：一个能从 diff 里读出来的触发条件、一项对应检查，以及它背后的线上故障或 PR 记录。其中一条是“`--resume` 会加载旧对话记录”。当会话存储或消息类型发生变更时，我们就会追问：新字段能安全加载吗？毕竟旧对话记录里根本没有这个字段。

Claude 读 diff，只挑触发条件命中的条目来查——通常是 3 到 10 条——这样没人需要把历史上的事故全背下来。

**一个审查者，多轮打磨**

我们不靠堆更多审查者来提升审查质量。在主审查者之上再加一个更贵、更强的审查者，往往不如把主审查者调好。我们的做法是写一份 [REVIEW.md](https://code.claude.com/docs/en/code-review-customize)，明确告诉审查者：针对这块代码，该盯什么。

我们还认为，审查与验证的每一轮都该在前一轮的基础上叠加。每一遍都直接指向上一轮的上下文和过往的失败，而不是从头把一切重查一遍。这样更便宜，也能挖出更多东西。

**改动不能动评判自己的那套检查**

如果一次改动能改掉评判它的那项检查，这项检查就已经废了。Code Review 始终从基线分支或默认分支读取 REVIEW.md，[绝不从 PR 自身的改动里读](https://code.claude.com/docs/en/code-review-customize)。Claude Code 团队会把“把关改动”的规则放在一处改动本身碰不到的分支上。

另外，Claude Code 团队把审查和具体的 commit 绑定。如果在审查进行时有人又推了新代码，这次审查结果就失效了——一个过期 commit 上的“审查通过”毫无意义。

团队还坚持先跑便宜的检查。如果智能体在本地还没测过就推送，它花掉的是大家共享的审查和 CI 时间，而这个 Bug 本来它自己就能抓住。在我们团队，Claude 会在开 PR 之前先跑测试、构建和 Linter。你可以用一个 [hook](https://code.claude.com/docs/en/hooks) 在 Claude 收工时自动跑测试，或者设一个“测试全绿”的 [/goal](https://code.claude.com/docs/en/goal) 来强制这一点。

**新关卡先以观察模式上线**

在我们自己的仓库里，每个 commit 都会被打上“它是怎么被验证的”标记。标记里甚至有“none”这一档，好让我们能查出那些压根没验证过的提交。

我们还做了一个提交卡点（commit gate）：只要这次会话里没跑过 /code-review 或 /verify，它就可以把提交拦下来。它有三种模式：关闭（off）、观察（observe）和强制（enforce）。

观察模式只记录“本来会被拦下什么”，方便我们复核误报，确保没人被白白波及。

强制模式则会真的拦住提交。不过任何提交都可以在提交信息里说明“为什么没做验证”。如果同一次会话里已经被拦过两次，第三次就放行，免得 Claude 卡死——毕竟 Claude Code 也不是完美的。

**拿真正要紧的事来检验你的检查**

Claude Code 团队还会定期审查审查者。我们跟踪三组数：合入之后又被回滚的改动有多少、维护者在合入前打回的改动有多少，以及一组规模匹配、至今保持干净的改动作为对照。

也可以做得更正式，建一套评测。在[那篇代码审查文章](https://claude.dev/blog/solving-code-review-at-anthropic/)里，我们讲过 Code Review 团队如何基于历史故障和回滚搭起评测：对每个样例，他们把仓库还原到当时审查那一刻的状态，再给出用一句话写成的“标准答案”，点明 Bug 究竟是什么。只有准确描述了这个 Bug 的发现才算得分。他们还把已合入且稳定的改动当作对照组，防止过度报警。调参用的集合单独拆开，与用来评估系统的固定测试集互不重叠。

他们还会把三个阶段的召回率分开算：原始发现、验证之后、以及最终审查输出。这样才能看出系统是否在把自己已经找到的 Bug 弄丢。如果把这一切压成一个端到端总分，这种细微差别就全被抹掉了。

除了“准不准”，我们还关心另一个维度：这条意见值不值得改。一个合格的审查者能抓出几乎所有技术上确实成立的问题，但人真正在意的是：这个 Bug 是必须修、该修，还是只是吹毛求疵。

Code Review 里就有这套设计，会把问题标成 [Important（重要）、Nit（吹毛求疵）或 Pre-existing（历史遗留）](https://code.claude.com/docs/en/code-review-pull-requests)。其中 Pre-existing 的意思是：这本来就是旧 Bug，审查者不该让本次作者背锅。

最后，Claude Code 团队会把召回率一直往上调，直到再往上一点就变成“对着评测集过拟合”、而非真的在抓 Bug 为止。

**把漏掉的补成规则**

在 Claude Code 仓库里，我们有两种把漏网案例变成规则的办法。第一种，是从人类代码审查意见和 PR 回滚里抽模式，找出共性问题。一条候选规则必须至少在两个 PR 里出现过、并且能从 diff 里识别出来，才算数。之后会派三个智能体专门去证伪它，最后由人在 PR 里审核批准。

第二种，是对一个对应着已知故障的 PR，让三个查 Bug 的智能体重放一遍。如果至少两个找出了那个 Bug，就说明它是可检出的。反过来，如果这么小的 diff 上还是漏了，那就是个真实的缺口，值得写成 REVIEW.md 里的一条规则。

不稳定测试也照此办理。Claude 不许跳过它、不许加 sleep、也不许一直重试到它变绿。如果查不出根因，就删掉这个测试，并写下为什么删。

规则本身也需要清理。测试套件、验证步骤和各类 .md 文件，你要是放任不管，它们只会越长越大，所以我们定期做一次梳理。

## 好测试，好结果

我们发现，给智能体一条验证自身工作、且反馈足够强的路子，效果天差地别。请把验证层当成一个正经系统来经营：让它待在“被它评判的那些改动”够不着的地方；用真正让你吃过亏的 Bug 来给它打分；它漏掉什么，就把教训写下来，别让同一个坑踩第二次；同时不断修剪这些教训，让它们始终值得跑。

做到这些，你的工作就从“读每一个 diff”变成了“定义什么叫完”以及“审阅证据”——而这，才正是让你能同时驾驭一大群 Claude 的原因。
